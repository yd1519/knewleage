# 项目深挖（一）：Scrapbound《废械星途》

**项目类型：** 模块化载具建造、程序化世界探索、物理玩法。<br>
**开发背景：** 腾讯超新星计划游戏赛，主题为“PCG + 物理”，一个月限时开发。<br>
**技术环境：** Unity 2022.3、C#。<br>
**个人职责：** 核心客户端开发，主要负责模块化载具、质量属性、浮力与阻力、程序化世界生成，以及核心玩法闭环。<br>
**复习范围：** 玩法拆解、零件拓扑、刚体映射、质量与惯性张量、体素浮力、逐零件阻力、确定性随机、地形生成与验证、语义内容生成、外围模块布局、事务式世界提交、存档与测试。<br>
**面试目标：** 不依赖具体 C# 代码，也能把每套系统的目标、数据、流程、算法、取舍和边界讲清楚，并能根据追问定位到对应实现。

## 一、先把项目讲清楚

### 1. 这是一款什么游戏？

玩家坠落在一颗由程序生成的星球上，需要在开放地形中回收废料，用零件不断改造载具，使它能够适应陆地、水域和部分立体区域。玩家收集三枚能源核心后返回撤离点，完成本局游戏。

核心循环可以压缩成：

~~~text
进入 Seed 世界
    ↓
驾驶载具探索
    ↓
回收废料，增加建造预算
    ↓
运行时增删零件，改变载具能力
    ↓
跨越坡地、水域和外围挑战
    ↓
收集 3 枚能源核心
    ↓
返回撤离点并结算
~~~

这个项目不是单独展示某个物理算法或 PCG Demo，而是把程序化世界、物理反馈和改车玩法连接成了一个能够从开始走到结算的完整闭环。

### 2. “PCG + 物理”如何真正影响玩法？

两部分不是互相独立的技术展示：

- PCG 决定这一局有哪些地形、水域、资源和挑战，以及它们在什么位置。
- 物理系统决定玩家当前搭建的载具能不能越过这些环境。
- 废料和能源核心的分布推动玩家继续探索。
- 运行时改车让玩家能够针对本局世界调整结构，而不是只能驾驶一辆固定车辆。

因此，世界生成的意义不是“每局换一张地图”，物理系统的意义也不是“车辆看起来会晃动”。两者共同构成了观察环境、调整结构、验证效果的玩法循环。

### 3. 一个月内如何控制范围？

项目早期尝试过更完整的多体车辆模拟，包括轮胎接触、悬挂、转向、刚体岛和动力传递。该方案的拓扑、约束和受力链耦合很强，调试成本高，不适合一个月的比赛周期。

后续把目标收缩为：

- 保留模块化拼装和结构影响运动的反馈。
- 保留动态质量、质心、惯性、浮力和阻力。
- 不追求完整的车辆工程仿真。
- 将开发时间投入到运行时改车、PCG 探索和通关闭环。

这次调整不是简单地“换引擎”或“降低难度”，而是重新判断哪部分技术最能服务玩法和交付目标。

### 4. 项目规模应该怎样表述？

当前工程中可以确认的资产规模为：

- `Assets/Scripts` 下有 175 个业务 C# 脚本。
- `Assets/Tests` 下有 42 个测试文件。
- 测试文件中共有 341 个 `Test`、`UnityTest` 或 `TestCase` 声明。

这些数字描述的是工程资产规模，不代表已经在当前环境重新执行并通过全部测试。面试时可以说“建立了覆盖核心模块的测试资产”，不要说“341 个测试全部通过”。

## 二、系统全景与数据流

### 1. 项目可以拆成哪些主要系统？

| 系统 | 主要职责 | 对玩法的影响 |
|---|---|---|
| Machine / Part | 表达载具和零件连接关系 | 支持运行时拼装、删除和结构拆分 |
| Mass Properties | 计算总质量、质心和惯性主轴 | 让质量分布影响加速、翻转和姿态 |
| Buoyancy | 查询动态水面并计算体素浮力 | 让排水体积和安装位置影响漂浮状态 |
| Resistance | 计算逐零件空气/水体阻力 | 让形状、朝向和遮挡影响运动 |
| PCG Pipeline | 从 Seed 规划并验证候选世界 | 提供可复现且基本可玩的地图 |
| Terrain Semantics | 保存坡度、水深、岸距、占位等语义 | 为环境和资源放置提供统一依据 |
| Runtime Commit | 构建候选世界并原子切换 | 避免生成失败污染当前场景 |
| Run Progress | 管理废料、能源核心、撤离和结算 | 串起完整游戏目标 |
| Archive / Command | 保存载具、校验合法性、撤销编辑 | 保证建造过程可恢复且预算一致 |

### 2. 一局游戏从生成到结算经历什么？

~~~text
Requested Seed
    ↓
生成候选地形、布局和水域
    ↓
验证坡度、高差、可达率、坑洼、水域等条件
    ├─ 不通过：派生新的 Effective Seed，确定性重试
    └─ 通过：继续生成表面、环境、资源和外围挑战
                     ↓
              构建 Pending World
                     ↓
              全部成功后提交
                     ↓
玩家探索 → 回收废料 → 改车 → 收集能源核心 → 撤离结算
~~~

### 3. 最重要的设计原则是什么？

这个项目里反复出现三条原则：

1. **逻辑拓扑与物理模拟分离。** 零件连接关系不能简单等同于 Rigidbody 层级。
2. **共享语义而不是各系统各猜一遍。** 地形、环境、奖励和验证读取同一份分析数据。
3. **先构建候选，再验证并提交。** 无论是生成世界还是加载车辆，都尽量避免先破坏当前有效状态。

## 三、模块化载具：零件树与 Rigidbody 层级为什么要分开？

### 1. 载具连接关系是什么结构？

当前版本把一辆载具约束为一棵有根零件树：

- `CorePart` 是主载具的根。
- 每个非根零件只有一个父连接。
- 从某个零件向下可以递归找到它的全部子结构。
- 不支持多父节点和闭环机械结构。

树的表达能力弱于一般图，但它让运行时增删、拆分、序列化和恢复更直接。当前玩法并不依赖闭环机构，因此这个限制是主动的工程取舍。

### 2. 零件树和 Rigidbody 层级分别回答什么问题？

- 零件树回答：“这个零件装在谁下面？删除它后，哪些零件属于下游分支？”
- Rigidbody 层级回答：“这个零件的碰撞、质量、浮力和阻力最终施加到哪个刚体？”

二者有关，但不是一一对应关系。多个零件可以共享同一个 Rigidbody。

### 3. FixedPart 和 MovablePart 有什么区别？

| 类型 | 是否拥有独立 Rigidbody | 物理含义 |
|---|---:|---|
| FixedPart | 否 | 与父级刚性连接，共享最近的父级刚体 |
| MovablePart | 是 | 允许相对运动，通过 Joint 与父级刚体连接 |
| Machine | 是 | 表示一棵独立模拟的载具或断裂分支 |

FixedPart 会把物理职责转交给最近的 Machine 或 MovablePart。安装在同一刚体下的 FixedPart 形成复合碰撞体，不需要为每个零件再增加一个刚体和固定约束。

### 4. 为什么不让每个零件都拥有 Rigidbody，再用 FixedJoint 焊接？

这样做实现直观，但有三个问题：

- 刚体和约束数量会随零件数增长。
- FixedJoint 仍要参与约束求解，可能积累误差并产生抖动。
- 一组本来没有相对运动的零件被拆成多个物理实体，调试和性能成本都更高。

因此，真正需要相对运动的部件才拥有独立刚体；其余固定结构共享刚体。

### 5. `ISimulator` 抽象解决了什么问题？

零件需要知道“由谁负责模拟”，但它不应该到处判断父级究竟是 Machine、MovablePart 还是其它类型。统一的模拟者接口可以提供：

- 所属 Rigidbody。
- 添加或移除子零件。
- 重算质量属性。
- 刷新阻力遮挡。
- 在模拟状态变化时传播设置。

它隔离了“零件连接关系”和“具体刚体拥有者”，让 FixedPart 可以把操作继续转发给上层模拟者。

### 6. 面试时怎样用一句话概括？

> 我用有根零件树管理连接和拆分，用 Machine 与 MovablePart 管理实际刚体；FixedPart 只参与拓扑和复合碰撞，不额外创建 Rigidbody，从而把编辑结构与物理模拟层级解耦。

## 四、运行时增删零件、结构拆分与撤销

### 1. 添加零件时发生什么？

添加操作不只是把一个 Prefab 放到场景里，还需要完成：

1. 根据连接点推导新零件的世界变换。
2. 建立父子连接并加入零件树。
3. 确定它应该共享父刚体还是拥有独立刚体。
4. 更新建造预算。
5. 重新计算受影响刚体的质量属性。
6. 刷新邻近零件的阻力遮挡。
7. 把操作加入 Undo 栈。

### 2. 删除中间零件为什么比添加更复杂？

删除一个叶子节点很简单，但删除中间节点可能使多个下游分支失去与主车的连接。系统需要把每个仍然连通的分支识别出来，并转换为独立物理实体。

流程可以概括为：

~~~text
找到待删除零件及相关连接
    ↓
断开 Joint
    ↓
递归收集仍然连通的子树
    ↓
为每个独立分支创建新的 Machine
    ↓
迁移零件与刚体归属
    ↓
原 Machine 和新 Machine 分别重算质量、质心、惯性和遮挡
~~~

删除一个零件可能产生零个、一个或多个新 Machine，不能把实现理解成“永远只掉下来一个物体”。

### 3. Command 和 Archive 分别解决什么？

| 机制 | 粒度 | 用途 |
|---|---|---|
| Command | 单次编辑操作 | 添加、删除、Undo、Redo |
| Archive | 整辆载具快照 | 驾驶/建造状态切换、存档加载、安全恢复 |

删除命令在执行前保存必要的临时 Archive，撤销时根据快照恢复结构。Command 不等于每次保存整个场景；Archive 也不替代编辑历史。

### 4. 为什么预算不能只依赖一个不断加减的计数器？

只在添加时加、删除时减，看起来很简单，但撤销、加载、销毁和结构分离都可能使计数发生漂移。因此，预算系统会从当前存活的零件图重新汇总已使用成本，并在加载 Archive 前校验：

- 零件是否都存在于目录中。
- 是否恰好有一个核心零件。
- 总成本是否不超过预算。

只有校验通过，才会清除当前载具并加载新结构。这和世界生成中的“候选成功后再提交”是同一类思路。

## 五、质量、质心和惯性张量如何动态更新？

### 1. 为什么不能只更新总质量？

质量分布不同的两辆车，即使总质量相同，运动表现也应该不同：

- 总质量影响相同外力下的线加速度。
- 质心影响重力、浮力和外力相对车体的力臂。
- 惯性张量影响绕不同方向旋转的难易程度。

如果玩家把重零件装到高处或侧面，车辆更容易产生侧翻、偏航或不同的空中姿态；只修改 `mass` 无法表现这些差异。

### 2. 合成质心怎么计算？

对第 `i` 个质量元素，质量为 `m_i`，在目标刚体局部坐标中的质心为 `r_i`：

$$
M = \sum_i m_i
$$

$$
\boxed{
c = \frac{\sum_i m_i r_i}{M}
}
$$

第一遍先求总质量和加权质心。这样第二遍计算惯性时，所有零件都能相对于最终合成质心进行平移。

### 3. 各零件的惯性如何汇总到整车？

每个零件先提供自己的局部惯性张量。将其旋转到目标刚体坐标后，再通过平行轴定理移动到整车质心：

$$
I_i^{body} = R_i I_i^{local} R_i^T
$$

$$
\boxed{
I = \sum_i \left(I_i^{body} + m_i(\|d_i\|^2E-d_i d_i^T)\right)
}
$$

其中：

- `d_i = r_i - c` 是零件质心相对整车质心的偏移。
- `E` 是三阶单位矩阵。
- 第二项是平行轴项。

### 4. 为什么还需要求主轴？

汇总得到的是一个对称的 `3×3` 惯性矩阵，可能含有非零的非对角项。Unity Rigidbody 使用三个主惯性矩和一个主轴旋转来表达惯性，因此需要对矩阵做特征分解：

$$
I = Q \Lambda Q^T
$$

- `Λ` 的三个特征值写入 `inertiaTensor`。
- `Q` 表示的主轴方向写入 `inertiaTensorRotation`。

项目使用 Jacobi 迭代对对称矩阵进行对角化，最多执行固定轮数，以便在运行时得到稳定的主惯性轴。

### 5. 单个零件的惯性从哪里来？

当前实现主要根据物理 Collider 的包围盒近似成箱体，再计算箱体惯性。它比只根据 Transform 缩放猜测更接近碰撞形状，但仍然不是任意复杂网格的精确体积分。

这是合理的游戏工程近似：玩家需要感知质量布局的差异，但项目不需要为每个复杂 Mesh 做高成本的精确体积分。

### 6. 什么时候重算？

质量属性主要在以下事件发生后更新：

- 添加或删除零件。
- 结构断裂并形成新 Machine。
- 加载或恢复载具。
- 刚体模拟状态发生变化。

静态结构不需要每帧重复计算。正常物理帧主要使用已经写入 Rigidbody 的结果。

### 7. 高频追问：为什么不能对每个零件的惯性直接求和？

因为每个零件的惯性最初是绕自己的质心、在自己的局部坐标下定义的。直接把三个数相加既忽略了方向旋转，也忽略了零件距离整车质心的平行轴贡献，结果会严重低估分散质量带来的转动惯量。

## 六、动态水面与逐零件体素浮力

### 1. 为什么选择逐零件体素浮力？

固定船体可以直接配置少量浮力点，但本项目中的载具由玩家动态拼装，形状和排水体积分布随时可能变化。逐零件采样有两个直接好处：

- 每个浮力零件独立提供排水贡献。
- 零件位置变化会自然改变合力作用位置和翻转趋势。

### 2. 体素采样点如何生成？

初始化时，系统根据 Collider 的包围盒和采样尺寸生成规则网格点，再通过 `Collider.ClosestPoint` 判断候选点是否位于碰撞体内部。保留下来的点作为体素中心。

这些采样点是运行时计算数据。编辑器中显示的小球只是调试 Gizmo，并不是手工摆放的浮力点。

### 3. 动态水面是怎样生成的？

水面不是单纯的 Shader 顶点动画。CPU 侧维护一张规则网格，多个径向正弦波源根据时间和距离对顶点高度产生偏移：

$$
h(x,z,t) = h_0 + \sum_k A_k(d_k)\sin(\omega_k t + \phi_k(d_k))
$$

这里是可控的波形叠加，不是 Navier–Stokes 流体仿真。项目没有求解压力场、流速场和真实水体相互作用。

### 4. 任意位置的水面高度如何查询？

查询点先转换到水面局部坐标，再定位到规则网格中的方格。由于实际 Mesh 由三角形组成，系统会判断查询点落在哪个三角形投影内，读取该三角形的三个实时顶点，通过平面方程反求当前位置的 `y`。

相比简单平均四个角点，这种方法能与当前渲染网格的分片平面保持一致。

### 5. 单个体素的浮力如何计算？

设计依据采用阿基米德形式：

$$
\boxed{
F_i = -\rho V_i g
}
$$

其中 `ρ` 是水体密度参数，`V_i` 是单个体素近似体积，`g` 是重力向量。对所有浸水体素累加：

$$
F = \sum_i F_i
$$

每个体素相对刚体质心还会产生力矩：

$$
\boxed{
\tau = \sum_i (p_i-c) \times F_i
}
$$

因此，同样数量的浮力点分布在车辆不同位置，会产生不同的回正或翻转效果。

### 6. 为什么力矩必须相对所属 Rigidbody 的质心计算？

一个 FixedPart 可能没有自己的 Rigidbody，而是共享整车或某个 MovablePart 的刚体。真正接受合力的是所属 Rigidbody，因此力臂也必须相对这个刚体的世界质心计算，不能使用零件 Transform 原点代替。

### 7. 当前浮力模型有哪些近似？

- 体素通过中心点判断是否浸水，当前是二值状态。
- 没有精确计算体素连续浸没比例。
- 采样越密，形状描述越细，但每个物理步成本越高。
- 水体密度和施加方式包含玩法调参，不能包装成严格 SI 单位仿真。
- 当前累计结果以物理步冲量形式施加，不应宣称是完整连续流体力学求解。

面试中主动说明这些边界，比把方案描述成“真实浮力模拟”更可信。

## 七、逐零件二次阻力、表面遮挡与批量限幅

### 1. 为什么不用 Rigidbody 自带 Drag？

整体 Drag 主要依据刚体速度产生统一阻尼，难以表达玩家改变零件方向、位置和遮挡后产生的差异。本项目希望以下结构能有不同反馈：

- 宽扁和细长零件。
- 正装和侧装零件。
- 外露和被其它零件挡住的表面。
- 靠近质心和远离质心的零件。

因此阻力由各零件产生，再按实际 Rigidbody 汇总。

### 2. 二次阻力如何表示？

先把零件位置处的世界速度转换到零件局部空间。对局部轴 `j`：

$$
\boxed{
F_j = -C_j |v_j|v_j M
}
$$

- `C_j` 是该轴的阻力系数。
- `v_j` 是局部速度分量。
- `M` 是空气或水体介质倍率。
- 负号保证阻力与运动方向相反。

实际物理步中会将其换算成冲量贡献。

### 3. 为什么使用 `GetPointVelocity`？

刚体旋转时，不同位置的瞬时速度不同：

$$
v(p) = v_{com} + \omega \times (p-c)
$$

只读取刚体线速度会漏掉角速度对偏置零件的影响。使用零件位置处的点速度后，长车体转动时两端能够产生方向和大小不同的局部阻力。

### 4. 六向表面遮挡怎么做？

每个零件维护局部 `+X/-X/+Y/-Y/+Z/-Z` 六个受阻方向。拓扑建立或变化时，沿六个局部方向做短距离射线检测：

- 如果命中同一 Machine 的其它零件，对应面标记为被遮挡。
- 被遮挡方向不再产生完整外露阻力。
- 结果缓存下来，正常 FixedUpdate 不重复发射全部射线。

这是局部近邻遮挡近似，不是计算真实迎风面积、尾流或流场。

### 5. 为什么要先汇总，再统一限幅？

同一 Rigidbody 可能收到很多零件的二次阻力。若逐项直接施加，某个物理步的总冲量可能使速度越过零点并反向，引起抖动。

系统先计算所有贡献造成的总线性冲量和总角冲量，再估算它们对该刚体速度状态的影响。如果变化过强，就给同一批贡献乘一个统一比例，使相关速度在单步内最多衰减约 80%。

统一缩放比逐零件裁剪更合理，因为它能保留：

- 各零件阻力的相对大小。
- 合力中心的位置。
- 原始力矩分布。

### 6. 水中倍率 775 是物理常数吗？

不是。它用于制造空气和水体之间明显的阻力差异，可以理解为参考介质密度数量级后得到的游戏化参数，但最终还要与车辆动力、浮力和手感一起调节。

### 7. 方案的局限是什么？

- 分轴系数不能精确表示任意形状的迎风面积。
- 六向短射线只能处理明显的局部遮挡。
- 没有尾流、涡流和零件间流体耦合。
- 二次阻力和限幅都服务于稳定与可玩性，不是 CFD。

## 八、确定性 PCG：Seed 为什么不只是一个 Random 参数？

### 1. 项目对“确定性”的定义是什么？

在相同工程版本、相同生成配置和相同逻辑下：

- 相同 Requested Seed 产生相同的候选序列。
- 如果前几个候选验证失败，会在相同次数失败。
- 最终接受的世界及其 Effective Seed 保持一致。

这不等于承诺跨算法版本、跨配置永久位级一致。工程中保留生成版本，是为了明确复现边界。

### 2. 为什么不能让所有模块共用一个全局随机序列？

假设环境模块多调用一次随机数，如果后面的资源、地标和挑战继续消费同一序列，它们的位置都会改变。这样一个局部改动会造成全世界连锁变化，难以测试和复现。

项目通过固定 Salt 从根 Seed 派生模块随机流：

~~~text
Root Seed
├─ Terrain Salt      → 地形随机流
├─ Environment Salt  → 环境随机流
├─ Salvage Salt      → 废料随机流
└─ WorldLayout Salt  → 外围布局随机流
~~~

模块内部仍应保持稳定的迭代顺序，但 Salt 能降低模块之间的随机调用耦合。

### 3. Requested Seed 和 Effective Seed 有什么区别？

- Requested Seed 是玩家或系统输入的一局根 Seed。
- Attempt 0 直接使用 Requested Seed。
- 若候选验证失败，后续尝试根据 Requested Seed 和 Attempt Index 通过固定哈希派生 Effective Seed。

因此重试不是临时换一个不可追踪的随机数，而是 Requested Seed 对应的一条固定候选序列。

### 4. 随机工具采用什么方法？

工程使用自定义的确定性伪随机工具，核心状态更新采用 `xorshift32`，并结合 Seed 混合函数和兼容版本。它的目标是轻量、可复现和便于分流，不是密码学安全。

### 5. 一句面试回答

> 我的确定性不是只保存初始 Seed，而是固定了模块 Salt、重试 Seed 派生方式和候选接受条件，所以同一版本中，失败过程和最终世界也能一起复现。

## 九、地形不是“多层噪声一叠就结束”

### 1. 基础高度如何生成？

项目使用确定性 Value Noise，并通过多个 Octave 形成 Fractal Value Noise。一般形式可以写成：

$$
H(x,z) = \frac{\sum_{k=0}^{n-1} a_k N(f_kx,f_kz)}{\sum_{k=0}^{n-1} a_k}
$$

频率逐层提高，振幅逐层衰减，最后除以总振幅，使不同层数下的输出范围更稳定。

这里是 Value Noise，不应误称为 Perlin Noise。

### 2. 为什么还要显式生成 Hill、Valley、Flat、Mound 和 Ditch？

噪声擅长提供自然连续起伏，但很难稳定保证：

- 出生点附近有足够平地。
- 世界存在可辨认的谷地或通道。
- 某些位置适合放置挑战和地标。
- 水域能够形成可玩的盆地和岸线。

因此基础噪声之上还叠加明确的语义地形特征，并经过平滑、坡度松弛、边缘塑形、水岸安全处理和总高差限制。

### 3. 为什么高度图分辨率是 `2^n + 1`？

Unity Terrain 常用该形式。以 513 为例，它包含 513 个高度采样点，对应 512×512 个地形网格单元。分析阶段不必使用完整分辨率，项目会降采样到较小网格以降低验证成本。

### 4. 水位如何决定？

水位不是简单写死的固定高度。系统会参考高度样本分布搜索候选水位，使水域覆盖接近配置目标，再检查：

- 总水域比例。
- 主水体规模。
- 水深范围。
- 边缘安全。
- 水域连通性。

随后还会塑形水下盆地，并在固定水位下重新分析。

### 5. 地形为什么必须验证？

“生成没有报错”不代表“地图能玩”。随机结果可能出现：

- 出生入口过陡。
- 平缓区域互不连通。
- 局部坑洼卡住车辆。
- 总高差或最大坡度失控。
- 水域面积和深度不符合玩法目标。

因此每个候选都要经过静态验证，只有达到阈值才会被接受。

## 十、可达性验证怎样工作？

### 1. 分析网格记录什么？

Terrain Analyzer 将地形采样到统一分析网格，并为每个格子保存或推导：

- 高度。
- 坡度。
- 是否属于可驾驶区域。
- 是否为水域。
- 水深和距岸距离。
- 局部坑洼等风险信息。

这份网格不仅服务验证，后面的环境、废料和表面生成也会继续使用。

### 2. 可达率如何计算？

系统从出生入口附近的有效格子出发，在满足坡度等通行条件的网格上执行八邻域洪泛搜索：

~~~text
找到出生入口格
    ↓
加入队列并标记已访问
    ↓
遍历八个相邻格
    ↓
只扩展满足通行条件且未访问的格子
    ↓
计算可达平缓区域 / 全部目标平缓区域
~~~

它是一种快速的静态筛选，不等价于让真实物理车辆完整驾驶地图。

### 3. “85% 可达”意味着所有奖励都能被基础车拿到吗？

不意味着。全局可达验证保证主要可驾驶区域具有足够连通性；Capability 类型资源本来就可以位于水面、悬崖或特殊结构上，要求玩家改车后获取。

### 4. 为什么不直接用 AI 车跑图？

真实车辆回放更贴近最终体验，但对每个候选完整执行物理驾驶成本很高，也会引入控制器能力这一额外变量。网格验证适合作为运行时第一层筛选；自动驾驶回放更适合离线回归测试。

## 十一、共享地形语义与内容生成

### 1. 这里的“语义”是什么？

不是自然语言标签，而是程序能够直接查询的空间含义，例如：

- 当前格子的高度和坡度。
- 水深、岸距和所属水体。
- 地表类型。
- 是否有环境障碍占位。
- 是否靠近出生点、地标或外围模块。
- 是否属于已验证的可达区域。

### 2. 为什么不能直接在随机坐标生成树木和奖励？

只随机坐标容易产生数量正确但体验错误的结果：

- 树木堵住出生区。
- 奖励落在过陡位置。
- 资源被岩石或其它对象覆盖。
- 需要改车才能获取的奖励却出现在起点旁边。

共享语义能让不同内容模块对同一位置得出一致判断。

### 3. 环境和废料的生成顺序为什么重要？

环境对象先根据地表权重和配置生成，并把树木、岩石等碰撞障碍写入占位网格。随后废料生成器读取最终占位状态，从仍然有效的位置中选择候选，避免奖励被障碍覆盖。

如果环境放置后导致出生区可达率下降，系统会按确定性优先级移除部分可移除障碍，重建占位并重新洪泛，直到满足阈值或确认失败。

### 4. 废料为什么分成 Basic、Skill 和 Capability？

| 类型 | 位置倾向 | 玩法目的 |
|---|---|---|
| Basic | 开阔、低风险、容易到达 | 保证玩家能获得基础改造资源 |
| Skill | 坡地、较难驾驶区域 | 考验操作和路线选择 |
| Capability | 水面、悬崖、岩石等特殊位置 | 要求玩家先获得或搭建对应能力 |

具体语义还包括 `OpenLand`、`Slope`、`WaterHover`、`CliffTop`、`RockTop` 和 `RockPocket` 等候选类型。

### 5. 目标数量等于最终一定生成数量吗？

不一定。配置中的总数和分类比例是目标值。生成器会记录 Target Count 和 Actual Count，但若合格候选不足，实际放置数可能低于目标。因此不能把“目标 12–16 个”说成“每局严格保证 12–16 个”。

## 十二、外围挑战布局为什么需要回溯？

### 1. 外围模块解决什么问题？

纯高度场适合表达坡地和水域，但不容易产生明确的人工结构与立体挑战。外围模块用于放置出生区、撤离区和不同类型的挑战，让世界边缘出现更可辨认的玩法目标。

### 2. 布局有哪些约束？

候选模块需要同时满足：

- 位于允许的边缘或网格位置。
- 旋转和朝向正确。
- 不与已放置模块发生空间冲突。
- 与角落和关键区域保留安全距离。
- 满足各类挑战的最低覆盖要求。

### 3. 为什么贪心放置不够？

如果每一步只选择当前看起来最合适的位置，前面的选择可能占据后续稀缺空间，导致最后一个必选挑战无处可放。回溯会在后续失败时撤销前面的某个选择，尝试下一个确定性候选。

伪流程：

~~~text
Place(typeIndex):
    if 所有必需类型均已放置:
        return success

    for candidate in 当前类型的确定性候选序列:
        if candidate 与已放置模块兼容:
            放入 candidate
            if Place(typeIndex + 1):
                return success
            撤销 candidate

    return failure
~~~

### 4. 如何保持回溯过程确定性？

候选集合、排序、随机打散方式和冲突判断都来自固定 Seed 和规则。相同输入下，搜索顺序和最终接受布局一致。

## 十三、候选世界与事务式提交

### 1. 为什么不能一边生成一边直接替换当前场景？

若生成到一半失败，场景可能留下：

- 新旧 Terrain 混合。
- 已生成的环境对象和缺失的奖励。
- 已切换的数据引用与未完成的 GameObject。
- 下次重试难以清理的残留状态。

因此，生成数据成功和构建场景成功被视为两个阶段。

### 2. 提交流程是什么？

~~~text
在内存中生成并验证全部规划数据
    ↓
创建未激活的 PendingTerrainRoot
    ↓
在 Pending Root 下构建 Terrain、水体、环境、资源和外围模块
    ├─ 任一阶段失败：销毁 Pending Root，保留当前有效世界
    └─ 全部成功：关闭旧 Root
                    ↓
                 更新 Current 数据引用
                    ↓
                 激活 Pending Root
                    ↓
                 将其提升为 GeneratedTerrainRoot
                    ↓
                 销毁旧 Root
~~~

这是一种类似事务的工程实现：候选状态只有完整成功后才成为当前状态。

### 3. “失败后保留旧世界”有没有前提？

有。如果此前已经存在有效世界，失败候选不会替换它；如果这是首次生成，场景本来没有旧世界，则结果只是生成失败。准确说法是“失败不会污染当前有效状态”，不是“永远存在备用世界”。

### 4. 重试范围需要怎样准确描述？

最多若干次确定性重试主要发生在地形、水域和世界主布局候选阶段。主候选通过后才继续规划表面、环境、地标和废料；不能把所有后处理阶段的任意失败都描述成自动进入下一次完整 Attempt。

## 十四、怎样形成完整玩法闭环？

### 1. 废料、预算和改车怎样连接？

玩家拾取 Salvage 后增加建造预算。进入建造状态时，可以在预算范围内添加零件；删除、撤销、加载和结构分离后，系统会重新汇总当前零件成本，避免预算漂移。

预算不是单纯的货币 UI，而是把探索结果转化为载具能力的中间层。

### 2. 能源核心为什么只允许主载具收集？

结构拆分后，场景中可能同时存在主车和多个断裂 Machine。如果任意掉落零件都能触发收集，会产生远程误拾取或利用断裂物绕过玩法的问题。因此，核心拾取会检查碰撞零件是否属于包含 CorePart 的主 Machine。

### 3. 撤离结算如何触发？

默认需要三枚能源核心。玩家进入撤离平台后，系统先检查是否满足撤离条件；满足后停止载具、暂停交互、播放提示或效果，并记录本局完成快照，进入结算界面。

### 4. 还有哪些支撑完整体验的系统？

除了简历中最突出的技术点，工程还包含：

- 雷达和指南针。
- 教学与分阶段提示。
- Checkpoint 和进度管理。
- 结算记录。
- 建造预算与载具合法性校验。
- 编辑器配置和调试工具。

这些系统单独看并不复杂，但它们决定项目是否只是技术 Demo，还是一款能够完整游玩的游戏。

## 十五、自动化测试覆盖了什么？

### 1. 为什么这个项目尤其需要确定性测试？

PCG 的输入空间很大，仅靠手工打开几个 Seed 很难发现边界问题。确定性使测试能够保存失败 Seed，并在修改后重复生成同一候选。

### 2. 当前测试资产主要覆盖哪些方向？

| 方向 | 关注点 |
|---|---|
| PCG | Seed 确定性、地形范围、坡度、可达性、水域、语义内容、外围布局 |
| 载具 | 零件连接、拆分、质量属性、预算和 Archive 合法性 |
| 物理 | 浮力、阻力、遮挡和限幅 |
| 游戏流程 | 废料、能源核心、撤离、Checkpoint、教学和结算 |
| UI/导航 | 雷达、指南针和相关数据更新 |

### 3. 测试应该如何分层？

- **EditMode：** 适合纯数据、算法、确定性和数学计算，例如 Seed、布局、质量属性。
- **PlayMode：** 适合依赖场景生命周期、物理步、Trigger 和完整流程的行为。
- **人工游玩：** 用于判断手感、节奏和视觉可读性，不能被单元测试完全替代。

### 4. 面试时怎样描述测试最准确？

> 工程里有 42 个测试文件和 300 多个测试声明，覆盖 PCG、模块布局、质量属性、阻力、浮力和通关流程。当前我能确认的是测试资产规模；如果没有在提交前重新跑全量 Test Runner，就不会说它们此刻全部通过。

## 十六、项目中的关键取舍与不足

### 1. 零件拓扑为什么选树而不是一般图？

**收益：** 父子关系唯一，递归增删、拆分、序列化和恢复简单。<br>
**代价：** 不能直接表达多父节点、环和闭环机械结构。<br>
**适用原因：** 当前玩法不依赖复杂闭环机构，一个月项目更需要稳定交付。

### 2. 浮力为什么选体素近似？

**收益：** 能适配动态拼装和不规则分布，安装位置自然影响力矩。<br>
**代价：** 采样成本随点数增长，水线附近存在离散跳变。<br>
**改进：** 使用部分浸没比例、分层采样或按形状自适应采样。

### 3. 阻力为什么选六向遮挡？

**收益：** 实现和调试成本可控，能让零件朝向与局部遮挡影响运动。<br>
**代价：** 不能表达连续迎风面积、尾流和真实流体耦合。<br>
**改进：** 使用投影面积、方向采样或离线拟合的阻力模型。

### 4. 可达性为什么选网格洪泛？

**收益：** 运行快、结果稳定、适合多次候选筛选。<br>
**代价：** 不能完全代表真实车辆在物理环境中的可通过性。<br>
**改进：** 把网格验证作为第一层，再增加离线车辆回放和失败 Seed 回归集。

### 5. PCG 还可以怎样加强？

- 为每个生成版本保存一批基准 Seed。
- 统计大量 Seed 的失败类型和指标分布。
- 将 Surface、Environment 和 Salvage 的硬约束与软评分分开。
- 对运行时生成做分帧或异步构建，减少卡顿。
- 记录生成 Trace，让失败候选更容易复盘。

### 6. 物理系统还可以怎样加强？

- 对浮力体素计算连续浸没比例。
- 对高速运动使用更稳定的阻力积分方式。
- 缓存和局部更新遮挡，而不是拓扑变化后全量刷新。
- 对复杂 Collider 使用更合理的体积和惯性近似。
- 增加不同固定时间步下的稳定性回归。

## 十七、面试时怎样介绍这个项目？

### 1. 30 秒版本

> 《废械星途》是我在腾讯超新星计划中参加一个月限时比赛完成的模块化载具探索游戏，主题是 PCG 加物理。我主要负责核心客户端代码：一部分是运行时载具拼装，把零件连接树和 Rigidbody 层级分开，并在增删零件后更新质量、质心和惯性；另一部分是体素浮力、逐零件阻力以及 Seed 驱动的确定性世界生成。最终做出了从回收废料、改车、收集能源核心到撤离结算的完整流程。

### 2. 90 秒版本

> 这个项目叫《废械星途》，是一个月限时完成的模块化造车探索游戏。玩家进入程序化生成的星球，回收废料来增加建造预算，运行时改造车辆，跨越陆地和水域，收集三枚能源核心后撤离。
>
> 我主要做了三块。第一块是模块化载具。我没有让每个零件都挂独立刚体，而是用有根零件树管理连接关系，根据 FixedPart 和 MovablePart 自动映射到不同 Rigidbody；删除中间零件时，断开的子树会变成独立 Machine。结构变化后还会重新计算质量、质心和完整惯性张量。
>
> 第二块是多介质物理。水面在 CPU 网格上动态更新，浮力零件通过 Collider 体素采样计算合力和力矩；阻力按零件局部速度、安装方向、六面遮挡和空气/水体介质计算，再按 Rigidbody 汇总限幅。
>
> 第三块是 PCG。世界由 Seed 驱动，先生成地形、水域和外围布局，再用坡度、可达率、坑洼等指标验证并确定性重试。完整世界先构建在未激活的 Pending Root 下，成功后才替换当前世界。这个项目让我比较系统地做了一次从底层机制到完整玩法闭环的落地。

### 3. 三分钟版本的讲述顺序

1. 用一句话说明游戏目标和开发限制。
2. 说明为什么“运行时改车”要求拓扑与刚体解耦。
3. 选择质量属性、浮力或阻力中的一个深入讲算法。
4. 说明 PCG 不只是随机生成，而是生成、验证、重试和提交。
5. 用完整游戏循环收尾，并主动说一个不足和改进方向。

不要在开头罗列 175 个脚本、42 个测试文件等数字。先让面试官理解游戏和问题，数字只在对方追问规模或工程化时使用。

## 十八、高频面试问题与回答提纲

### 1. 你在项目中的个人贡献是什么？

**回答重点：**

- 主导核心客户端代码，而不是声称独立完成所有美术、策划和展示内容。
- 具体点出模块化载具、多介质物理、PCG 和玩法闭环。
- 选择一两个最熟悉的模块深入，不要平均罗列所有功能。

**参考回答：**

> 我主要负责核心玩法和底层系统代码，包括模块化载具连接与拆分、动态质量属性、浮力与阻力，以及确定性 PCG 的生成、验证和运行时提交。同时把废料预算、能源核心和撤离结算串成完整流程。美术和其它协作内容我会按实际分工说明，不会都算成个人完成。

### 2. 这个项目最难的问题是什么？

可以从两个角度回答：

- **载具角度：** 同一棵零件树中多个零件可能共享刚体，结构还会在运行时变化，因此连接拓扑、刚体归属和质量属性必须同步更新。
- **PCG 角度：** 随机生成不难，难的是让结果可复现、可验证，并且失败时不污染当前场景。

### 3. 为什么不直接使用现成车辆或浮力插件？

> 固定车辆插件通常假设车体和轮组结构预先确定，而这里的核心玩法是玩家运行时改变结构。现成浮力方案也不一定能表达多个零件共享刚体、每个零件独立贡献排水体积的情况。项目并不是排斥插件，而是核心数据模型需要围绕动态拼装设计。

### 4. 如何证明 PCG 是确定性的？

回答应包含四层：

1. 自定义确定性随机工具。
2. 固定 Salt 拆分模块随机流。
3. Requested Seed 与 Attempt Index 确定性派生 Effective Seed。
4. 测试中比较相同输入的高度、布局、数量和关键指标。

### 5. PCG 验证能保证地图一定通关吗？

> 不能把静态验证说成绝对通关证明。它能排除明显失控的候选，例如出生口过陡、主要平缓区域断开、水域或坑洼不合理；但真实可通过性还会受到载具结构和玩家操作影响。更完整的方案是增加车辆回放和大量 Seed 回归。

### 6. 为什么惯性张量要做特征分解？

> 各零件经过旋转和平行轴变换后，合成惯性是一个一般的对称矩阵。Unity 需要主惯性矩和主轴旋转，因此要把矩阵对角化。特征值是主惯性矩，特征向量组成主轴方向。

### 7. 为什么阻力要统一缩放，不能逐零件 Clamp？

> 逐零件裁剪会改变贡献比例，进而改变合力中心和力矩。统一缩放整批冲量，既能防止单步过度减速，又尽量保留原来的空间分布。

### 8. 浮力系统真实吗？

> 它基于阿基米德原理和力矩累加，但实现上是面向玩法的体素近似。当前使用体素中心的二值浸水判断，水面也是正弦波网格，不是完整流体仿真。我更关注动态拼装后排水分布和姿态反馈是否稳定、可读。

### 9. 如果再给两周，你会先改什么？

优先选择能够形成闭环的改进，而不是随便加功能：

> 我会先建立一批固定 Seed 和固定载具的自动回归集，统计生成失败类型、可达率和不同固定时间步下的物理稳定性。之后再优化浮力的部分浸没比例和生成分帧。这样能先建立可衡量的质量基线，再继续提高表现。

### 10. 一个月比赛中最大的收获是什么？

> 最大收获不是某个 API，而是学会在时间受限时重新定义技术目标。早期完整多体车辆方案成本过高，我保留了结构影响物理的核心反馈，把范围收缩到可稳定交付的模块化载具、浮力、阻力和 PCG，并最终完成整个游戏循环。

## 十九、容易说错的口径

| 不建议这样说 | 更准确的说法 |
|---|---|
| 使用 Perlin Noise 生成地形 | 使用多层确定性 Value Noise，并叠加显式地形特征 |
| 实现了真实流体仿真 | 实现了动态水面查询和面向玩法的体素浮力近似 |
| 每个零件都是独立刚体 | FixedPart 共享父刚体，MovablePart 才拥有独立 Rigidbody |
| 删除零件后只生成一个新物体 | 每个断开的连通分支都可能成为独立 Machine |
| 相同 Seed 在任何版本都完全一样 | 在相同工程版本、Profile 和生成逻辑下可复现 |
| 生成失败后一定恢复旧地图 | 若已有有效世界则保留；首次生成时可能没有旧世界 |
| 每局严格生成目标数量的奖励 | 配置是目标数量，候选不足时 Actual Count 可能更少 |
| 可达率通过就保证任何车辆都能通关 | 它是静态网格筛选，不是完整物理通关证明 |
| 42 个测试文件全部通过 | 当前能确认测试资产规模，是否全通过需以实际 Test Runner 为准 |
| 水中倍率 775 是精确物理常数 | 它是参考介质差异后用于玩法调节的倍率 |
