# C++ 秋招八股复习文档（三）：资源管理与异常处理

**复习范围：** 动态内存、new/delete、placement new、RAII、资源所有权、智能指针、异常处理、异常安全保证、noexcept、资源管理类的拷贝与移动、Rule of Three/Five/Zero。

**标准版本：** 以 C++11/14 为主，并单独标注 C++17 等版本的相关特性。

## 一、C++ 资源管理的基本思想

### 1. 什么是资源？

资源不只指动态分配的内存。程序需要获取、使用并最终释放或归还的外部或系统实体，都可以视为资源，例如：

- 动态内存。
- 文件句柄、文件描述符。
- 网络连接与 socket。
- 互斥锁的锁定状态。
- 操作系统句柄、图形 API 资源。
- 临时注册、回调、事务或其他需要成对清理的状态。

资源管理的关键不是“调用了某个释放函数”，而是要明确：

1. 谁负责释放资源？
2. 资源在哪些路径上释放？
3. 异常或提前 return 时能否正确释放？
4. 资源能否复制或共享？如果能，所有权语义是什么？
5. 资源转移后，原对象还处于什么状态？

### 2. 什么是资源泄漏？

获取了资源，但在应该释放时没有释放，就可能产生资源泄漏。

~~~cpp
void Foo()
{
    int* p = new int(10);
    // 中途 return、抛异常或其他控制流离开函数
    // 若没有 delete p，资源就泄漏了
}
~~~

资源泄漏不仅会由忘记调用 `delete` 导致，也可能发生在文件句柄、锁、GPU 资源等其他资源上。

### 3. 什么是 RAII？

RAII 是 Resource Acquisition Is Initialization（资源获取即初始化）的缩写。它的核心思想是：**让资源的生命周期与一个对象的生命周期绑定，由对象的析构过程负责释放资源。**

~~~cpp
#include <memory>

void Foo()
{
    auto p = std::make_unique<int>(10);
    // 函数正常返回或抛出异常时，p 都会析构并释放资源
}
~~~

RAII 的优势：

- 正常执行、提前 return 和异常展开时，都可以自动清理资源。
- 资源获取与释放逻辑集中在一个类型中。
- 减少遗漏释放、重复释放和异常路径清理不完整的问题。
- 可以让复杂资源管理逻辑通过组合现成的 RAII 类型来实现。

常见 RAII 类型包括 `std::string`、标准容器、智能指针、锁管理器（如 `std::lock_guard`）和自定义资源包装类。

### 4. 为什么 RAII 是现代 C++ 的核心习惯？

对比裸资源管理：

~~~cpp
void Process()
{
    FileHandle* file = OpenFile();
    DoWork(file);
    CloseFile(file);
}
~~~

如果 `DoWork` 抛出异常，`CloseFile` 可能不会执行。

使用 RAII 包装后：

~~~cpp
void Process()
{
    File file = OpenFileRAII();
    DoWork(file);
} // file 的析构函数负责关闭文件
~~~

即使 `DoWork` 抛出异常，局部对象也会在栈展开过程中析构（前提是异常能够正常传播，而不是直接终止程序）。

## 二、new、delete 与动态内存

### 1. new 表达式做了什么？

~~~cpp
int* p = new int(42);
~~~

这里的 `new` 是 new-expression（new 表达式）。概念上它包含两个主要步骤：

1. 获取适合存放对象的存储空间，通常会调用相应的分配函数，例如全局或类专属的 `operator new`。
2. 在该存储空间中初始化对象，开始对象生命周期。

因此，new 表达式不等于单纯的 `malloc`。对于类类型，new 表达式还会调用构造函数。

### 2. delete 表达式做了什么？

~~~cpp
int* p = new int(42);
delete p;
~~~

对于有效的、与之匹配的非数组 new-expression 所创建的对象，delete 表达式会先执行对象析构（如果需要），然后调用相应的释放函数归还存储空间。

对内置类型的 `int`，析构步骤没有可观察的工作；对类对象，析构函数负责执行清理逻辑。

### 3. new 与 malloc 有什么区别？

| 对比项 | new 表达式 | malloc |
|---|---|---|
| 所属体系 | C++ 语言表达式 | C 标准库函数 |
| 返回值 | 返回目标类型指针 | 返回 `void*` |
| 类型大小 | 根据类型自动计算 | 需要手动提供字节数 |
| 构造函数 | 对类类型执行初始化 | 不调用构造函数 |
| 失败处理 | 默认分配失败时抛出 `std::bad_alloc`（除非使用不抛异常形式等） | 返回空指针 |
| 释放方式 | 使用匹配的 delete 表达式 | 使用 `free` |

不能混用分配和释放方式：

~~~cpp
int* p = new int(5);
delete p; // 正确匹配

int* q = static_cast<int*>(std::malloc(sizeof(int)));
std::free(q); // 与 malloc 匹配
~~~

以下都是错误搭配，会导致未定义行为：

~~~cpp
int* p = new int(5);
std::free(p); // 错误

int* q = static_cast<int*>(std::malloc(sizeof(int)));
delete q; // 错误
~~~

此外，`malloc` 只分配原始存储，不会自动执行一般类类型的构造函数；`free` 也不会调用 C++ 对象的析构函数。

### 4. new 失败时会怎样？

普通 new-expression 在分配失败时，默认会抛出 `std::bad_alloc`。

~~~cpp
try {
    int* p = new int[large_size];
    delete[] p;
} catch (const std::bad_alloc& e) {
    // 处理分配失败
}
~~~

实际项目中通常不应该通过无限制地申请超大内存来测试异常；这里仅展示默认失败行为。

还可以使用不抛异常形式：

~~~cpp
int* p = new (std::nothrow) int(42);
if (p == nullptr) {
    // 分配失败
}
delete p;
~~~

使用 `std::nothrow` 形式时，分配失败会返回空指针。不过，若类类型构造函数本身抛出异常，构造异常仍然可能传播；不抛异常分配形式不等于整个对象初始化过程绝对不抛异常。

### 5. new 和 delete 必须匹配吗？

必须使用符合规则的释放方式：

~~~cpp
int* p = new int(1);
delete p;

int* arr = new int[10];
delete[] arr;
~~~

数组形式的 new-expression 通常需要用 `delete[]` 释放，非数组形式则用 `delete`。错误匹配会导致未定义行为。

不要写成：

~~~cpp
int* arr = new int[10];
delete arr; // 错误：与数组 new 不匹配
~~~

即使某些简单类型或某些编译环境下看起来“运行正常”，也不代表行为合法。

### 6. 为什么 new[] 和 delete[] 是一对？

数组 new-expression 需要为数组元素执行初始化；数组 delete-expression 则需要按规定销毁相应元素，再释放存储空间。具体分配布局、是否存在数组 cookie 以及 cookie 的实现方式，都由实现决定。

不要依赖“数组前面一定保存一个元素个数”的说法作为语言标准保证。

### 7. new/delete 与 operator new/operator delete 有什么区别？

- `new T(args)` 是 new-expression，负责分配存储并初始化对象。
- `delete p` 是 delete-expression，负责销毁对象并释放存储。
- `operator new` 是分配函数，负责提供原始存储。
- `operator delete` 是释放函数，负责归还相应存储。

~~~cpp
void* memory = ::operator new(sizeof(int)); // 只获取原始存储
int* p = ::new (memory) int(42);            // placement new，在该存储中构造对象

p->~int(); // 注意：不能这样显式调用 int 的析构函数；内置类型不需要此步骤
::operator delete(memory);
~~~

上面的最后一段不要照抄成通用模式：内置类型没有可显式调用的析构函数。更通用的 placement new 用法会在下一节说明。

### 8. 什么是 placement new？

Placement new 是一种在调用者提供的存储空间中构造对象的 new-expression 形式。

~~~cpp
#include <new>

alignas(int) unsigned char buffer[sizeof(int)];

int* p = new (buffer) int(42);
// p 指向 buffer 中构造的 int 对象
~~~

placement new 通常不负责分配新的存储空间；它在提供的地址上构造对象。

需要注意：

- 提供的存储空间必须足够大且满足目标类型的对齐要求。
- 存储空间必须仍然有效。
- 若构造的是需要析构的类对象，应在适当时机显式调用析构函数。
- 对象析构与存储释放是不同的动作；不能对 placement new 构造出的对象随意使用普通 delete。
- placement new 是低层次工具，现代 C++ 日常代码通常优先使用 RAII 类型和标准容器。

### 9. placement new 的对象怎样析构？

~~~cpp
#include <new>

struct Widget {
    Widget() {}
    ~Widget() {}
};

alignas(Widget) unsigned char buffer[sizeof(Widget)];

Widget* p = new (buffer) Widget();
// 使用 p
p->~Widget(); // 显式调用析构函数，不释放 buffer 本身
~~~

这里的 `buffer` 是自动存储期的原始字节数组，不需要也不能通过 `delete p` 释放。显式析构对象后，原始存储仍然存在，直到其自身生命周期结束。

### 10. 什么是内存泄漏、悬空指针和重复释放？

- **内存泄漏：** 资源不再被需要，却没有被正确释放或归还。
- **悬空指针：** 指针仍保存某个地址，但所指对象的生命周期已经结束或存储已失效。
- **重复释放：** 对同一资源重复执行释放操作。
- **野指针：** 未被正确初始化或已经失效、却仍被当作有效指针使用的指针。

~~~cpp
int* p = new int(10);
delete p;
p = nullptr; // 可以避免之后通过这个变量再次误用旧地址

delete p; // delete nullptr 是安全的
~~~

将单个指针置空不能修复所有别名：如果另一个指针也指向原资源，它仍可能变成悬空指针。更好的方式是让资源所有权清晰，并优先使用智能指针或值语义类型。

## 三、资源所有权与智能指针

### 1. 什么是资源所有权？

所有权回答的是：**哪个对象或组件负责确保资源最终被释放？**

常见所有权模型：

- 独占所有权：同一时刻只有一个所有者负责释放资源。
- 共享所有权：多个所有者共同维持资源存活，通常在最后一个所有者释放后销毁资源。
- 非拥有访问：只借用资源，不负责释放它。

裸指针本身不表达完整的所有权语义。它可能是拥有指针，也可能只是观察指针；需要结合接口约定和类型设计理解。

### 2. 智能指针是什么？

智能指针是封装资源管理策略的类类型，通常通过 RAII 自动释放其管理的资源。

标准库主要智能指针包括：

| 类型 | 所有权语义 | 典型用途 |
|---|---|---|
| `std::unique_ptr` | 独占所有权 | 单一组件负责管理对象 |
| `std::shared_ptr` | 共享所有权 | 多个对象共同拥有资源生命周期 |
| `std::weak_ptr` | 弱引用，不延长对象生命周期 | 观察 shared_ptr 管理的对象，打破循环引用 |

智能指针不能自动解决所有设计问题。尤其需要谨慎设计共享所有权，避免无意中让对象存活过久。

### 3. unique_ptr 的基本用法

~~~cpp
#include <memory>

auto p = std::make_unique<int>(42);
std::cout << *p;
~~~

`std::unique_ptr` 表达独占所有权：

- 离开作用域时，自动释放所管理的对象。
- 不可复制。
- 可以移动，移动后所有权转移。
- 默认删除器会对相应对象使用匹配的删除操作。
- 可以管理数组形式的资源，例如 `std::unique_ptr<int[]>`。

~~~cpp
auto p1 = std::make_unique<int>(10);
// auto p2 = p1; // 错误：unique_ptr 不可复制
auto p2 = std::move(p1); // 所有权转移
~~~

### 4. make_unique 是什么？哪个版本引入？

`std::make_unique` 从 C++14 起提供。

~~~cpp
auto p = std::make_unique<Widget>(arg1, arg2);
~~~

它可以直接创建对象并返回管理该对象的 `unique_ptr`，代码简洁，也能避免手写裸指针管理。

在 C++11 中，标准库没有提供 `std::make_unique`；可以直接构造 `std::unique_ptr<T>(new T(...))`，或在项目中使用经过验证的兼容实现。

### 5. unique_ptr 的 get、release、reset 有什么区别？

| 操作 | 含义 | 是否转移或释放所有权 |
|---|---|---|
| `get()` | 获取原始指针用于观察或调用 | 不转移所有权 |
| `release()` | 返回原始指针并放弃管理 | 转移管理责任，但不会释放对象 |
| `reset(ptr)` | 释放当前管理对象（如适用），改为管理新指针 | 会更新所有权 |

~~~cpp
auto p = std::make_unique<int>(10);
int* raw = p.get(); // 只是观察，不能自行 delete raw
~~~

~~~cpp
int* raw = p.release(); // p 不再负责释放对象
delete raw;             // 调用者现在负责释放
~~~

如果调用 `release()` 后忘记接管返回的指针，就会泄漏资源。除非接口确实要求转移给裸指针接收方，否则应避免轻率使用它。

### 6. 如何把 unique_ptr 传给函数？

不同参数形式表达不同语义：

~~~cpp
void Observe(const Widget& widget);               // 借用对象
void ObservePtr(const Widget* widget);            // 借用指针，允许为空的语义可由接口约定
void TakeOwnership(std::unique_ptr<Widget> ptr);  // 接收独占所有权
void ModifyOwner(std::unique_ptr<Widget>& ptr);   // 修改调用者的 unique_ptr
~~~

转移所有权时通常显式使用：

~~~cpp
auto p = std::make_unique<Widget>();
TakeOwnership(std::move(p)); // p 被移动，通常变为空
~~~

如果函数只是暂时访问对象，不需要转移所有权，则一般不应该要求调用者移动一个 `unique_ptr`。

### 7. shared_ptr 的基本用法

~~~cpp
auto p1 = std::make_shared<int>(42);
auto p2 = p1;

std::cout << p1.use_count();
~~~

多个 `shared_ptr` 可以共享同一对象的所有权。通常当最后一个共享所有者销毁或放弃所有权时，对象才会被销毁。

注意：

- `use_count()` 主要用于观察，不应轻易用它作为并发同步或业务正确性的依据。
- 共享所有权会增加控制块和引用计数管理的成本。
- 对象具体何时销毁，取决于最后一个强所有者何时释放所有权。
- 不要因为“共享更方便”就默认所有对象都使用 `shared_ptr`。

### 8. make_shared 有什么优势？

~~~cpp
auto p = std::make_shared<Widget>(arg1, arg2);
~~~

`std::make_shared` 通常可以在一次分配中同时存放对象和共享控制块，减少分配次数，并且表达更简洁。

但这属于常见实现策略；标准主要规定可观察的语义，而不是强制特定内存布局。

另外，若存在指向对象内部的长期弱引用，使用 `make_shared` 时对象析构后，控制块所在的合并分配可能要等弱引用也消失后才能整体释放。对极大对象或特殊内存约束场景，需要理解实际实现和生命周期需求。

### 9. shared_ptr 的引用计数是什么？

通常可以从概念上区分：

- 强引用计数：有多少共享所有者维持对象存活。
- 弱引用计数：有多少弱引用关联控制块；具体内部计数策略属于实现细节。

当强引用计数归零时，所管理对象被销毁；控制块则在相关弱引用也不再需要它时释放。

不要把“引用计数为 1”当作任意并发环境下都能安全修改对象的证明。引用计数管理与对象本身的数据同步是两个不同的问题。

### 10. weak_ptr 为什么存在？

`std::weak_ptr` 是对 `shared_ptr` 所管理对象的弱引用，不会增加对象的强引用计数。

它通常用于：

- 打破 shared_ptr 的循环引用。
- 缓存或观察某个对象，但不希望延长其生命周期。
- 在尝试访问对象时，先检查对象是否仍然存在。

~~~cpp
std::weak_ptr<Widget> weak = shared;
if (auto strong = weak.lock()) {
    strong->DoWork(); // lock 成功时，strong 临时持有共享所有权
} else {
    // 对象已经不存在
}
~~~

相比先检查 `expired()` 再访问，直接使用 `lock()` 获取一个局部 `shared_ptr` 通常更可靠，因为它会原子地尝试获取共享所有权。

### 11. 什么是 shared_ptr 循环引用？

~~~cpp
struct Node {
    std::shared_ptr<Node> next;
    ~Node() { std::cout << "destroyed"; }
};

auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->next = b;
b->next = a;
~~~

这里两个节点通过强引用彼此拥有。即使外部变量 `a` 和 `b` 离开作用域，每个节点仍被对方持有，强引用计数无法归零，导致对象无法自动销毁。

如果其中一条只是观察关系，可以使用 `std::weak_ptr` 表达：

~~~cpp
struct Node {
    std::shared_ptr<Node> next;
    std::weak_ptr<Node> previous;
};
~~~

实际关系要根据对象图的所有权语义设计，不能机械地把任意一条 shared_ptr 改成 weak_ptr。

### 12. shared_ptr 线程安全的边界是什么？

不同的 `shared_ptr` 实例若共享同一控制块，标准库会提供引用计数所需的线程安全保证。但这不等于：

- 同一个 `shared_ptr` 变量可以被多个线程无同步地同时读写。
- `shared_ptr` 所指向的对象自动线程安全。
- 多个线程修改对象成员不需要互斥或原子操作。

要区分控制块的引用计数安全、智能指针变量本身的并发访问安全，以及被管理对象的数据同步。

### 13. 自定义删除器是什么？

有时资源不能用普通 `delete` 释放，例如 C 库返回的资源需要调用专属释放函数。

~~~cpp
#include <memory>
#include <cstdio>

using FilePtr = std::unique_ptr<std::FILE, decltype(&std::fclose)>;

FilePtr file(std::fopen("data.txt", "r"), &std::fclose);
~~~

当 `file` 析构时，自定义删除器会调用 `std::fclose`。

自定义删除器可以是函数指针、函数对象或 lambda 等可调用对象。对 `unique_ptr` 来说，删除器类型通常是其类型的一部分；对 `shared_ptr` 来说，删除器通常存放在控制块中，具体布局由实现决定。

### 14. 智能指针的常见误区

- 不要对 `unique_ptr.get()` 返回的指针随意 `delete`。
- 不要对同一个裸指针分别构造两个独立的 `shared_ptr`；这会导致重复管理同一资源并可能重复释放。
- 不要用 `shared_ptr` 代替所有权设计。
- 不要认为 `weak_ptr` 能直接像 `shared_ptr` 一样解引用；需要先通过 `lock()` 尝试获取强引用。
- 不要假设智能指针能让被管理对象的成员访问自动线程安全。
- 不要把智能指针的原始指针接口误当成所有权转移接口。

## 四、异常处理基础

### 1. C++ 的异常处理机制是什么？

C++ 使用 `try`、`throw`、`catch` 表达异常处理流程。

~~~cpp
try {
    DoWork();
} catch (const std::exception& e) {
    std::cerr << e.what();
}
~~~

- `throw` 抛出异常对象。
- `try` 包围可能抛出异常的代码。
- `catch` 根据异常类型匹配并处理异常。
- 若当前函数没有匹配的处理器，异常会继续向调用栈上传播，直到找到匹配处理器；如果没有处理器，程序会调用 `std::terminate`。

### 2. 如何抛出异常？

~~~cpp
void SetHealth(int health)
{
    if (health < 0) {
        throw std::invalid_argument("health must not be negative");
    }
}
~~~

可以抛出不同类型的异常对象。标准库异常通常派生自 `std::exception`，很多标准异常都提供 `what()`。

建议：

- 选择能表达错误含义的异常类型。
- 不要使用难以理解的裸整数或字符串来代替所有异常分类。
- 只在适当的层次捕获并处理异常，避免无意义地捕获后静默忽略。

### 3. 为什么 catch 通常使用 const 引用？

~~~cpp
try {
    DoWork();
} catch (const std::exception& e) {
    Log(e.what());
}
~~~

使用 `const std::exception&` 可以：

- 避免为了捕获而复制异常对象。
- 保留通过基类引用访问派生异常对象的多态行为。
- 避免意外修改异常对象。

如果按值捕获基类类型，可能发生对象切片；如果确实需要复制或转换异常对象，则应明确这样做的目的。

### 4. catch 的匹配顺序是什么？

多个 catch 子句按书写顺序进行匹配，应该把更具体的派生异常放在更通用的基类异常之前。

~~~cpp
try {
    DoWork();
} catch (const std::invalid_argument& e) {
    // 更具体的错误
} catch (const std::exception& e) {
    // 其他标准异常
}
~~~

如果先捕获 `std::exception`，再捕获它的派生类型，后面的派生类型处理器可能永远匹配不到。

### 5. 什么是栈展开（stack unwinding）？

当异常离开某个作用域并向外传播时，语言会按规则销毁已经构造完成、需要离开作用域的自动存储期对象，这个过程称为栈展开。

~~~cpp
struct Guard {
    ~Guard() { std::cout << "cleanup"; }
};

void Work()
{
    Guard guard;
    throw std::runtime_error("error");
}
~~~

异常从 `Work` 向外传播时，`guard` 的析构函数会执行。

RAII 正是依靠对象析构与栈展开配合，保证异常路径中的资源清理。

### 6. 构造函数抛出异常时会怎样？

如果构造函数抛出异常，完整对象没有成功构造，因此该对象自己的析构函数不会被调用。

但在抛出异常之前已经成功构造完成的基类和成员子对象会被销毁，帮助清理它们已经获取的资源。

~~~cpp
struct Member {
    ~Member() { std::cout << "Member destroyed"; }
};

struct A {
    Member m;

    A()
    {
        throw std::runtime_error("construction failed");
    }

    ~A() { std::cout << "A destroyed"; }
};
~~~

创建 `A` 对象失败时，`m` 会被销毁，但 `A` 的析构函数不会执行。

这也是为什么应该把资源放进 RAII 成员中，而不是在构造函数中获取资源后完全依赖外层对象析构函数清理。

### 7. 析构函数中可以抛异常吗？

从语法角度看，析构函数可以涉及可能抛异常的操作，但从设计角度，**不应该让异常从析构函数逃逸**。

许多析构函数默认具有不抛异常的异常规范。若析构函数中的异常逃逸，而此时已经有另一个异常在栈展开中传播，程序会调用 `std::terminate`。

资源清理通常应该做到可靠、尽可能不抛异常。若清理动作本身可能失败，应设计明确的错误报告或显式关闭接口，而不是依赖析构函数向外抛异常。

### 8. 重新抛出异常怎么写？

~~~cpp
try {
    DoWork();
} catch (const std::exception& e) {
    Log(e.what());
    throw; // 重新抛出当前正在处理的异常对象
}
~~~

在 catch 处理器中使用不带操作数的 `throw;` 会重新抛出当前异常，保留原始异常对象的动态类型。

不要轻易写成 `throw e;`：当 `e` 是基类引用时，这种写法可能按静态类型重新构造异常对象，从而发生切片。

### 9. 什么是异常安全保证？

异常安全通常分为几个层级：

1. **无泄漏保证（No-throw resource leak guarantee）：** 发生异常时不会泄漏资源；对象仍保持可析构和可清理的状态。
2. **基本保证（Basic guarantee）：** 发生异常后，对象保持有效状态，满足类不变量，但状态可能发生变化。
3. **强保证（Strong guarantee）：** 操作成功则完成效果；失败则对可观察状态没有影响，通常称为“要么成功，要么无效果”。
4. **不抛异常保证（No-throw guarantee）：** 操作保证不向外传播异常。

不同资料对层级命名可能略有差异；回答面试题时要说明保证的具体含义。

### 10. 如何实现强异常安全保证？

一种常见思路是先准备新状态，所有可能失败的操作都在临时状态上完成；成功后再以不抛异常的方式交换或提交状态。

~~~cpp
void SetValue(const Value& value)
{
    Value temp(value); // 复制可能抛异常，但当前对象还未改变
    data.swap(temp);   // 若 swap 满足不抛异常，则提交新状态
}
~~~

这个示例依赖 `Value` 的构造与 `swap` 具备相应性质，不能无条件套用。

另一种常见实现是 copy-and-swap：先构造临时副本，再交换资源，让赋值操作获得强异常安全保证（前提是相关复制和交换设计满足要求）。

### 11. 什么是 noexcept？

`noexcept` 用于声明函数不会向外传播异常。

~~~cpp
void ReleaseResource() noexcept
{
    // 清理操作
}
~~~

若一个标记为 `noexcept` 的函数让异常逃逸，程序会调用 `std::terminate`。

`noexcept` 不会把函数内部所有潜在异常都自动变成安全处理；它是函数对调用者作出的契约。

### 12. noexcept 与移动操作的关系

标准库容器在某些重新分配或扩容操作中，会考虑元素的移动构造是否不抛异常，以及复制是否可用，以满足异常保证。

因此，若移动构造确实不会抛异常，正确地声明为 `noexcept` 可能使标准库在相应场景选择移动操作。

但不要仅为了让容器“移动更快”就随意添加 `noexcept`。错误的承诺会使异常逃逸时触发终止。

### 13. 什么是异常规范？旧式动态异常规范呢？

现代 C++ 常见的是 `noexcept`。旧式动态异常规范，例如 `throw(Type)`，已在后续标准中被弃用并最终移除（C++17 移除）。

面试中重点掌握：

- `noexcept` 表达函数不会让异常逃逸。
- `noexcept(expr)` 可以在编译期查询某个表达式是否被声明为不抛异常。
- `noexcept` 与“函数内部绝对不会发生任何异常相关事件”不是同一概念。
- `noexcept` 不是用来代替错误处理设计的万能开关。

## 五、资源管理类与 Rule of Five

### 1. 为什么资源管理类要特别注意拷贝？

假设一个类拥有一块动态内存：

~~~cpp
class Buffer {
public:
    explicit Buffer(std::size_t size)
        : data(new int[size]), size(size)
    {
    }

    ~Buffer()
    {
        delete[] data;
    }

private:
    int* data;
    std::size_t size;
};
~~~

如果使用编译器生成的拷贝构造，两个对象的 `data` 可能指向同一块数组；两个析构函数都会尝试释放它，导致未定义行为。

如果类明确拥有原始资源，就需要设计拷贝、赋值、移动和析构行为。更推荐使用 `std::vector<int>` 或 `std::unique_ptr<int[]>` 等 RAII 成员，尽量避免手写裸资源管理。

### 2. Rule of Three 是什么？

如果类需要自定义以下三个操作中的一个，就应该认真检查另外两个是否也需要自定义：

- 析构函数。
- 拷贝构造函数。
- 拷贝赋值运算符。

原因是这通常说明类自己管理着某种资源；仅自定义其中一个，可能导致默认拷贝语义与资源所有权不匹配。

### 3. Rule of Five 是什么？

C++11 引入移动语义后，资源管理类还需要考虑：

- 移动构造函数。
- 移动赋值运算符。

因此常说 Rule of Five：析构、拷贝构造、拷贝赋值、移动构造和移动赋值五个操作应作为一组认真设计。

这不是要求每个类都必须手写五个函数，而是提醒开发者：自定义资源管理时要全面检查所有权语义。

### 4. Rule of Zero 是什么？

Rule of Zero 提倡：如果可以，就让资源由现成的 RAII 类型管理，使自己的类不必显式编写析构、拷贝和移动操作。

~~~cpp
class Buffer {
public:
    explicit Buffer(std::size_t size)
        : data(size)
    {
    }

private:
    std::vector<int> data;
};
~~~

这里 `std::vector<int>` 自己负责管理动态内存，`Buffer` 可以直接依靠成员类型获得合适的资源管理行为。

Rule of Zero 通常是现代 C++ 代码的首选。

### 5. 什么是 copy-and-swap？

copy-and-swap 是实现赋值运算符的一种常见惯用法：

~~~cpp
class Buffer {
public:
    Buffer(const Buffer& other); // 复制构造
    void swap(Buffer& other) noexcept;

    Buffer& operator=(Buffer other)
    {
        swap(other);
        return *this;
    }
};
~~~

参数按值传递：左值赋值时通常先复制构造临时参数，右值赋值时可能移动构造。随后与当前对象交换资源；函数返回时，临时参数析构并释放旧资源。

优点：

- 代码结构简洁。
- 若参数构造失败，当前对象尚未交换，通常可获得强异常安全保证。
- 统一处理复制和移动赋值的部分逻辑。

前提是复制/移动构造、swap 和析构实现正确；实际项目还需考虑性能、类型特性与自赋值语义。

### 6. 自赋值是什么？为什么需要考虑？

~~~cpp
a = a;
~~~

自赋值指对象将自身赋值给自身。

简单的资源管理赋值实现可能先释放目标资源，再尝试从源对象复制资源；如果源和目标是同一个对象，就可能读到已经释放的资源。

可通过自赋值检查、copy-and-swap 或其他经过验证的赋值策略处理。不过不需要盲目地给所有赋值运算符都添加检查：应结合具体实现和性能需求判断。

### 7. 移动后源对象必须为空吗？

不一定。

移动操作的语义由类型定义决定。对于标准库类型，通常应遵循该类型对 moved-from 对象的规定：对象仍然有效，但具体值可能未指定。

对自己实现的类型，可以设计移动后源对象为空或处于某个明确的有效状态，但应保证其可以安全析构，并满足类不变量。

## 六、异常处理与资源管理的结合

### 1. 为什么不能只依靠 try-catch 清理资源？

~~~cpp
void Process()
{
    int* p = new int[100];
    try {
        DoWork();
    } catch (...) {
        delete[] p;
        throw;
    }
    delete[] p;
}
~~~

这种写法必须在每一个可能离开的控制路径中考虑释放；后续维护时很容易漏掉某条路径，代码也会变得复杂。

更稳妥的写法是：

~~~cpp
void Process()
{
    auto p = std::make_unique<int[]>(100);
    DoWork();
} // 自动释放
~~~

RAII 将清理逻辑放在资源所有者类型中，比散落在业务代码中的手动清理更可靠。

### 2. catch(...) 是什么？

~~~cpp
try {
    DoWork();
} catch (...) {
    // 捕获任何 C++ 异常
    throw;
}
~~~

`catch (...)` 可以匹配任何 C++ 异常，但它不能直接访问具体异常对象的类型和内容。

通常适合用于最外层边界的兜底处理，或在清理后重新抛出异常。不要无条件捕获并忽略所有异常，否则容易隐藏真正的错误。

### 3. 异常与错误码如何选择？

异常与错误码各有适用场景：

- 异常适合跨越多层调用传播错误，且调用方可以在合适层次处理的情况。
- 错误码或显式结果类型适合错误是常见控制流、调用方需要逐步处理结果、或项目约定不使用异常的情况。
- 具体选择还受到性能预算、API 约定、平台、团队规范等影响。

面试时不要说“异常一定比错误码好”或“异常绝对不能用于游戏引擎”。应结合项目架构、错误频率、跨模块边界和异常安全设计讨论。

### 4. 构造函数失败时，如何避免资源泄漏？

优先把每项资源封装成 RAII 成员：

~~~cpp
class Service {
public:
    Service()
        : buffer(std::make_unique<int[]>(100))
    {
        Initialize(); // 如果抛出异常，buffer 成员会自动析构
    }

private:
    std::unique_ptr<int[]> buffer;
};
~~~

如果构造函数抛出异常，已成功构造的成员会按规则销毁。相比在构造函数体里先拿裸资源、再执行可能抛异常的初始化逻辑，这种设计更安全。

### 5. 函数 try block 是什么？

构造函数和普通函数可以使用函数 try block 来捕获函数体及（对构造函数而言）成员初始化阶段传播出来的异常。

~~~cpp
Widget::Widget() try
    : member(Init())
{
    DoWork();
}
catch (const std::exception& e) {
    Log(e.what());
    throw;
}
~~~

构造函数函数 try block 的 catch 处理器执行时，已构造完成的基类和成员子对象已经被销毁；不应把它当作能够继续使用一个部分构造对象的机会。

函数 try block 是较专门的语法，日常资源管理仍应优先依靠 RAII。

## 七、常见面试题与易错点

### Q1：new 与 malloc 的区别是什么？

new-expression 会执行对象初始化，并在类类型场景中调用构造函数；malloc 只分配原始存储。默认 new 分配失败时抛出 `std::bad_alloc`，malloc 则返回空指针。两者必须使用匹配的释放方式。

### Q2：new 和 operator new 有什么区别？

new-expression 负责分配存储并初始化对象；`operator new` 是提供原始存储的分配函数，本身不等同于完整的对象创建流程。

### Q3：为什么数组 new 必须与 delete[] 配对？

数组 new-expression 与数组 delete-expression 在元素初始化、销毁和存储释放上具有相应规则。使用不匹配的 delete 形式会导致未定义行为。

### Q4：placement new 会分配内存吗？

通常不会。它在调用者提供的、大小与对齐均满足要求的存储空间中构造对象。对象析构与存储释放需要分开考虑。

### Q5：RAII 为什么能保证异常安全？

因为异常传播时会销毁已构造完成的自动存储期对象，而 RAII 对象的析构函数负责释放其持有的资源。

### Q6：unique_ptr 和 shared_ptr 的核心区别是什么？

`unique_ptr` 表达独占所有权，不可复制但可移动；`shared_ptr` 表达共享所有权，通常通过强引用计数决定对象何时销毁。

### Q7：weak_ptr 为什么不能直接访问对象？

它不持有强所有权，不保证对象仍然存活。需要调用 `lock()` 尝试获取 `shared_ptr`，成功后才能在该强引用的生命周期内安全使用对象。

### Q8：shared_ptr 循环引用为什么会泄漏？

互相持有的强引用使双方强引用计数都无法归零，因而对象不会自动销毁。对非拥有关系使用 weak_ptr 可以打破相应循环。

### Q9：为什么析构函数通常不应抛异常？

异常逃逸可能导致终止，尤其在已有异常进行栈展开时。析构函数应可靠地清理资源；可能失败的操作可通过显式接口报告错误。

### Q10：noexcept 有什么意义？

它声明函数不会让异常向外传播。若异常逃出 noexcept 函数，程序会调用 std::terminate。对移动操作，正确的 noexcept 声明可能影响标准库容器的策略选择。

### Q11：什么是异常安全的强保证？

操作成功时完成预期效果，失败时不改变可观察状态，常称为“要么成功，要么无效果”。常见实现方式是先准备临时状态，再通过合适的 swap 或提交操作完成更新。

### Q12：为什么资源管理类容易违反 Rule of Three/Five？

因为默认逐成员拷贝不会自动复制裸指针指向的资源；自定义析构却会释放资源，可能导致浅拷贝、重复释放和悬空指针。因此必须一起审视拷贝、移动与析构语义。
