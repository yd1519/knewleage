## 一、并发编程的基本概念

### 1. 并发和并行有什么区别？

- **并发（Concurrency）**：多个任务在一个时间范围内都有进展，执行可能交替发生。
- **并行（Parallelism）**：多个任务在同一时刻实际执行，通常涉及多个处理核心。

单核心 CPU 上可以通过调度实现并发，但不一定有真正的同时执行；多核心系统可以让不同线程并行。并发是组织多个任务的方式，并行是具体执行方式，两者相关但不等价。

### 2. 进程和线程的区别是什么？

在常见操作系统中：

- 进程通常拥有独立的虚拟地址空间和系统资源管理上下文。
- 同一进程中的线程通常共享进程地址空间、代码和全局数据。
- 各线程通常拥有自己的线程执行状态、调用栈和线程局部存储。
- 线程间共享内存使数据传递方便，也使同步和竞态问题更加突出。

具体进程、线程的实现属于操作系统；C++ 标准主要规定线程执行、对象访问和内存模型的可观察语义。

### 3. 什么是线程安全？

一个操作被称为线程安全，需要说明**并发调用的条件和保证**。常见含义是：在满足接口前置条件时，多个线程调用不会发生数据竞争或破坏对象不变量，并产生符合接口约定的结果。

不要把以下概念混淆：

- **无数据竞争**：没有违反 C++ 内存模型的数据访问冲突。
- **操作原子性**：某个操作以不可分割的方式对外表现。
- **线程安全**：整个接口在规定并发条件下行为正确。
- **逻辑正确**：即使没有数据竞争，程序也可能出现丢失工作、错误顺序或死锁。

### 4. 什么是竞态条件（Race Condition）？

竞态条件是指程序的正确性依赖线程的执行交错或时间关系。它可能导致逻辑错误，但不一定构成 C++ 语言定义的**数据竞争（Data Race）**。

例如两个线程都通过加锁的接口检查余额后分别扣款，如果检查和扣款并非同一个受保护事务，仍可能发生逻辑上的检查-使用竞态（TOCTOU）。

### 5. 什么是数据竞争（Data Race）？

在 C++ 内存模型中，可以简化理解为：两个不同线程中的执行涉及同一内存位置，至少一个访问是写入，访问不满足所要求的原子性或同步关系，且两者没有按 `happens-before` 等规则排序，便可能构成数据竞争。

~~~cpp
int counter = 0;

void Increment()
{
    ++counter; // 若两个线程无同步地同时执行，发生数据竞争
}
~~~

**数据竞争在 C++ 中导致未定义行为（UB）。** 不能仅仅说“最后结果可能少于预期”，因为标准不保证程序行为。

正确做法可以是互斥锁或合适的原子操作。

## 二、std::thread：线程创建与生命周期

### 1. 如何创建线程？

C++11 在 `<thread>` 中提供 `std::thread`：

~~~cpp
#include <iostream>
#include <thread>

void Worker(int id)
{
    std::cout << "worker " << id << '\n';
}

int main()
{
    std::thread t(Worker, 1);
    t.join();
}
~~~

构造线程对象后，新线程可以开始执行提供的可调用对象。不要假设新线程一定在主线程后面才执行第一条工作语句；实际交错由调度和同步决定。

### 2. join() 是什么？

`join()` 会等待目标线程执行结束，然后使该 `std::thread` 对象不再关联一个可连接线程。

~~~cpp
std::thread t([] {
    DoWork();
});

t.join(); // 等到 DoWork 执行结束
~~~

同一个线程对象不能成功 `join()` 两次。调用前可用 `joinable()` 检查关联状态；还要避免线程尝试 join 自己等错误操作。

线程完成和 join 成功返回之间存在标准规定的同步关系：被 join 线程执行结束与 join 返回后的后续工作可以建立相应的顺序保证。

### 3. detach() 是什么？

`detach()` 使 `std::thread` 对象与底层线程分离。分离后，线程可以独立继续运行，当前线程对象不再负责 join 它。

~~~cpp
std::thread t([] {
    DoWork();
});
t.detach();
~~~

**注意：**

- detach 不表示线程已经结束。
- detach 之后不能再通过原来的线程对象 join。
- 必须确保分离线程访问的对象在访问期间仍然存活。
- 进程退出或运行时终止时，并不能保证分离线程总能完成工作和清理。

实际工程中，除非生命周期设计非常明确，通常优先采用可管理的线程所有权和 join，而不是随意 detach。

### 4. joinable() 是什么意思？

`joinable()` 用于判断 `std::thread` 对象当前是否关联一个线程执行实体，**不是判断线程此刻是否仍在运行**。

即使线程函数已经执行完毕，只要还没有 join 或 detach，对应 `std::thread` 仍可能是 joinable。

### 5. 为什么 std::thread 析构时可能导致 terminate？

~~~cpp
void Bad()
{
    std::thread t([] {
        DoWork();
    });
} // t 仍 joinable：析构时调用 std::terminate
~~~

`std::thread` 的析构函数不会自动 join 或 detach；如果析构时仍为 joinable，会调用 `std::terminate`。

这是高频面试题。**创建线程后，必须明确处理线程对象的生命周期。**

### 6. 如何用 RAII 管理 thread？

C++11/14 可以自行封装一个“析构时 join”的对象：

~~~cpp
#include <thread>
#include <utility>

class JoiningThread {
public:
    explicit JoiningThread(std::thread thread)
        : thread_(std::move(thread))
    {
    }

    ~JoiningThread()
    {
        if (thread_.joinable()) {
            thread_.join();
        }
    }

    JoiningThread(const JoiningThread&) = delete;
    JoiningThread& operator=(const JoiningThread&) = delete;

private:
    std::thread thread_;
};
~~~

这只是基础示意：真实工程还需要考虑是否允许移动、析构时从工作线程自身执行、停止协议和任务可能阻塞等问题。

C++20 的 `std::jthread` 提供了更方便的线程生命周期管理；后文会介绍。

### 7. 如何向线程函数传递参数？

~~~cpp
void Process(int id, std::string name)
{
}

std::thread t(Process, 1, std::string("Alice"));
t.join();
~~~

`std::thread` 会按其构造规则保存并转交调用参数，不能简单把所有实参都视为绑定到原变量的引用。

### 8. 如何传递引用参数？

~~~cpp
#include <functional>
#include <thread>

void Increase(int& value)
{
    ++value;
}

int main()
{
    int x = 0;
    std::thread t(Increase, std::ref(x));
    t.join();
    // x == 1
}
~~~

这里使用 `std::ref(x)` 明确告诉线程调用机制传递对 `x` 的引用。

**生命周期警告：** 传给线程的引用指向的对象必须在相应访问期间存活。示例在主线程中 join，保证离开作用域前完成写入。

### 9. lambda 捕获与线程生命周期

~~~cpp
void Launch()
{
    int value = 42;

    std::thread t([&] {
        Use(value);
    });

    t.join(); // 在 value 销毁前等待线程完成
}
~~~

如果改成 `detach()`，线程可能在 `value` 生命周期结束后继续访问它，造成悬空引用与未定义行为。

延迟回调和异步任务中的 lambda 引用捕获也是同样的风险。并不是“捕获了引用就一定线程不安全”，而是必须保证生命周期与同步正确。

### 10. thread::hardware_concurrency() 是什么？

`std::thread::hardware_concurrency()` 返回实现提供的并发线程数量提示，可能返回 0，且不保证等于程序真正可用的核心数或最佳线程池大小。

不要直接把它当作准确 CPU 核数；CPU 配额、超线程、处理器亲和性、任务阻塞比例和部署环境都可能影响合理的线程数。

## 三、共享数据、数据竞争与同步

### 1. 为什么 counter++ 不是原子操作？

~~~cpp
int counter = 0;
++counter;
~~~

对于普通 `int`，`++counter` 不能保证跨线程原子完成。概念上它可能包含读取、计算和写回等步骤。

两个线程无同步地同时修改同一变量时，会形成数据竞争，属于未定义行为。

不能说“整型是机器天然支持的，所以 ++ 一定线程安全”。即使某个平台支持某种单条指令，该 C++ 表达式仍需要满足语言层面的原子或同步规则。

### 2. 加锁后的正确计数器

~~~cpp
#include <mutex>

int counter = 0;
std::mutex counterMutex;

void Increment()
{
    std::lock_guard<std::mutex> lock(counterMutex);
    ++counter;
}
~~~

互斥锁让使用同一锁正确保护的临界区串行执行，避免这些访问之间的数据竞争。

**前提：** 所有可能与之冲突的其他访问，也要遵守同一同步协议。仅给写入方加锁、读取方不加锁，仍可能存在数据竞争。

### 3. volatile 能保证线程安全吗？

不能。

~~~cpp
volatile int counter = 0;
// 两线程同时 ++counter 仍不能视为合法的线程同步
~~~

`volatile` 不提供原子性，也不建立 C++ 线程间的同步关系。对于多线程共享变量，应使用互斥锁、`std::atomic` 等同步机制。

`volatile` 的用途与某些硬件接口、特殊可观察访问有关，不应当作“防止编译器优化，所以线程安全”的万能方案。

### 4. 只读共享对象需要锁吗？

如果多个线程只读取一个已经安全发布、且不会并发修改的对象，通常不需要为每次读取都加锁。

但“现在只读”并不自动意味着安全：还需要确保对象已经构造完成、读取的发生顺序正确、对象生命周期足够长，并且没有其他线程同时修改这些内存位置。

### 5. std::vector 等标准容器是线程安全的吗？

标准库通常允许不同线程并发使用**不同容器对象**；在满足要求的条件下，对同一容器进行并发只读访问也可以合法。

但不能认为“vector 自己会自动加锁”。例如：

~~~cpp
std::vector<int> values;
// 一个线程 push_back，另一个线程在无同步下访问同一 vector
// 通常不安全
~~~

当一个线程可能修改容器的大小、结构、元素存储或某个元素，而其他线程同时访问受影响的数据时，需要考虑同步。`vector<bool>` 的按位压缩表示尤其不适合套用普通元素独立写入的简单直觉。

## 四、mutex 与 RAII 锁管理

### 1. std::mutex 是什么？

`std::mutex` 是互斥原语。线程在访问共享临界区之前获取锁，完成后释放锁；其他尝试获取同一互斥锁的线程可能需要等待。

~~~cpp
std::mutex m;

void Foo()
{
    m.lock();
    // 访问受保护数据
    m.unlock();
}
~~~

这种手动 `lock()/unlock()` 写法存在忘记释放的风险，尤其是提前 return 或抛异常的路径。

### 2. 为什么优先使用 lock_guard？

~~~cpp
void Foo()
{
    std::lock_guard<std::mutex> lock(m);
    DoWork();
} // lock 析构时自动解锁
~~~

`std::lock_guard` 在构造时获取锁，并在作用域结束时自动释放锁，符合 RAII 思想。

适合不需要中途解锁、转移锁所有权等复杂行为的简单临界区。

### 3. unique_lock 和 lock_guard 有什么区别？

| 对比 | lock_guard | unique_lock |
|---|---|---|
| 主要用途 | 简洁的作用域加锁 | 灵活的锁所有权管理 |
| 中途 unlock/relock | 不支持接口 | 支持 |
| 延迟加锁 | 不适用 | 可使用 defer_lock |
| 锁所有权转移 | 不可移动 | 可移动 |
| 条件变量 wait | 不能直接作为 std::condition_variable::wait 参数 | 可用于 wait |
| 一般成本 | 简单、开销少 | 维护更多状态，可能略复杂 |

~~~cpp
std::unique_lock<std::mutex> lock(m);
UpdateSharedState();

lock.unlock(); // 可以主动提前解锁
DoSlowWork();  // 不需要保护共享数据时，避免长期持锁
~~~

### 4. 什么是 defer_lock、try_to_lock、adopt_lock？

这些标签控制 RAII 锁包装器如何处理已有锁状态：

~~~cpp
std::unique_lock<std::mutex> a(m, std::defer_lock); // 构造时不加锁
std::unique_lock<std::mutex> b(m, std::try_to_lock); // 尝试加锁，不保证成功
~~~

`std::adopt_lock` 表示当前线程已经正确持有目标锁，让包装器接管释放责任。若未持锁却错误使用 adopt_lock，将违反前置条件。

### 5. try_lock() 的作用

`try_lock()` 尝试获取互斥锁，通常不会像 `lock()` 一样等待锁变为可用；获取失败则返回失败结果。

~~~cpp
std::unique_lock<std::mutex> lock(m, std::try_to_lock);
if (!lock.owns_lock()) {
    return;
}

UpdateSharedState();
~~~

需要处理“未能获取锁”的分支。尝试加锁不是“锁一定空闲时才会返回成功”的同步之外的额外保证，而是由互斥量本身的原语规定结果。

### 6. recursive_mutex 是什么？

`std::recursive_mutex` 允许同一线程在已经拥有该锁时再次成功锁定，并要求相应次数的解锁。

它有时用于旧代码重入路径，但容易掩盖复杂的锁层次设计。若普通 `std::mutex` 被同一线程重复 `lock()` 而没有正确解锁，则会违反对应使用约束，可能死锁。

不应把 recursive_mutex 当作“更安全的 mutex”。能简化锁作用域和调用结构时，通常优先简化设计。

### 7. shared_mutex 和读写锁

读写锁允许多个读取者共享访问，但写入需要独占访问。

C++14 提供 `std::shared_timed_mutex`，C++17 提供 `std::shared_mutex`。可用 `std::shared_lock` 获取共享读锁、`std::unique_lock` 获取独占写锁。

~~~cpp
// C++17
#include <shared_mutex>

std::shared_mutex rwMutex;
std::unordered_map<int, int> table;

int Read(int key)
{
    std::shared_lock<std::shared_mutex> lock(rwMutex);
    auto it = table.find(key);
    return it == table.end() ? -1 : it->second;
}

void Write(int key, int value)
{
    std::unique_lock<std::shared_mutex> lock(rwMutex);
    table[key] = value;
}
~~~

读写锁不一定比普通互斥锁快：需要考虑读写比例、临界区长度、争用程度和实现开销。

### 8. 什么是锁粒度？

- **粗粒度锁**：一把锁保护较大范围，简单但并行度可能较低。
- **细粒度锁**：多个锁保护不同资源，增加并行机会，但设计与死锁分析更复杂。

过大的锁作用域可能导致线程长时间排队；过小的锁粒度又可能增加锁开销和复杂度。需要按真实热点、共享状态和性能测量选择。

### 9. std::once_flag 与 call_once

某些初始化逻辑应该全局只执行一次：

~~~cpp
#include <mutex>

std::once_flag initFlag;

void Initialize()
{
    std::call_once(initFlag, [] {
        SetupGlobalResource();
    });
}
~~~

`std::call_once` 保证对同一标志的成功初始化具有相应一次执行和同步语义；如果传入的函数抛异常，这次调用不会被视为成功完成，以后可以重试。

C++11 的函数局部 static 初始化也具有线程安全保证，但它与 `call_once` 的接口形式和适用场景不同。

## 五、死锁、活锁与饥饿

### 1. 什么是死锁？

死锁是多个执行实体互相等待彼此持有或依赖的资源，导致无法继续前进的情况。

~~~cpp
std::mutex m1;
std::mutex m2;

// 线程 A
void A()
{
    std::lock_guard<std::mutex> l1(m1);
    std::lock_guard<std::mutex> l2(m2);
}

// 线程 B
void B()
{
    std::lock_guard<std::mutex> l2(m2);
    std::lock_guard<std::mutex> l1(m1);
}
~~~

如果 A 已持有 m1 并等待 m2，而 B 已持有 m2 并等待 m1，就可能死锁。

### 2. 死锁的四个必要条件

经典操作系统理论中，死锁通常与以下必要条件有关：

1. 互斥。
2. 请求并保持。
3. 不可抢占。
4. 循环等待。

这些是理解死锁的一种常用模型，不意味着识别 C++ 程序的每一个并发问题都必须套成四句话。

### 3. 如何避免两个 mutex 的死锁？

C++11 可通过 `std::lock` 同时协调获取多把锁：

~~~cpp
std::unique_lock<std::mutex> l1(m1, std::defer_lock);
std::unique_lock<std::mutex> l2(m2, std::defer_lock);

std::lock(l1, l2); // 使用避免该锁获取过程死锁的算法
~~~

C++17 可以使用 `std::scoped_lock`：

~~~cpp
std::scoped_lock lock(m1, m2); // C++17
~~~

其他常见策略是统一锁获取顺序、缩短临界区、减少锁嵌套和明确锁层次。

### 4. 活锁与饥饿是什么？

- **活锁（Livelock）**：线程持续采取动作或重试，但彼此相互干扰，无法完成有效进展。
- **饥饿（Starvation）**：某个线程长期无法获得它需要的资源或执行机会。
- **死锁**：线程相互等待，缺乏进展。

三者都属于并发系统的活性问题；程序可以完全没有数据竞争，却依然死锁或饥饿。

### 5. 优先级反转是什么？

高优先级线程等待低优先级线程持有的锁，而中优先级任务可能影响低优先级线程的运行，导致高优先级线程被间接阻塞。

优先级继承等机制可用于某些实时系统，但不属于 `std::mutex` 在所有平台上统一保证的行为。需要结合操作系统和调度策略分析。

## 六、condition_variable：线程间等待与通知

### 1. 为什么需要条件变量？

如果线程需要等待某个条件成立，不应一直忙等：

~~~cpp
while (!ready) {
    // 空转，会消耗 CPU；普通 ready 还可能形成数据竞争
}
~~~

`std::condition_variable` 允许线程在条件暂时不满足时等待，并由其他线程在状态变化时通知它。

### 2. 最基本的等待模型

~~~cpp
std::mutex m;
std::condition_variable cv;
bool ready = false;

void Consumer()
{
    std::unique_lock<std::mutex> lock(m);
    cv.wait(lock, [] { return ready; });

    // 持锁且 ready == true
    Consume();
}

void Producer()
{
    {
        std::lock_guard<std::mutex> lock(m);
        ready = true;
    }
    cv.notify_one();
}
~~~

需要包含 `<mutex>` 和 `<condition_variable>`。这里假设 `Consume()` 访问的相关状态也遵守同一同步协议。

### 3. wait 为什么要用谓词？

`condition_variable::wait` 允许**虚假唤醒（spurious wakeup）**：线程可能在未收到满足业务条件的通知时返回。

因此推荐：

~~~cpp
cv.wait(lock, [] { return ready; });
~~~

它的逻辑等价于反复检查：

~~~cpp
while (!ready) {
    cv.wait(lock);
}
~~~

不要只在 wait 前检查一次：

~~~cpp
if (!ready) {
    cv.wait(lock); // 错误习惯：醒来时不保证 ready 已成立
}
~~~

### 4. wait 如何与 mutex 配合？

调用 `wait(lock)` 时，条件变量会以规定的原子等待操作释放关联的互斥锁并进入等待状态；被唤醒后，在 wait 返回给调用者前重新获取锁。

因此等待线程不会在整个睡眠期间一直占有这把 mutex，生产者可以获得锁并修改共享状态。

### 5. 什么是“丢失通知”？

如果仅把通知当作事件、不用受锁保护的共享状态记录条件，通知可能发生在另一个线程真正开始等待之前，导致后者之后一直等待。

正确思路是：**条件变量负责提示“状态可能改变了”，真正的判断依据是受同步保护的共享谓词。**

发送方改变受锁保护的状态，等待方检查谓词，才能避免把通知当作可累积的计数信号。

### 6. notify_one 和 notify_all 的区别

- `notify_one()`：通知一个正在等待的线程。
- `notify_all()`：通知所有正在等待的线程。

选择取决于业务条件。例如一个新任务通常只需要唤醒一个消费者；队列关闭时可能需要唤醒所有消费者。

通知不是任务本身，通知次数也不是稳定的工作队列容量。应由共享状态记录实际任务和停止条件。

### 7. 生产者—消费者队列示例（C++11）

~~~cpp
#include <condition_variable>
#include <mutex>
#include <queue>

std::queue<int> tasks;
std::mutex queueMutex;
std::condition_variable queueCv;
bool stopping = false;

// 生产者
void PushTask(int value)
{
    {
        std::lock_guard<std::mutex> lock(queueMutex);
        tasks.push(value);
    }
    queueCv.notify_one();
}

// 消费者
void Worker()
{
    for (;;) {
        int task;
        {
            std::unique_lock<std::mutex> lock(queueMutex);
            queueCv.wait(lock, [] {
                return stopping || !tasks.empty();
            });

            if (stopping && tasks.empty()) {
                return;
            }

            task = tasks.front();
            tasks.pop();
        }

        Process(task); // 不持锁执行耗时工作
    }
}

// 停止所有工作线程前
void StopWorkers()
{
    {
        std::lock_guard<std::mutex> lock(queueMutex);
        stopping = true;
    }
    queueCv.notify_all();
}
~~~

示例展示关键同步机制，省略了线程创建和 join。这里约定：调用 `StopWorkers()` 后不再提交新任务；真实系统需要将“停止”和“禁止新提交”作为一致的接口协议。

### 8. 为什么把耗时工作移出锁作用域？

线程从队列取出任务后释放锁，再执行 `Process(task)`，使其他线程可以继续入队或取任务。

若把耗时工作也放在锁内执行，所有消费者在处理任务时都排队等待同一把锁，会严重降低并发度。

### 9. wait_for 和 wait_until

条件变量可以进行超时等待：

~~~cpp
std::unique_lock<std::mutex> lock(m);
bool ok = cv.wait_for(lock,
                      std::chrono::milliseconds(100),
                      [] { return ready; });
~~~

使用带谓词版本，返回值可表达条件是否满足。超时、通知、系统调度等情况都需要考虑；**超时不等于业务条件绝对不会很快变化**。

使用循环式相对超时等待时要小心虚假唤醒导致总等待时间被反复重置，必要时使用绝对截止时间。

## 七、std::atomic：原子操作

### 1. 什么是原子操作？

原子操作是按照 C++ 内存模型定义对某个原子对象进行不可分割的访问或修改。它可以消除针对该原子对象的某些数据竞争，但**不自动保证由多个对象和多个操作构成的业务事务具有原子性**。

~~~cpp
#include <atomic>

std::atomic<int> counter{0};

void Increment()
{
    ++counter;
}
~~~

多个线程执行原子自增不会对 `counter` 本身造成数据竞争，每次自增效果会被纳入该原子对象的修改顺序。

### 2. atomic 与 mutex 有什么区别？

| 对比项 | atomic | mutex |
|---|---|---|
| 典型保护对象 | 单个原子对象或精心设计的无锁协议 | 临界区内的多个数据对象和不变量 |
| 典型接口 | load、store、exchange、fetch_add、CAS | lock、unlock、RAII 锁 |
| 是否允许阻塞 | 取决于操作和实现；并非所有 atomic 都锁自由 | 获取锁时可能阻塞 |
| 业务事务范围 | 通常需要额外协议 | 临界区易于表达复合事务 |
| 使用复杂度 | 简单计数容易；复杂内存序很难 | 通常更容易正确组织复杂共享状态 |

atomic 不一定比 mutex 快。性能还取决于争用、缓存行流量、内存序、临界区大小和平台实现。

### 3. load 和 store

~~~cpp
std::atomic<bool> ready{false};

ready.store(true);
bool value = ready.load();
~~~

未显式指定内存序时，常见原子成员操作默认使用 `std::memory_order_seq_cst`（顺序一致）。

### 4. fetch_add / fetch_sub / exchange

~~~cpp
std::atomic<int> x{10};

int old1 = x.fetch_add(3); // 返回旧值 10；x 变为 13
int old2 = x.fetch_sub(2); // 返回旧值 13；x 变为 11
int old3 = x.exchange(5);  // 返回旧值 11；x 变为 5
~~~

这些原子读-改-写操作对同一个原子对象具有不可分割的效果。

### 5. 原子自增与 fetch_add

~~~cpp
std::atomic<int> x{0};

++x;           // x 变成 1，前置自增表达式得到新值
int old = x++; // old 为 1；x 变成 2
~~~

对于整数原子类型，`fetch_add(1)` 返回修改前的值。熟悉原子操作的返回值语义对分析并发计数器代码很重要。

### 6. atomic 是否总是 lock-free？

不一定。

~~~cpp
std::atomic<int> value{0};
bool lockFree = value.is_lock_free();
~~~

`is_lock_free()` 可查询该原子对象的操作是否由实现以锁自由方式支持。不同类型、大小、对齐及平台可能产生不同结果。

不要把 `std::atomic<T>` 直接等同于“必定是一条 CPU 原子指令”。C++ 标准关注语义保证，底层实现可能使用特定指令或其他机制。

## 八、CAS：Compare-And-Swap / Compare-Exchange

### 1. 什么是 CAS？

CAS 是比较并交换操作。概念上：

1. 读取原子对象的当前值。
2. 比较是否等于期望值。
3. 若相等则把它更新为目标值，否则不更新。

这三个动作作为一个原子读-改-写逻辑进行。

### 2. compare_exchange_strong

~~~cpp
std::atomic<int> x{10};
int expected = 10;

bool ok = x.compare_exchange_strong(expected, 20);
// 成功：ok == true，x == 20，expected 通常保持 10
~~~

如果比较失败：

~~~cpp
std::atomic<int> x{15};
int expected = 10;

bool ok = x.compare_exchange_strong(expected, 20);
// ok == false
// x 仍为 15
// expected 被更新为实际读取到的值 15
~~~

**高频考点：CAS 失败时会把观察到的当前值写回 expected。**

### 3. weak 与 strong 的区别

`compare_exchange_weak` 允许**伪失败（spurious failure）**：即使当前值与 expected 相等，也可能报告失败。

因此 weak 常用于重试循环：

~~~cpp
std::atomic<int> value{0};

void AddOne()
{
    int old = value.load();
    while (!value.compare_exchange_weak(old, old + 1)) {
        // 失败时 old 会被更新为观察到的当前值
    }
}
~~~

strong 不允许这种伪失败，但仍然会因为实际比较不匹配而失败。选择 weak 还是 strong 要结合重试模式和平台实现，并不是“strong 永远更好”。

### 4. CAS 一定不会重试吗？

不会。**单次 CAS 操作是原子尝试，使用 CAS 构造的完整算法可能不断失败并重试。**

在高竞争场景下，CAS 循环可能频繁失败而消耗 CPU，并不保证每个线程都能很快完成操作。

### 5. 什么是 ABA 问题？

无锁算法中，一个线程读取到状态为 A，期间其他线程可能把它变为 B 再变回 A。随后原线程 CAS 检查到的值仍为 A，就可能误以为状态从未改变。

~~~text
线程 1：看到 head == A
线程 2：A → B → A
线程 1：CAS(head, A, C) 成功，但期间结构可能已经变化
~~~

这是经典 ABA 问题。常见缓解方案包括版本标签、特定引用计数设计，以及与内存回收协议配合的无锁数据结构设计。

**ABA 不只是“数值又变回来了”，在无锁链表中还可能涉及节点回收与复用。**

## 九、C++ 内存模型与 happens-before

### 1. 为什么存在 C++ 内存模型？

CPU、编译器和缓存体系可能改变实际指令调度与访存方式。多线程不能以“每条源代码语句按顺序立刻写到所有核心可见的内存”来理解。

C++ 内存模型规定了共享对象如何合法访问、原子操作具有哪些顺序语义，以及何时可以认定一个线程对数据的写入对另一个线程可见。

要区分：

- 源代码中的先后顺序。
- 编译器在不改变合法程序语义前提下的优化。
- CPU 对内存访问的执行机制。
- C++ 标准中的 `sequenced-before`、`synchronizes-with` 与 `happens-before` 关系。

### 2. sequenced-before 是什么？

`sequenced-before` 用于描述**同一线程内**两个求值之间由语言规则确立的顺序关系。

例如普通语句：

~~~cpp
int x = 1;
int y = x + 1;
~~~

对一个线程的执行而言，这里的初始化在规定的顺序下进行。

但不要把“代码在同一个函数里写得靠前”机械当作所有子表达式求值顺序的保证：C++ 对某些表达式内的求值顺序仍有具体规定或未指定部分。

### 3. synchronizes-with 是什么？

`synchronizes-with` 是跨线程同步关系的重要来源。例如，某线程释放互斥锁，与另一个线程随后成功获得同一互斥锁之间存在相应同步关系。

原子操作在正确的 release/acquire 配合下，也能建立同步关系。

### 4. happens-before 是什么？

可以把 `happens-before` 理解为 C++ 内存模型中约束不同求值顺序和可见性的核心关系。它可由线程内的顺序关系、跨线程同步关系及其传递性建立。

**面试记忆：**

- 一个线程中对某数据的写入，不会仅因“墙上时间更早”就自动同步到另一个线程。
- 需要使用锁、正确配对的原子 release/acquire 或其他具有同步语义的机制建立关系。
- 若存在两个没有适当排序的冲突非原子访问，可能发生数据竞争并导致 UB。

### 5. 什么是修改顺序（Modification Order）？

每个原子对象都有它自己的修改顺序，所有线程对该对象的修改都纳入这个顺序。

但“每个原子对象都有修改顺序”**不等于**所有不同原子对象上的操作都存在一个大家一致观察到的全局顺序。跨对象顺序由所用内存序和同步协议决定。

### 6. 原子操作怎样帮助发布普通数据？

考虑一个线程写入普通数据，再通过原子标志告知另一个线程可以读取：

~~~cpp
#include <atomic>
#include <thread>

int data = 0; // 非原子对象
std::atomic<bool> ready{false};

void Producer()
{
    data = 42;
    ready.store(true, std::memory_order_release);
}

void Consumer()
{
    while (!ready.load(std::memory_order_acquire)) {
        // 等待标志变成 true
    }
    // 当 acquire 读取到了相应 release 所发布的 true：
    // 这里可以安全读取 data，结果为 42
    Use(data);
}
~~~

理解关键：

1. `data = 42` 在生产者线程中先于 release store。
2. 消费者的 acquire load **实际读取到**对应 release store（或符合规则的 release sequence）发布的值。
3. 因此建立同步关系，发布前写入可以对消费者可见。
4. 这里还假设生产者不再对 `data` 进行与读取相冲突的无同步修改，且对象生命周期有效。

**不是**只要在程序里写了 acquire/release 关键字，就自动保证任意两个线程的非原子对象访问都合法；必须有正确的配对和读取关系。

## 十、memory_order：内存序

### 1. 为什么 atomic 还需要内存序？

原子性解决的是“针对某个原子对象的访问不可分割”等问题。内存序进一步控制其他访问与原子操作之间的排序和同步保证。

不同协议需要不同保证。为了让程序正确且可维护，**通常应优先使用默认的 `seq_cst` 或 mutex，只有在证明有必要并能验证正确性时才采用较弱内存序。**

### 2. 常见内存序总览

| 内存序 | 主要含义 | 常见使用 |
|---|---|---|
| `memory_order_relaxed` | 保证原子性与该原子对象的修改顺序，但不额外建立跨线程同步 | 独立统计计数 |
| `memory_order_release` | 用于发布该操作之前的写入 | 生产者设置就绪标志 |
| `memory_order_acquire` | 用于获取与某 release 发布相匹配的同步信息 | 消费者读取就绪标志 |
| `memory_order_acq_rel` | 读-改-写操作同时具备 acquire 与 release 语义 | 同时接收并发布同步关系的 RMW |
| `memory_order_seq_cst` | 具有顺序一致性语义；默认值，提供更强的全局顺序约束 | 通用、易推理的原子操作 |
| `memory_order_consume` | 依赖传播相关语义；实现支持和标准演进复杂 | 一般工程中不建议依赖其细节 |

### 3. memory_order_relaxed 的典型用法

~~~cpp
std::atomic<unsigned long long> completed{0};

void MarkCompleted()
{
    completed.fetch_add(1, std::memory_order_relaxed);
}
~~~

如果只需要最终计数值，而不把这个计数器用于发布其他普通数据，relaxed 可以是合适选择。

**但计数器本身正确，不代表其他数据自动同步。** 不能把 “completed 已经加到某个值” 当成“其他线程的普通写入都已经可读”的依据，除非另有同步协议。

### 4. release/acquire 的典型用途

release 和 acquire 经常用于消息发布、初始化完成标志等“一方产生数据，另一方开始使用”的场景。

重点不是“store 一定对应 release，load 一定对应 acquire”，而是**当读取操作实际观察到相应发布操作时，才建立所需的同步关系**。

如果消费者一直读到旧值，尚未通过该标志完成同步，就不能提前访问被发布的普通数据。

### 5. memory_order_acq_rel 用在什么地方？

`acq_rel` 通常用于读-改-写操作，例如 `fetch_add`、`exchange` 或 CAS：

~~~cpp
std::atomic<int> state{0};
int old = state.exchange(1, std::memory_order_acq_rel);
~~~

其 acquire 部分可用于接收相应同步信息，release 部分可用于发布本线程之前的操作。不能把它当作“普通 load 或普通 store 都可以指定 acq_rel”的通用规则：不同原子操作允许的内存序有约束。

### 6. seq_cst 有什么优势？

`seq_cst`（顺序一致）在适当规则下为所有顺序一致操作建立一个统一顺序，便于按较直观的全局顺序推理。

~~~cpp
std::atomic<int> x{0};
x.store(1); // 默认 seq_cst
int value = x.load(); // 默认 seq_cst
~~~

不过顺序一致性也不意味着程序中所有普通对象的无同步访问都合法；非原子共享访问仍要满足数据竞争规则。

### 7. relaxed 可以保证原子计数，但不能发布 data

下面的程序存在问题：

~~~cpp
int data = 0;
std::atomic<bool> ready{false};

void Producer()
{
    data = 42;
    ready.store(true, std::memory_order_relaxed);
}

void Consumer()
{
    while (!ready.load(std::memory_order_relaxed)) {
    }
    // 错误：不能据此断定对 data 的读取已安全同步
    Use(data);
}
~~~

即使消费者读到 `ready == true`，relaxed load/store 之间也没有建立发布普通 `data` 的 synchronizes-with 关系。这类程序对 `data` 的访问可能构成数据竞争，导致 UB。

正确设计应使用合适的 release/acquire 配对，或使用同一 mutex 保护数据和状态。

### 8. 为什么不能随意组合内存序？

CAS、load、store、RMW 等允许的内存序并不完全相同：

- 对普通原子 load，不应使用仅适用于释放侧的内存序。
- 对普通原子 store，不应使用仅适用于获取侧的内存序。
- CAS 的成功与失败路径可以有不同内存序；失败路径只是加载行为，因此有其专门限制。

不符合操作要求的内存序参数可能违反前置条件并产生未定义行为。编写复杂原子代码前，应核对对应标准版本的准确接口规则。

### 9. atomic_thread_fence 是什么？

`std::atomic_thread_fence` 是线程栅栏（fence）接口，用于在特定原子操作配合下建立更复杂的排序与同步关系。

~~~cpp
std::atomic_thread_fence(std::memory_order_release);
~~~

**仅仅调用 fence 并不意味着所有普通内存访问都自动跨线程同步。** fence 需要按规定与原子操作建立关系，才能得到预期的线程间排序保证。

日常业务代码通常优先使用 mutex 或可直接推理的原子 acquire/release 标志，避免不必要地手写 fence 协议。

## 十一、重排序与经典面试题

### 1. 什么是指令重排序？

编译器和处理器可以在遵守合法程序可观察语义的范围内，改变操作的实现顺序或执行方式。这是优化的重要来源。

在多线程程序中，不能通过“单线程写代码的顺序”推断其他线程必然按同样顺序观察所有共享变量。

内存模型、同步原语与平台提供的顺序约束共同决定哪些结果合法。

### 2. 两个 relaxed 原子读到 0 的例子

~~~cpp
std::atomic<int> x{0};
std::atomic<int> y{0};
int r1 = -1;
int r2 = -1;

// 线程 A
void A()
{
    x.store(1, std::memory_order_relaxed);
    r1 = y.load(std::memory_order_relaxed);
}

// 线程 B
void B()
{
    y.store(1, std::memory_order_relaxed);
    r2 = x.load(std::memory_order_relaxed);
}
~~~

假设主线程正确启动、等待两个工作线程结束后再读取 `r1` 和 `r2`，那么在 relaxed 语义下，`r1 == 0 && r2 == 0` 是允许的结果。

这里 `r1` 和 `r2` 分别只由各自工作线程写入，主线程在 join 后读取，因此示例本身不需要让这两个结果变量也变成原子对象。

### 3. 把上述操作改为 seq_cst 呢？

如果四个原子操作都使用 `memory_order_seq_cst`，则同样结构下 `r1 == 0 && r2 == 0` 不可能作为一个符合顺序一致性规则的结果。

可以用全局一致顺序的约束来推理：

- 若 A 读到 0，说明 A 对 `y` 的 load 必须排在 B 写入 `y=1` 之前。
- 若 B 读到 0，说明 B 对 `x` 的 load 必须排在 A 写入 `x=1` 之前。
- 又要求每个线程内的 store 排在自己的 load 之前。
- 这些约束会形成不可满足的循环顺序。

**面试要点：** relaxed 与 seq_cst 都保证对各原子对象访问的原子性，但跨对象顺序允许的结果不同。

### 4. release/acquire 与 seq_cst 的关系

release/acquire 为符合配对条件的操作建立同步；seq_cst 提供更强的统一顺序约束。

不能说“release/acquire 等于 seq_cst，只是写法复杂”。它们约束的跨对象可见顺序不同，适合不同同步协议。

## 十二、锁自由算法与性能问题

### 1. lock-free 和 wait-free 有什么区别？

简化理解：

- **Lock-free（锁自由进展保证）**：系统整体可持续取得进展，不保证任意指定线程在有限步骤内完成。
- **Wait-free（无等待进展保证）**：每个线程的操作都能在有界步骤内完成，进展保证更强。
- **Obstruction-free（无障碍进展保证）**：在缺少其他线程持续干扰的情况下，单独执行的线程能够取得进展。

这些属于并发算法的进展性质，不等于“程序绝不调用互斥锁”这一表面实现细节。

### 2. lock-free 就一定更快吗？

不一定。

无锁算法可能遭遇：

- 大量 CAS 重试。
- 缓存行竞争。
- 内存回收困难。
- ABA 问题。
- 指令和内存屏障开销。
- 调试及维护成本增加。

当临界区很短、争用不高时，mutex 可能既简单又具有很好的性能。**正确性优先，性能结论必须用真实负载验证。**

### 3. 什么是假共享（False Sharing）？

两个线程写入不同变量，虽然从 C++ 语言上不存在数据竞争，但这些变量可能位于同一 CPU 缓存行。缓存一致性协议会让同一缓存行在核心间反复转移，导致性能下降。

~~~cpp
struct Counters {
    std::atomic<int> a{0};
    std::atomic<int> b{0};
};
~~~

如果 `a`、`b` 位于同一缓存行，不同线程频繁分别修改它们，可能发生假共享。

这不是 C++ 的未定义行为，而是硬件缓存层面的性能问题。

### 4. 如何缓解假共享？

- 尽量让高频写入的独立数据远离同一缓存行。
- 使用线程本地计数器，再在需要时汇总。
- 在有证据表明问题存在时，使用 `alignas` 或合适的填充和数据布局。
- C++17 的 `std::hardware_destructive_interference_size` 可在实现提供时作为相关参考，但不保证所有实现都可用或准确代表所有实际硬件。

### 5. 什么是线程局部存储（thread_local）？

~~~cpp
thread_local int localCount = 0;
~~~

不同线程拥有各自的 `localCount`，通常不需要就这个变量本身在不同线程间加锁。

它适合局部统计、临时缓存或线程独立状态。但要注意线程局部对象的初始化和析构、线程池任务与线程的对应关系，以及是否需要跨线程汇总结果。

### 6. 原子对象可否随意通过 memcpy 复制？

不能把 `std::atomic<T>` 当作普通的可随意按字节复制的共享状态对象。很多原子类型不可复制，直接对其存储字节做未同步操作可能破坏并发语义。

如果需要复制原子对象的值，通常应通过合法的 `load` 与 `store` 等接口，在所需同步关系下进行。

## 十三、future、promise 与 async

### 1. std::future 是什么？

`std::future<T>` 表示一个将来可能可用的异步结果。通过 `get()` 获取结果时，如果结果尚未就绪，会等待；如果异步操作记录了异常，`get()` 可以重新抛出该异常。

~~~cpp
#include <future>

std::future<int> result = std::async(std::launch::async, [] {
    return 6 * 7;
});

int answer = result.get(); // 42
~~~

普通 `std::future` 通常只能调用一次 `get()`；获取后会消耗其共享状态中的结果访问权。

### 2. std::promise 用来做什么？

`std::promise<T>` 提供产生异步结果的一端，对应的 `std::future<T>` 提供消费结果的一端。

~~~cpp
#include <future>
#include <thread>

std::promise<int> promise;
std::future<int> future = promise.get_future();

std::thread worker([&promise] {
    promise.set_value(42);
});

int answer = future.get();
worker.join();
~~~

示例中等待线程能通过 future 获取值；但真实代码还需要处理工作线程异常、超时策略和线程对象生命周期。

### 3. promise 如何传递异常？

~~~cpp
std::promise<int> promise;
auto future = promise.get_future();

try {
    throw std::runtime_error("failed");
} catch (...) {
    promise.set_exception(std::current_exception());
}

// 在获取异常结果时，future.get() 会重新抛出保存的异常
~~~

如果 promise 在尚未设置结果时被销毁，其相关共享状态可能以 `broken_promise` 错误通知未来的消费者。

### 4. std::async 一定启动新线程吗？

不一定。

~~~cpp
auto result = std::async(Work);
~~~

未指定启动策略时，标准允许选择包含 `std::launch::async` 和 `std::launch::deferred` 的实现定义策略组合。某些调用可能异步执行，也可能延迟到调用 `get()`、`wait()` 等操作时才执行。

如果确实要求独立的异步执行语义，应显式指定 `std::launch::async`，但仍要考虑线程资源与实现约束。

### 5. async 与 deferred 有什么区别？

~~~cpp
auto a = std::async(std::launch::async, Work);
auto b = std::async(std::launch::deferred, Work);
~~~

- `launch::async`：要求异步执行，通常会由另一个线程运行。
- `launch::deferred`：推迟执行，直到对应共享状态发生非定时等待等触发动作时才在调用者线程中执行；若从未触发，函数可能根本不执行。

所以 `std::async` 并不是绝对等价于 `std::thread`。

### 6. async 返回的 future 析构会等待吗？

要特别注意：某些由 `std::async(std::launch::async, ...)` 创建、关联到异步共享状态的 future，在释放最后一个共享状态引用时，可能阻塞等待异步任务完成。

~~~cpp
std::async(std::launch::async, [] {
    DoSlowWork();
}); // 临时 future 的析构可能等待任务完成
~~~

这意味着“忘记保存 future”不等于任务一定会在后台独立持续执行。具体阻塞语义要按共享状态来源和最后引用释放等条件判断，不能说所有 future 析构都等待。

### 7. packaged_task 是什么？

`std::packaged_task<R(Args...)>` 把可调用对象包装为任务，并将结果或异常保存在可通过 future 访问的共享状态中。

~~~cpp
#include <future>
#include <thread>

std::packaged_task<int()> task([] {
    return 42;
});

auto result = task.get_future();
std::thread t(std::move(task));

int value = result.get();
t.join();
~~~

它很适合为线程池中的任务提供 future 结果，但 packaged_task 本身不是线程池，也不负责选择在哪个线程执行。

### 8. std::shared_future 是什么？

`std::shared_future<T>` 允许多个持有者访问同一个异步共享状态的结果，并支持多次 `get()`；与普通 future 不同，它可以复制。

~~~cpp
std::promise<int> promise;
std::shared_future<int> shared = promise.get_future().share();

promise.set_value(42);
int a = shared.get();
int b = shared.get();
~~~

如果多个线程共享同一个结果，需要确保结果类型和具体访问方式不会引入额外的数据竞争。shared_future 的共享状态同步不等于它返回的对象可以被任意线程无同步修改。

### 9. std::thread 与 future 的区别

`std::thread` 主要管理线程执行实体的生命周期；`std::future` 主要管理异步结果的获取、等待和异常传播。

两者并非互斥选择。线程任务可以通过 promise/packaged_task 向 future 提供结果；`std::async` 则把异步工作与结果获取组合进一个高级接口。

## 十四、线程池的基本设计

### 1. 为什么需要线程池？

频繁为每个小任务创建和销毁线程，可能带来线程创建、调度和资源管理成本。

线程池通常：

1. 创建固定或可调整数量的工作线程。
2. 把新任务放入受保护的任务队列。
3. 工作线程等待队列非空。
4. 取出任务后解锁，在锁外执行任务。
5. 通过约定的关闭协议停止接收任务、唤醒线程并 join。

线程池适合大量相对独立的任务，但不意味着所有任务都应尽可能拆成极小的单元。

### 2. 线程池核心状态

常见设计包含：

~~~cpp
std::vector<std::thread> workers;
std::queue<std::function<void()>> tasks;
std::mutex mutex;
std::condition_variable condition;
bool stopping = false;
~~~

其中：

- `workers` 管理线程。
- `tasks` 保存待执行任务。
- `mutex` 保护队列和停止状态。
- `condition` 让空闲线程等待任务或关闭事件。
- `stopping` 参与关闭协议。

**注意：** `stopping` 可以是普通 bool，只要它的所有相互冲突访问都正确地由同一互斥锁保护；不需要因为它“被多个线程使用”就机械地改成 atomic。

### 3. 线程池工作线程的典型循环

~~~cpp
void WorkerLoop()
{
    for (;;) {
        std::function<void()> task;

        {
            std::unique_lock<std::mutex> lock(mutex);

            condition.wait(lock, [this] {
                return stopping || !tasks.empty();
            });

            if (stopping && tasks.empty()) {
                return;
            }

            task = std::move(tasks.front());
            tasks.pop();
        }

        task(); // 在锁外执行任务
    }
}
~~~

这里假定代码是线程池成员函数，`mutex`、`condition`、`tasks`、`stopping` 均是成员变量。示例展示 worker 核心逻辑，不是独立完整的线程池类。

如果任务直接抛出异常而没有被处理，异常一旦逃出工作线程的入口函数，会调用 `std::terminate`。实际线程池应定义任务异常处理策略，例如通过 packaged_task 保存异常到 future，或在工作线程的合适层次捕获并记录异常。

### 4. 为什么线程池需要停止协议？

如果析构线程池时仍有工作线程在等待队列，直接销毁队列、互斥锁或条件变量会造成严重生命周期问题。

典型关闭流程：

1. 在锁保护下标记停止并禁止新任务提交。
2. `notify_all()` 唤醒等待的工作线程。
3. 工作线程按照协议处理剩余任务或立即退出。
4. 管理者 join 所有工作线程。
5. 确认没有线程再访问队列、锁和条件变量后，销毁相关对象。

需要明确业务策略：**优雅关闭（drain）**是处理完已提交任务再退出，还是**立即停止**并丢弃待执行任务。这两种语义不能模糊混用。

### 5. 如何让提交任务返回 future？

常见思路是用 `std::packaged_task` 包装任务，再把可以执行它的闭包提交给工作队列。

~~~cpp
using Result = int;

auto packaged = std::make_shared<std::packaged_task<Result()>>(
    [] { return 42; });

std::future<Result> future = packaged->get_future();

// 任务队列可保存这个可复制的闭包：
std::function<void()> queued = [packaged] {
    (*packaged)();
};
~~~

由于 packaged_task 本身是仅可移动的，C++11/14 的 `std::function` 通常需要可复制的目标对象，使用 `shared_ptr` 承载 packaged_task 是常见解决思路之一。

### 6. 线程池有哪些常见难点？

- 任务队列是否有容量上限？
- 任务提交速度大于处理速度时如何限流或拒绝？
- 是否支持优先级与任务取消？
- 是否有长期阻塞任务？
- 线程池中任务互相等待，会不会发生饥饿或死锁？
- 工作线程异常怎样报告给提交方？
- 析构和提交任务并发时怎样定义对象生命周期与接口约束？
- 如何统计等待时间、执行时间和队列深度？

线程池并不是“把 vector<thread> 和 queue 写在一个类里就完成了”。正确的停止、所有权、背压和任务依赖设计同样重要。

## 十五、C++20：jthread、stop_token 和原子等待

### 1. std::jthread 与 std::thread 的区别

C++20 引入 `std::jthread`，更方便地管理线程退出：

~~~cpp
#include <thread>

void Run()
{
    std::jthread worker([] {
        DoWork();
    });
} // 析构时，若 joinable，jthread 请求停止并 join
~~~

与 `std::thread` 不同，`jthread` 的析构在仍关联线程时会按其规则请求停止并等待线程结束，降低忘记 join 的风险。

但如果线程无法结束，析构仍可能长时间阻塞。不能认为它能强制杀死线程。

### 2. stop_token 是什么？

`std::stop_token` 表达可协作查询的停止请求：

~~~cpp
#include <thread>

std::jthread worker([](std::stop_token token) {
    while (!token.stop_requested()) {
        DoOneIteration();
    }
});
~~~

停止是**协作式**的。任务需要主动检查停止标志或使用支持停止通知的等待机制，才会响应停止请求。

### 3. 原子等待与通知（C++20）

C++20 为原子对象提供 `wait()`、`notify_one()`、`notify_all()` 等机制，可在某些场景避免手写自旋轮询。

~~~cpp
std::atomic<int> state{0};

// 等待方
state.wait(0); // 当值仍等于 0 时可阻塞等待状态变化

// 通知方
state.store(1);
state.notify_one();
~~~

实际代码需要完整的共享状态设计和生命周期约束。原子等待与条件变量一样，不是“通知必然被永久记住”的魔法机制：要根据状态变化本身判断是否可以继续执行。

### 4. 协程是不是线程？

不是。

C++20 协程是可以暂停、恢复执行的语言机制，不等于创建一个新的 OS 线程。协程是否跨线程恢复、由谁调度，取决于库和调度器设计。

面试不要把“异步”“多线程”“并行”“协程”当成同义词。

## 十六、工程实践与性能排查

### 1. 多线程一定比单线程快吗？

不一定。多线程可能产生：

- 线程创建与切换开销。
- 锁争用和等待。
- 缓存一致性流量。
- 原子操作竞争。
- 任务拆分和调度开销。
- 内存带宽瓶颈。
- 负载不均衡。

对于小任务、顺序依赖强或资源竞争大的工作，多线程甚至可能更慢。

### 2. 什么是线程过度订阅（Oversubscription）？

当可运行线程数远超机器当下可以有效并行执行的处理资源时，系统可能花费过多时间在调度和上下文切换上。

如果任务主要等待 I/O，合理线程数可能与 CPU 密集型任务不同。线程池大小需要结合工作性质、硬件环境和性能测量决定。

### 3. 如何减小锁竞争？

常见思路：

- 缩短锁持有时间。
- 在锁外执行耗时任务。
- 减少共享可变状态。
- 采用线程本地缓冲和批量提交。
- 对独立数据进行合理分片。
- 适当使用读写锁。
- 使用专门的并发容器或队列（在其契约适用时）。
- 用真实数据确认争用瓶颈。

不要未经测量就把所有 mutex 替换成 atomic/CAS。

### 4. 什么是 ThreadSanitizer？

ThreadSanitizer（TSan）是一些编译器工具链提供的线程相关运行期检测器，可帮助发现数据竞争等并发错误。

在支持的 GCC/Clang 环境中，常见编译选项为：

~~~bash
g++ -std=c++14 -g -O1 -fsanitize=thread -pthread main.cpp -o app
~~~

TSan 依赖平台、运行环境和工具链支持；无法保证找出所有竞态、死锁或逻辑错误，也不能代替对同步关系的分析。

### 5. -pthread 的作用是什么？

在部分 GCC/Clang 及类 Unix 工具链中，`-pthread` 会同时影响编译和链接时线程相关选项，是常见的线程程序构建参数。

它不是 ISO C++ 标准规定的统一编译选项；Windows/MSVC 和其他平台使用不同构建方式。

### 6. 如何测试并发程序？

- 使用足够多的线程和重复执行扩大交错覆盖。
- 用 TSan 等工具检测数据竞争。
- 用有意义的断言验证状态不变量。
- 设计超时与死锁检测方案。
- 记录线程、任务和状态变化的关键事件。
- 用压力测试覆盖任务突发、停止、超时和异常路径。
- 在不同编译优化配置下测试，但不要依赖“重复运行一万次都没错”证明正确性。

并发 bug 可能只在特定调度和硬件状态下出现。测试只能提高发现概率，关键正确性仍依赖设计和同步推理。

## 十七、C++ 多线程高频面试题

### Q1：并发与并行的区别？

并发是多个任务在时间上交错或共同推进；并行是多个任务在同一时刻实际执行。单核心上可以并发而不并行。

### Q2：竞态条件和数据竞争的区别？

竞态条件是结果依赖线程执行交错的广义问题；数据竞争是 C++ 内存模型定义的无适当同步的冲突访问，属于未定义行为。没有数据竞争也可能有逻辑竞态。

### Q3：std::thread 为什么必须 join 或 detach？

`std::thread` 析构时若仍 joinable，会调用 `std::terminate`。创建线程后必须明确管理线程执行实体与对象生命周期。

### Q4：joinable() 代表线程一定正在运行吗？

不代表。线程函数可能已经结束，但如果线程对象尚未 join/detach，它仍可能是 joinable。

### Q5：lock_guard 和 unique_lock 的区别？

lock_guard 适合简单作用域内自动加锁/解锁；unique_lock 可移动、可延迟获取、可主动解锁再加锁，并可用于 condition_variable::wait。

### Q6：什么是死锁？如何避免？

多个线程因等待彼此持有的资源无法前进。可统一锁顺序、减少嵌套、使用 std::lock 或 C++17 scoped_lock，以及重新设计资源依赖。

### Q7：condition_variable 为什么要配合 while 或谓词？

因为可能虚假唤醒，而且通知本身不等于业务状态已经满足。等待线程醒来后必须重新检查受保护的条件。

### Q8：notify_one 和 notify_all 的区别？

前者通知一个等待线程，后者通知所有等待线程；要根据队列、停止状态和条件变化决定。通知只是提示，真正的状态仍由受同步保护的数据记录。

### Q9：atomic 与 mutex 有什么区别？

atomic 适合对单个原子对象执行定义明确的原子操作；mutex 更适合保护多个对象组成的临界区和不变量。atomic 不保证整个业务事务自动线程安全。

### Q10：为什么 volatile 不能实现线程同步？

volatile 不提供原子性，也不会在 C++ 内存模型中建立线程间同步关系。多线程共享数据应使用 atomic、mutex 等机制。

### Q11：CAS 的 expected 为什么会变化？

比较失败时，compare_exchange 操作会把观察到的原子对象当前值写回 expected，让调用者能根据新值决定是否重试。

### Q12：compare_exchange_weak 和 strong 的区别？

weak 允许伪失败，适合循环重试；strong 不允许伪失败，适合需要单次尝试语义的情况。二者都可能因实际值不匹配而失败。

### Q13：memory_order_relaxed 可以用来发布普通数据吗？

不能单靠 relaxed store/load 建立普通数据的发布与获取同步。独立计数常可以使用 relaxed；发布普通数据通常需要正确配对的 release/acquire 或锁。

### Q14：release/acquire 怎样建立同步？

当 acquire 读取到相应 release 操作（或符合规则的 release sequence）发布的值时，两者之间形成同步，发布前的写入可以按 happens-before 关系对获取方可见。

### Q15：seq_cst 和 acquire/release 一样吗？

不一样。seq_cst 有额外的统一顺序约束，release/acquire 则主要在满足配对条件时建立同步关系。跨多个原子对象时，允许的执行结果可能不同。

### Q16：什么是 happens-before？

它是 C++ 内存模型中的顺序与可见性关系，可由线程内顺序和跨线程同步及其传递性建立，用于推理何时可以合法、安全地观察写入。

### Q17：无锁算法一定更快吗？

不一定。CAS 重试、缓存行竞争、ABA、内存回收等可能造成高昂成本。性能应基于真实负载测量，而不是仅凭“无锁”二字。

### Q18：什么是假共享？

不同线程访问不同变量，但变量位于同一缓存行，缓存一致性协议导致额外竞争与性能下降。通常是性能问题，不等于语言层面的数据竞争。

### Q19：std::async 一定创建新线程吗？

不一定。默认策略可能选择异步或延迟执行。需要特定异步行为时应显式选择策略，并了解 future 生命周期与异常传播语义。

### Q20：future、promise、packaged_task 分别做什么？

future 用于等待和读取异步结果；promise 用于设置结果或异常；packaged_task 把可调用对象的执行结果或异常连接到 future 共享状态。

### Q21：线程池为什么要用条件变量？

当没有任务时让工作线程等待，而不是持续自旋轮询；任务到来或停止时通过通知唤醒。条件变量应与受锁保护的队列和状态谓词配合。

### Q22：线程池析构时最关键的步骤是什么？

定义清楚关闭协议：禁止新提交、设置停止状态、唤醒等待线程、按照约定处理剩余任务、join 所有线程，最后再销毁共享状态。

### Q23：std::jthread 的优势是什么？

C++20 的 jthread 在析构时能按规则请求停止并 join，减少忘记管理线程生命周期的风险。但停止是协作式的，不会强行结束不可中断的线程。

### Q24：协程等于多线程吗？

不是。协程是可暂停/恢复的控制流抽象，不自动创建 OS 线程。是否并行执行、在哪个线程恢复，由具体调度器和运行时决定。
