## 一、什么是 Texture 和 Sampler？

### 1. 为什么实时渲染需要 Texture？

Texture 可以看作通过坐标访问的离散数据集合，最常见的是 2D 图像，但也可能存放法线、粗糙度、深度、查找表、体素或其他任意渲染数据。

使用纹理可以将细节从几何表示中分离：一块粗糙的网格表面可以通过 Albedo、Normal、Roughness 等贴图提供高频材质变化，不必把每个图案都建成三角形。

**不要把纹理等同于“彩色 PNG 图片”。** 图片文件是资产来源之一，GPU 纹理则包含存储格式、维度、Mipmap、采样约束及可能的压缩布局。

### 2. Texture、Texture View、Sampler 分别是什么？

| 概念 | 描述 | 典型属性 |
|---|---|---|
| Texture Resource | GPU 中存放纹素的数据资源 | 维度、分辨率、格式、Mip、Layer、Usage |
| Texture View | 对资源的某一范围/格式解释建立访问视图 | Mip Range、Layer、可兼容格式 |
| Sampler | 如何依据坐标获取样本值的状态 | Filter、Address/Wrap、LOD Bias、Anisotropy、Compare |
| Sample | 执行采样操作后得到的值 | 可能涉及寻址、LOD、多个 Texel 与过滤 |

OpenGL 可使用 Texture Object 与 Sampler Object；D3D/Vulkan 等 API 通常有相应资源/视图/采样器概念，但对象与绑定方式不同。

### 3. Texel 和 Pixel 有什么区别？

- **Texel：** 纹理存储中的一个离散数据元素。
- **Pixel：** 帧缓冲或图像目标中的一个像素位置。
- **Texture Sample：** 经过地址计算与过滤的结果，可能综合多个 Texel。
- **Fragment：** 光栅化产生的候选片元，不等价于一个屏幕 Pixel 或一个 Texel。

**面试易错点：** 一个像素对应的纹理 Footprint 可以覆盖一个、多个甚至数百个 Texel，并非“一个 Fragment 固定读一个 Texel”。

### 4. 常见纹理种类有哪些？

| 种类 | 典型用途 | 主要特点 |
|---|---|---|
| Texture2D | 大部分表面贴图、屏幕缓冲 | 2D 坐标 |
| Texture2DArray | Layer 化贴图、Shadow Cascade 等 | Layer 是离散选择，通常不跨 Layer 插值 |
| Cubemap | 环境图、反射、点光阴影 | 方向向量决定 Face 和坐标 |
| Texture3D | 体数据、体积噪声、LUT | 三维 Texel 与三线性空间插值 |
| Depth Texture / Comparison Sampler | 阴影比较、深度效果 | 可能返回深度比较/PCF 结果 |
| Multisample Texture | MSAA 数据 | 按 Sample Index 获取，不是普通 Mipmap 采样 |
| Buffer Texture | 通过纹理访问大块缓冲数据 | 没有常规 2D UV 过滤语义 |

### 5. 纹理坐标为什么经常使用 UV，而不是屏幕像素坐标？

UV 是映射在几何表面上的参数化坐标，通常由模型制作和导入流程决定；屏幕坐标则会随着相机位置变化。

Fragment Shader 收到的 UV 一般已经过**透视校正插值**。之后 Sampler 用当前 UV、纹理尺寸、寻址规则和 LOD 决定需要访问哪些 Texel。

## 二、UV、Texel Center 与寻址模式

### 1. 归一化 UV 如何对应 Texel？

一张宽 `W`、高 `H` 的 2D 纹理，第 `i,j` 个 Texel 的中心可以写成：

```math
u_i=\frac{i+0.5}{W},\qquad
v_j=\frac{j+0.5}{H}.
```

这里的 `v` 只是数学坐标；图像文件的第一行位于上方还是下方，需要与上传和 Shader 约定对应。

**易错点：** `u=0` 对应纹理边界，不必恰好是第一个 Texel 中心。使用线性过滤时，纹理边界处的结果与 Wrap/Clamp State 有关。

### 2. Repeat、Mirrored Repeat、Clamp to Edge、Clamp to Border 怎么区分？

| Address Mode | 超出坐标范围时 | 典型用途 |
|---|---|---|
| Repeat | 对 UV 取周期重复 | 地表、墙砖等平铺纹理 |
| Mirrored Repeat | 交替镜像重复 | 减轻连续拼接方向性 |
| Clamp to Edge | 使用边缘 Texel 延伸 | UI、LUT、非平铺贴图 |
| Clamp to Border | 返回/插值到边界颜色（支持情况依 API） | 某些阴影或特殊边界处理 |

例如 `u=1.25` 在 Repeat 下的周期坐标与 `0.25` 相同；在 Clamp to Edge 下靠近最右边界。

### 3. 为什么 Wrap Mode 还会影响双线性采样？

双线性采样可能访问当前 Texel 中心两侧的邻居。当 UV 靠近边缘时，需要决定“边缘外的 Texel”是从另一端循环、边缘复制还是边框值获得。

因此一张贴图产生边缘缝隙不一定因为 UV 错，可能是 Sampler State 或 Atlas Padding 出问题。

### 4. 为什么纹理 Atlas 容易出现颜色串边（Bleeding）？

Atlas 把多个子贴图放入同一大纹理，双线性过滤或 Mipmap 生成会使一个区域的采样 Footprint 跨越到邻居区域。

常见处理：

1. 在每个子图四周做合理的 Extruded Padding/Gutter。
2. 在生成 Mipmap 时对 Atlas Border 进行专门处理。
3. 对超出子区域的采样 UV 施加边界约束（但要小心导数）。
4. 对大量重复独立纹理，可以考虑 Texture Array 而不是 Atlas。

### 5. UV Seam 与 Texture Seam 是一样的问题吗？

UV Seam 是模型的参数化切口，通常导致同一世界位置对应不同 UV；Texture Seam 是最终可见接缝，可能由 UV、切线空间、纹理颜色、Mipmap、Wrap 或压缩误差共同造成。

所以 UV Seam 并不一定可见；可见的接缝也不一定都由 UV Seam 引起。

## 三、Nearest 与 Bilinear Filtering

### 1. Nearest Sampling 的原理是什么？

把纹理坐标映射到离散 Texel 网格，选择距离最近的 Texel 值。成本低、保持像素块边界，但纹理放大后容易出现明显的马赛克。

典型用途是像素风、索引/ID 纹理或要求精确离散取值的数据采样。

### 2. Bilinear Filtering 为什么要读取四个 Texel？

在 2D 纹理网格中，待采样点通常位于四个邻近 Texel 中心围成的矩形内部。根据水平和垂直方向的相对位置插值得到平滑结果。

假设四个点值为 `C00、C10、C01、C11`，水平方向权重 `t`、垂直方向权重 `s`：

```math
\boxed{
C(t,s)=
(1-t)(1-s)C_{00}
+t(1-s)C_{10}
+(1-t)sC_{01}
+tsC_{11}.
}
```

也可以先做两次水平 Lerp，再做一次垂直 Lerp：

```math
C_0=(1-t)C_{00}+tC_{10},
```

```math
C_1=(1-t)C_{01}+tC_{11},
\qquad
C=(1-s)C_0+sC_1.
```

### 3. 双线性过滤会“凭空产生”细节吗？

不会。它在离散样本之间做插值，表现为局部平滑，不能恢复未被纹理分辨率捕获的高频信息。放大纹理时它通常比 Nearest 更平滑，但也更模糊。

### 4. Bilinear 和 Bicubic Filtering 有什么区别？

- Bilinear 使用常见的 2×2 邻域。
- Bicubic 一般使用更大的邻域（常见 4×4），通过三次函数插值获得更平滑、不同锐度的结果。
- Bicubic 不等于硬件默认的 `GL_LINEAR`；通常要额外 Shader 处理或特殊采样技巧。

不同三次插值核还可能带来过冲、振铃和额外采样成本。

### 5. 为什么使用线性过滤不能解决远处纹理闪烁？

Bilinear 在**单个 Mip Level 内**过滤局部 Texel。物体很远时，一个屏幕像素的纹理 Footprint 可能覆盖几十、几百个基础级别 Texel，仅过滤四个邻居远远不足以抑制高频信号。

这需要从采样理论解释，也正是 Mipmap 的重要动机。

## 四、纹理走样、采样理论和 Footprint

### 1. Texture Aliasing 的本质是什么？

纹理是一种离散信号。把高频纹理映射到有限像素网格时，若经过映射后的信号频率超过当前采样率可表达的范围，就可能产生：

- 远处棋盘格闪烁或摩尔纹。
- Camera Motion 时不稳定的细条纹。
- 强烈斜视角下的模糊与闪烁。
- 镜面/法线贴图导致的高光噪声。

**采样不足不是简单“纹理分辨率不够”**；过于清晰的高频纹理在远距离反而更容易 Aliasing。

### 2. Nyquist 采样定理对纹理意味着什么？

对一维理想带限信号，若最高频率为 `f_max`，采样频率必须高于其两倍，才能在满足相应条件下避免频率混叠并重建信号。

实际 GPU 的像素采样、透视投影、离散纹理、过滤核、非带限材质都比一维理想模型复杂；核心结论是：

**在降低采样分辨率之前，应先低通滤波，抑制当前像素无法表达的高频信息。**

### 3. 什么是 Texture Footprint？

把屏幕上的一个 Pixel（或某个 Sample 及其微分邻域）映射到 UV 空间，得到它在纹理上对应的一片区域，这片区域就是 Texture Footprint。

它通常不是一个点，也并不总是轴对齐正方形：斜视角、透视、UV 拉伸或不同方向的缩放，都会使 Footprint 形状发生变化。

### 4. Minification 和 Magnification 如何区分？

- **Magnification：** 屏幕采样比基础纹理 Texel 更密，一个纹素会被放大到多个像素。
- **Minification：** 一个屏幕像素覆盖多个基础纹素，需要抑制高频以避免混叠。

对应 OpenGL 常见的 `GL_TEXTURE_MAG_FILTER` 和 `GL_TEXTURE_MIN_FILTER`。注意一个三角形或甚至一个区域内，不同方向可能同时有放大与缩小特征；这种情况也揭示了各向异性过滤的必要性。

## 五、Mipmap：预过滤的多级纹理

### 1. Mipmap 是什么？

Mipmap 将基础纹理沿尺寸逐级缩小，形成多个过滤后的 Level：

~~~text
Level 0: 1024 × 1024
Level 1:  512 × 512
Level 2:  256 × 256
Level 3:  128 × 128
...
Level 10:   1 × 1
~~~

理想上，每一级代表对应采样分辨率下的**预过滤信号**。运行时不必每个像素都从最高分辨率遍历大量 Texel，而是选择尺寸合适的 Mip。

### 2. 一张纹理共有多少个 Mip Level？

对正尺寸 2D 纹理 `W×H`，一直缩小到 `1×1`：

```math
\boxed{
L=1+\left\lfloor
\log_2\big(\max(W,H)\big)
\right\rfloor.
}
```

例如 `1024×1024` 有 11 级（包含 Level 0），`1000×500` 在常规向下取整规则下也具有完整 Mip Chain，只是每一级尺寸未必都是二的幂。

### 3. Mipmap 为什么常说只增加约三分之一显存？

对于宽高都是二的幂、完整 2D Mip Chain，且不考虑行对齐和压缩块边界：

```math
S_{\mathrm{total}}
=WH\left(1+\frac14+\frac1{16}+\cdots\right)
<\frac43 WH.
```

相对于不含 Mipmap 的 Level 0，额外 Texel 数量接近 `1/3`。它不是所有贴图的固定精确值：NPOT、压缩 Block Alignment、Array Layer、Cubemap 和具体分配策略可能改变实际字节开销。

### 4. Mipmap 和降低原图分辨率有什么区别？

如果直接把原图永久缩到 256×256，近距离观察将失去原本 1024×1024 的细节；Mipmap 同时保留高分辨率和多个低分辨率版本，采样时按 Footprint 选择。

Mipmap 的核心目标是 **Minification Filtering**，不仅仅是“提升性能”。

### 5. Mipmap 通常怎么生成？

可以从上一层做 2×2 Box Average，也可以使用质量更好的低通核。

简单 Box 近似：

```math
C_{k+1}(i,j)=\frac14
\sum_{a=0}^{1}\sum_{b=0}^{1}
C_k(2i+a,2j+b).
```

上式适用于规则 2× 缩小且索引有效的简单情况。高质量生成器还应考虑 Gamma、Alpha Coverage、Normal Renormalization、不同尺寸、Seam 与滤波核形状。

### 6. 为什么 Mipmap 不是完美的纹理抗锯齿？

常见 Mip Level 假设在 UV 两个方向做较为相似的降采样；真实投影 Footprint 可能是倾斜的长椭圆。仅按一个标量 LOD 选择 Mip，可能让一个方向欠采样、另一个方向过度模糊。

因此斜视角表面通常需要 Anisotropic Filtering。

## 六、LOD：GPU 到底选择哪一级 Mipmap？

### 1. 什么是 Texture LOD（Level of Detail）？

LOD 是描述本次采样需要哪一级 Mipmap 的连续值：

- `LOD≈0`：使用基础级别纹理。
- `LOD≈1`：采样一个像素的 Footprint 大致对应基础纹理中 2 倍线性尺寸。
- `LOD≈2`：大致对应 4 倍线性尺寸。
- 非整数 LOD 可以在相邻 Mip Level 间过滤。

实际 LOD 还受到 Shader 显式采样指令、LOD Bias、Min/Max LOD、纹理视图可见级别、Anisotropy、Sampler State 的影响。

### 2. GPU 为什么需要 ddx、ddy（dFdx、dFdy）？

纹理坐标经透视校正后，在每个 Fragment 的值通常与邻近像素不同。

GPU 可以估计：

- `du/dx、dv/dx`：屏幕水平方向移动一像素对应的 UV 变化。
- `du/dy、dv/dy`：屏幕垂直方向移动一像素对应的 UV 变化。

GLSL 中对应 `dFdx`、`dFdy`，HLSL 中通常称 `ddx`、`ddy`。它们是屏幕空间的**局部有限差分估计**，不是一般解析微分公式的精确实现。

### 3. 经典的 Isotropic LOD 公式如何推导？

先将归一化 UV 导数转为以基础纹理 Texel 为单位的变化向量：

```math
\mathbf g_x=
\left(
W\frac{\partial u}{\partial x},
H\frac{\partial v}{\partial x}
\right),
\qquad
\mathbf g_y=
\left(
W\frac{\partial u}{\partial y},
H\frac{\partial v}{\partial y}
\right).
```

一个常见各向同性近似使用最大方向变化量：

```math
\rho=\max\big(\|\mathbf g_x\|,\|\mathbf g_y\|\big).
```

于是：

```math
\boxed{
\lambda=\log_2\rho.
}
```

如果 `ρ=1`，大约选择 Mip 0；`ρ=2`，大约 Mip 1；`ρ=4`，大约 Mip 2。

**重要限定：** 这是最常见、便于面试推导的 LOD 近似；不同 API 的纹理函数、采样器和 GPU 可能使用其他允许的微分/LOD 规则。实际 LOD 还会被 Bias 与 Min/Max LOD 修正，并受完整纹理状态约束。

### 4. 为什么一定要把 UV 导数乘以纹理尺寸？

UV 是归一化坐标。同样的 `Δu=0.01`，在 128 宽的纹理中对应约 1.28 个 Texel，而在 4096 宽的纹理中对应约 40.96 个 Texel。

没有乘 `W,H`，就无法正确表示同一个屏幕像素覆盖的基础纹理 Texel 数量。

### 5. LOD 的数值练习

设纹理为 `1024×1024`，UV 的屏幕导数为：

~~~text
dUVdx = (0.004, 0)
dUVdy = (0, 0.002)
~~~

则：

```math
\rho_x=1024\times0.004=4.096,
\qquad
\rho_y=1024\times0.002=2.048.
```

```math
\lambda=\log_2(4.096)\approx2.034.
```

各向同性过滤会选择约 Mip 2 附近的预过滤数据。

### 6. 为什么 dFdx/dFdy 与 2×2 Quad 有关？

实际 GPU 经常按相邻片元的 Quad 估算导数；几何边缘等处即使某些像素不真正写入渲染目标，仍可能产生 Helper Invocation 以供导数计算。

**动态不一致控制流**中的隐式导数可能不受规范保证。若不同 Lane 执行不同纹理采样路径，可能需要在分支前计算导数，或使用 `textureGrad` 等显式梯度操作。

### 7. 为什么 Texture LOD 不能简单等同于物体距离？

物体距离影响投影 Footprint，但并不是唯一因素。还包括：

- 视角和投影拉伸。
- UV 在模型上的缩放程度。
- 纹理本身的分辨率。
- Surface Orientation。
- 显式 LOD/Bias、Texture Streaming。
- Dynamic Resolution、屏幕空间导数。

近处斜视地面也可能需要低分辨率 Mip，而远处某个高 UV 缩放细节仍可能需要特殊处理。

## 七、Trilinear Filtering 与 LOD Bias

### 1. Trilinear Filtering 是什么？

在两个相邻 Mip Level 内分别进行 Bilinear，再按照 LOD 的小数部分在两个结果之间线性插值。

令 `k = floor(λ)`，`t=λ-k`，那么：

```math
\boxed{
C=(1-t)\,C_k(u,v)+t\,C_{k+1}(u,v).
}
```

其中 `C_k`、`C_{k+1}` 表示相应 Mip 上的 Bilinear Sample。

常说“三线性需要 8 个 Texel”，指典型 2D、两个 Mip 各 4 个 Texel 的概念模型；GPU 实际访存、Cache、格式和实现可能不同。

### 2. Bilinear、Trilinear 和 Mipmap 是什么关系？

- Bilinear：在同一层空间上插值。
- Mipmap：提供不同采样分辨率的预过滤层。
- Trilinear：同时在两层 Mip 内进行 Bilinear，并在两个结果之间插值。

因此“Trilinear 是 3D 纹理插值”与“2D 纹理的 Mipmap Trilinear”是语境不同的两个概念。3D Texture 的单级三线性空间过滤也可能访问八个空间邻居，不能混淆两者。

### 3. 为什么单独用 Nearest Mip 会出现 Mip Banding？

当 LOD 穿过整数边界，采样级别突然切换，两个 Mip 的细节/颜色可能不完全相同，于是出现明显的同心“Mip 分界线”。

Trilinear 可以让相邻级别之间平滑过渡，但会增加过滤量，也不能解决所有高角度各向异性问题。

### 4. LOD Bias 如何影响画面？

常见偏移思路：

```math
\lambda_{\mathrm{biased}}=\lambda+b.
```

- `b>0`：采样更粗的 Mip，通常更模糊，但可能更稳定。
- `b<0`：采样更细的 Mip，通常更锐利，但更容易纹理闪烁。

盲目使用大幅 Negative LOD Bias 会加重 Aliasing，而不是免费提升纹理细节。

### 5. Min Filter 和 Mag Filter 为什么状态不同？

Magnification 不需要按大 Footprint 选多个降采样 Mip；Minification 则需要选择合适 LOD。

OpenGL 中 `GL_TEXTURE_MAG_FILTER` 只支持 Nearest/Linear 等适用的放大过滤状态，而 `GL_TEXTURE_MIN_FILTER` 还可以设置 Mipmap 组合（如 `GL_LINEAR_MIPMAP_LINEAR`）。

## 八、Anisotropic Filtering：斜视角的关键

### 1. 各向同性过滤有什么问题？

视角倾斜或 UV 变换拉伸时，一个屏幕像素对应纹理空间的 Footprint 可能是**狭长椭圆**，而不是圆形或正方形。

选取能覆盖长轴的低分辨率 Mip 会使短轴方向过度模糊；选高分辨率 Mip 又可能让长轴方向走样。

### 2. Anisotropic Filtering 主要解决什么？

它根据 Footprint 长短轴差异，在长轴方向采用更多样本/更合适的过滤，尽量在减少走样的同时保留短轴方向细节。

典型效果：地板延伸到远处时，Anisotropic 纹理比单纯 Trilinear 更清晰。

### 3. 如何用 Jacobian 理解 Footprint 的方向性？

定义屏幕坐标到**纹理 Texel 坐标**的局部 Jacobian：

```math
J=
\begin{bmatrix}
W\,\frac{\partial u}{\partial x} &
W\,\frac{\partial u}{\partial y}\\
H\,\frac{\partial v}{\partial x} &
H\,\frac{\partial v}{\partial y}
\end{bmatrix}.
```

J 的奇异值 `σ_max`、`σ_min` 分别描述单位圆在局部映射下拉伸的长短轴量级，因此理想化的各向异性比值可理解为：

```math
\boxed{
A\approx\frac{\sigma_{\max}}{\sigma_{\min}}.
}
```

当 `σ_min` 很小，应通过适当阈值与硬件上限避免比值发散。

**细节：** 简单的 `max(‖g_x‖,‖g_y‖) / min(‖g_x‖,‖g_y‖)` 仅是粗略启发式，并不总与 Jacobian 奇异值比相等；在旋转或剪切的足迹上尤其如此。

### 4. Anisotropy 16× 是什么意思？

通常表示请求硬件允许的最大各向异性过滤程度，例如 4×、8×、16×。它不是“每个 Texture Sample 必定恰好读取 16 个 Texel”，也不是“纹理分辨率变成 16 倍”。

硬件实现、实际样本数、过滤核和性能开销依厂商与驱动而不同。

### 5. 为什么各向异性过滤也不能完全消除闪烁？

它处理的是纹理过滤中足迹各向异性的一部分问题。Shader Aliasing、过高频法线、Alpha-Test 边缘、运动相关的时间混叠等仍需要其他处理。

## 九、sRGB、Linear RGB 与数据纹理

### 1. 为什么 Albedo 通常需要标记为 sRGB？

绝大多数面向显示的颜色图片文件存储的是经过 sRGB Transfer Function 编码的数值，而光照积分、混合和材质计算需要在线性空间内操作。

因此典型路径为：

~~~text
Albedo PNG / TGA 等源素材（往往使用 sRGB 编码）
                       |
                       v
              sRGB Texture Format
                       |
                       v
   GPU Texture Sampling -> sRGB Decode -> Linear RGB
                       |
                       v
                   Lighting
                       |
                       v
       Tone Mapping / Display Encoding
~~~

**不能简单说“所有 PNG 都一定是 sRGB”。** 实际资产还要依据颜色配置、嵌入 Profile 与内容约定判断。

### 2. sRGB 解码的准确分段公式是什么？

对归一化 sRGB 编码通道 `c_s`，解码成 Linear RGB 通道 `c_l`：

```math
c_l=
\begin{cases}
c_s/12.92, & c_s\le 0.04045,\\[4pt]
\left(\frac{c_s+0.055}{1.055}\right)^{2.4},
& c_s>0.04045.
\end{cases}
```

反向编码：

```math
c_s=
\begin{cases}
12.92c_l,& c_l\le0.0031308,\\[4pt]
1.055c_l^{1/2.4}-0.055,&c_l>0.0031308.
\end{cases}
```

`pow(c, 2.2)` 只是常见粗略近似，不是严格的 sRGB Transfer Function。

### 3. sRGB 与 Gamma 2.2 是一回事吗？

不是。sRGB 采用特定的分段 Transfer Function；纯 Gamma 2.2 是一条幂律曲线。两者在部分取值范围接近，但尤其在暗部有所差异。

面试中推荐说“sRGB 编码/解码”，不要笼统地把全部操作称为 Gamma Correction。

### 4. 为什么 Normal、Roughness、Metallic、AO 通常不能标成 sRGB？

这类贴图储存的多是**线性数据值或编码向量**，而不是面向显示的颜色亮度。

- Normal：RGB 往往编码单位法线分量，通常需要从 `[0,1]` 映射回 `[-1,1]`。
- Roughness/Metallic/AO：表示数值参数或比例，采样时应保持相应线性解释。
- Height、Mask、ID 等：属于数据纹理，应依据自身格式和插值需求处理。

如果粗糙度为 `0.5`，错误套用 sRGB 解码会得到约 `0.214`，材质表现会明显改变。

### 5. sRGB 纹理的 Alpha 通道也会做 sRGB Decode 吗？

典型 sRGB RGB(A) 纹理格式对 **RGB** 颜色通道应用 sRGB Decode，而 Alpha 通道保持线性数据解释，不应用同样的颜色 Transfer Function。

因此 sRGB RGBA 纹理里的 Alpha 通道常能用于线性 Coverage/Opacity，但依然需要考虑压缩和 Mipmap 的 Alpha 处理。

### 6. 为什么 Mipmap 应在正确颜色空间生成？

假设黑白两个 sRGB Texel 的编码值分别为 `0` 和 `1`。

如果直接对 sRGB 编码值平均得到 `0.5`，其解码后的线性亮度只有约 `0.214`；而在**线性空间**平均后得到的线性值应为 `0.5`，重新编码到 sRGB 约为 `0.735`。

因此直接对 sRGB 编码值做平均，可能使缩小后的纹理系统性偏暗。

**工程要求：** 明确 Mip Generator 的输入、处理与输出颜色空间。部分 API/工具的具体生成行为需验证，不能以“纹理格式是 sRGB”就断言所有离线压缩工具已经正确处理。

### 7. 为什么 sRGB Framebuffer 也会影响透明 Blending？

透明合成应尽量在 Linear RGB 中执行。对带正确 sRGB Framebuffer 支持与配置的渲染路径，硬件可能进行目标解码、混合和重新编码；但对普通 UNORM 目标不能想当然地认为它会自动进行正确颜色空间变换。

详细的 Straight/Premultiplied Alpha 和 Blend State 见第三篇文档。

## 十、法线、粗糙度、Alpha 与特殊贴图的过滤

### 1. Normal Map 为什么不能直接当成普通颜色？

典型 Tangent-Space Normal 贴图将法线编码到纹理通道：

```math
\mathbf n_{\mathrm{decoded}}=2\mathbf c-1.
```

采样后通常需要归一化：

~~~glsl
vec3 tangentNormal = texture(uNormalMap, vUV).xyz * 2.0 - 1.0;
tangentNormal = normalize(tangentNormal);
~~~

然后用一致的 TBN 基转换到所需光照空间。

### 2. 为什么对单位法线做线性平均后可能不再是单位长度？

两个单位向量的平均值一般长度小于等于 1；差异越大，结果长度通常越短。

例如：

~~~text
n0 = (1, 0, 0)
n1 = (0, 1, 0)
average = (0.5, 0.5, 0)
length ≈ 0.707
~~~

如果直接将平均后的向量当单位法线参与 BRDF，会得到错误光照。因此采样法线一般要重新 Normalize。

### 3. 为什么 Normal Map 的 Mipmap 还可能造成镜面闪烁？

仅把多个法线方向平均并归一化，可能丢失一个重要信息：**原来这一块表面有多大的法线方向变化方差**。

远处像素覆盖一片强烈起伏的微法线时，直接使用平均法线会产生过于锐利/不稳定的高光。常见解决思路包括 Toksvig、LEAN Mapping、Normal Variance/Specular Antialiasing 等，用局部法线分布信息调节有效粗糙度。

**PBR 高频关联：** 纹理走样不只发生在 Albedo，Normal Map 中的高频变化会通过 BRDF 转化成 Specular Aliasing。

### 4. Roughness 的 Mipmap 能直接取算术平均吗？

这取决于你希望在统计意义上保留什么材质属性，不能一概而论。GGX 分布常使用 `alpha = roughness²` 等参数映射（具体 BRDF 实现与引擎定义可能不同）。

简单平均 Roughness 不一定等价于平均 Microfacet Distribution；高质量 Material Filtering 可能需要对分布、法线方差和 BRDF 能量做特殊处理。

对入门引擎：先统一“纹理值 → BRDF 参数”的定义，再结合 Specular AA 分析需要的 Mip 策略。

### 5. Masked 贴图为什么 Mipmap 后树叶会变细甚至消失？

原始 Alpha Test 为二值覆盖，例如 `alpha > 0.5` 才保留 Sample。多个低分辨率 Texel 平均后，Alpha 数值可能跨过阈值，导致原本存在的小叶片被丢弃。

一种处理思路是**保持 Alpha Coverage**：生成各级 Mip 时调整 Alpha 分布，使在相同阈值下保留的覆盖比例尽量接近原始纹理。

但 Coverage Preservation 不是“简单地将所有 Alpha 乘相同常数”就总能完全正确；离散采样和复杂形状可能需要额外处理。

### 6. Normal、Height、ID 等数据纹理都适合 Linear Filtering 吗？

不一定：

| 贴图语义 | 常见策略 | 注意事项 |
|---|---|---|
| Albedo/Base Color | Linear + Mipmap，视角倾斜时 Anisotropic | sRGB Decode |
| Normal | Linear + Mipmap，采样后 Normalize | 特殊 Mip 与 Specular AA |
| Roughness/Metallic/AO | 按材质设计过滤 | 一般按线性数据解释 |
| ID / Material Index | Nearest 或整数 Fetch | 不能插值不同离散 ID |
| Height / Displacement | 依算法过滤 | Filtering 可能改变极值和轮廓 |
| Shadow Comparison | Comparison Sampler / PCF 语义 | 不等于直接颜色 Bilinear |

### 7. 为什么过滤整数纹理或 Texture Buffer 与普通颜色纹理不同？

整数 Sample Type（例如 `isampler2D`、`usampler2D`）常用于精确整数语义，不能套用浮点线性过滤；具体格式和过滤能力由 API 限制决定。

如果需要精确索引，应该使用匹配的整数格式、Fetch 和地址方式，而不是把 ID 当 RGB 颜色进行双线性平均。

## 十一、Texture Compression：BC、ASTC、ETC

### 1. 为什么游戏引擎大量使用 GPU 纹理压缩？

纹理可能占用大量显存和带宽。GPU 纹理压缩的目标通常是在**保持可直接采样**的前提下，让每块 Texel 以更少的存储字节表示。

不同于普通 ZIP/PNG 之类为磁盘传输准备的通用或无损编码，BC/ASTC 等适合 GPU 按固定 Block 访问、解码，并可配合硬件纹理缓存。

### 2. Block Compression 的基本原理是什么？

以常见 BC 格式为例，把纹理切成固定尺寸 Block（通常 4×4 Texel），用少量 Endpoint、Index 或其他编码参数近似这一块内的值。

纹理硬件可以按需取得对应 Block 并解码样本，通常不需要 CPU 事先把整张压缩纹理解码成 RGBA8 再上传。

注意不同格式的编码与解码细节差异很大，不能将 BC7、ASTC 统统概括为“存两端颜色加插值”。

### 3. 常见 BC 压缩格式怎么选？

| 格式 | 典型 Block 字节 | 有效 bpp | 常见用途 |
|---|---:|---:|---|
| BC1 | 4×4，8 Byte | 4 | RGB / 可选 1-bit Alpha |
| BC3 | 4×4，16 Byte | 8 | 带较连续 Alpha 的 LDR Color |
| BC4 | 4×4，8 Byte | 4 | 单通道 Mask/数据 |
| BC5 | 4×4，16 Byte | 8 | 双通道 Normal XY |
| BC6H | 4×4，16 Byte | 8 | HDR RGB |
| BC7 | 4×4，16 Byte | 8 | 高质量 LDR RGB/RGBA |

上表是常见的**压缩 Block 存储大小与理论 bpp**。小尺寸 Mip、对齐、硬件支持和资源封装还会影响总字节数。

### 4. 为什么 Normal Map 常使用 BC5？

Tangent-Space Normal 的 `X,Y` 分量可以存两通道，`Z` 可以在合理假设下重建：

```math
z=\sqrt{\max(0,1-x^2-y^2)}.
```

通常还要归一化并处理可能的负 Z/符号约定。BC5 对两个通道采用适合标量数据的压缩方式，往往比把 Normal Map 作为普通颜色纹理压缩更有利于保留方向精度。

**前提：** 这适合约定法线位于正半球的常见 Tangent-Space Normal。不能用它无条件表达任意正负 Z 法线。

### 5. ASTC 与 BC 的重要区别是什么？

ASTC 是更灵活的 Block Compression 家族，可以选择多种 Block Footprint（如 4×4、6×6、8×8、12×12）。常见 ASTC LDR 变体每块使用 128 bit（16 Byte），随 Block 面积变化获得不同 bpp。

例如：

| ASTC Block | Block 大小 | 有效 bpp |
|---|---:|---:|
| 4×4 | 128 bit | 8 |
| 6×6 | 128 bit | 约 3.56 |
| 8×8 | 128 bit | 2 |
| 12×12 | 128 bit | 约 0.89 |

Block 越大，压缩率越高，但并不保证质量始终可接受。实际画质取决于纹理内容、编码器、编码质量参数及硬件支持。

### 6. BC、ASTC、ETC2 是所有平台都支持吗？

不是。目标桌面 GPU、移动 GPU、图形 API、操作系统和资源创建方式都会限制可用格式。

典型项目会针对不同目标平台选择合适压缩方案并 Cook 对应平台资源。不能将桌面 BC7 纹理文件不经适配直接视为任何移动设备都可硬件采样的格式。

### 7. 为什么压缩会让贴图出现 Block Artifact 或色带？

在有限的 Block 码率内，只能近似表达原始 Texel 的信息；颜色梯度、非常尖锐的边缘、法线变化或 Alpha 细节都可能暴露压缩误差。

排查需要区分：

- Source Image 本身有无损坏。
- 压缩编码时引入的误差。
- Mip 生成后的误差。
- Sampler Filtering 造成的模糊或串边。
- CPU 解码与 GPU 硬件采样是否遵守相同格式与颜色空间。

### 8. 为什么“8 bpp 格式”与“实际每个像素占 1 字节”不能完全等价？

8 bpp 是压缩 Block 的平均率，例如一整个 4×4 Block 存 16 Byte；并不是每个 Texel 独立、可随机修改其中 1 Byte。

小纹理 Mip 仍可能要占至少一个完整 Block，纹理行对齐和整个 Mip Chain 也会影响总大小。

## 十二、纹理数据的生命周期：文件、Source、Cooked、GPU

### 1. 一张贴图从磁盘到屏幕经历哪些阶段？

一种典型的资产管线：

~~~text
Source Image (PNG/TGA/EXR/PSD 等)
                  |
                  v
Import / Source Art / Color Interpretation
                  |
                  v
Mip Generation / Normal & Alpha Processing
                  |
                  v
Texture Compression / Platform Cook / Derived Data
                  |
                  v
Storage / Asset Package / Streaming Data
                  |
                  v
CPU Read / Decode or Direct Upload Preparation
                  |
                  v
GPU Resource Creation + Transfer / Upload
                  |
                  v
GPU Texture + Sampler + Shader Sampling
~~~

不同引擎可能把处理放在编辑器、Cooker、运行时，或在不同平台生成不同版本；上图是一般工程流程，不是某个引擎所有版本的固定函数调用顺序。

### 2. Source Art、Cooked Mip 和 GPU Resident Texture 有什么区别？

| 概念 | 代表什么 | 是否必须与最终像素完全相同 |
|---|---|---|
| Source Art | 导入后的编辑器源图或高保真来源 | 不保证 |
| Cooked / Derived Mip Data | 经目标平台设置、缩放、压缩、Mip 生成的数据 | 不保证 |
| GPU Resident Texture | 当前真正驻留并被 GPU 采样的资源内容 | 可能仅包含部分 Mip/Tile |

Source Art 可能采用更高精度、不同通道布局或颜色编码；GPU 数据可能已被压缩、有 Mipmap、经过 Platform Cook 或当前只驻留部分资源。

### 3. 为什么 Editor 里显示的 Source 图像与 GPU Decoded 图像可能不同？

常见原因：

- Source 与平台 Cook 的分辨率/Mip 不同。
- BC/ASTC 等有损压缩带来误差。
- 正在显示某个选定的 Mip，而不是原始 Level。
- 通道重排、Normal Map 处理、Alpha 处理。
- sRGB 与 Linear 显示路径解释不同。
- Texture Streaming 使某些高分辨率 Mip 尚未驻留。
- GPU 回读发生格式转换，或预览 Shader 应用了额外颜色/显示处理。

**面试时必须区分“读取 GPU Texture 存储内容”与“预览 Shader 采样并输出后的图像”。** 两条路径的数据语义可能不同。

### 4. Unreal Engine 的 Texture Source 和 Platform Data 怎么理解？

在 UE 的相关编辑器/运行时概念里，可以把它们按职责理解为：

- **Texture Source：** 编辑器导入或保存的源数据，供重新构建和再压缩使用。
- **Platform / Derived Texture Data：** 根据目标平台、Mip 与压缩配置派生的可供运行时使用的数据。
- **RHI/Texture Resource：** 最终用于 GPU 采样/上传的资源与状态。

各 UE 版本的具体 API 类型、Build Pipeline、BulkData 和 Editor-only 条件可能改变，**不要仅凭上述概念就断言某个版本必定可直接访问某个成员**。

### 5. 为什么 GPU Texture 通常不能直接由 CPU 当普通数组随意访问？

GPU 资源可能有专用的显存布局、压缩块、Tiling/Swizzling、多级缓存和异步使用约束。CPU 侧指针不等于 GPU Texture 的线性像素数组。

通常需要 API 提供的 Staging/Readback Buffer、Copy/Transfer 命令或特定 Map 能力，并处理 Resource State/同步。

### 6. 纹理流送（Texture Streaming）解决什么问题？

大场景中不必一次把所有高分辨率 Mip 都留在 GPU 内存。引擎可根据观察距离、屏幕尺寸、预算和预取策略决定哪些 Mip 或 Tile 驻留。

它会影响纹理清晰度、IO 带宽、上传压力和显存占用。Streamed Texture “突然变清晰”常被称为 Mip Pop / Texture Pop。

## 十三、GPU Upload 与 GPU Readback

### 1. Texture Upload 和 GPU Readback 有什么主要区别？

- Upload：CPU/IO 数据发送到 GPU 可采样资源。
- Readback：将 GPU 当前资源或计算结果变成 CPU 可以访问的数据。

两者都涉及数据移动与 Resource Synchronization，但 GPU Readback 经常需要等前面的渲染/计算写入完成，因此特别容易造成 GPU/CPU Pipeline Stall。

### 2. 为什么直接读取 GPU Texture 可能导致卡顿？

考虑时间线：

~~~text
CPU Submit Render A -> Submit Render B -> Readback Request
GPU       Render A ... Render B ... Write Texture
                                         |
                                         v
                                 GPU Copy to Staging
                                         |
                                         v
CPU must wait for data readiness before reading
~~~

如果 CPU 在 GPU 写入或 Copy 完成前就阻塞等待，CPU 线程可能被迫同步 GPU 进度；某些 API 调用还可能在提交或准备阶段隐式同步。

**异步读取的关键不是“把 Readback 放进工作线程”**，而是让 GPU Copy 与 CPU 访问之间使用合理的异步任务/缓冲与完成同步。

### 3. 什么是 Staging / Readback Buffer？

一种常见路径：

1. GPU 渲染/处理 Texture。
2. 使用 GPU Copy 操作把需要的数据放进 CPU 可读的 Buffer/Staging Resource。
3. 插入 Fence 或依赖完成标记。
4. CPU 不阻塞地继续其他工作。
5. 当 Fence 真正完成时 Map/Read 数据。
6. 按 Format、Row Pitch、Channel 语义正确转换到最终 CPU 图像。

在 OpenGL 中可使用 PBO（Pixel Buffer Object）配合 Fence 做这样的数据转移；在 D3D12/Vulkan 中则需要相应 Copy/Transfer、Resource State 和 Fence 等机制。

### 4. PBO 为什么有助于异步 Readback？

PBO 允许像素传输操作以 Buffer 为目的地，之后 CPU 可以在同步完成时读取 Buffer；这使驱动有机会把传输与 CPU 后续工作重叠。

但 **PBO 不保证任何场景下 `glReadPixels` 或 `glGetTextureImage` 都绝对无阻塞**：读回前的数据依赖、驱动、资源格式与尺寸仍可能带来等待或复制成本。

### 5. GPU Readback 时 Row Pitch 为什么重要？

纹理行存储可能有对齐要求。CPU 图像的紧密 Row Pitch 通常为 `width * bytesPerPixel`，但 GPU Copy 目标可能要求更大 Alignment。

如果直接假设连续内存每行没有 Padding，颜色可能错行、倾斜或整个图像损坏。

### 6. Compressed Texture 的 Readback 是原始压缩块，还是解码后的像素？

**必须指定读取 API/路径。**

- 读取 Compressed Image Data 的 API 可能返回 BC/ASTC 等编码后的 Block Data。
- 读取普通格式的像素数据 API 或先通过 Shader 绘制到 RGBA Render Target，再 Readback，可以取得对应路径的像素/采样结果。

它们不等价：

- **压缩比特流**不等于 RGBA 像素。
- **压缩纹理解码值**不保证等于 Source Art。
- **Shader 预览结果**可能额外经历 sRGB Decode、Filtering、Mip 选择、材质与显示转换。

### 7. GPU Readback 和 Histogram 计算可以怎么结合？

针对 Texture Editor 的统计需求，至少有两类方向：

- **CPU 路径：** 将需要的 Mip/通道回读到 CPU，再进行 Luminance / Channel Histogram 统计；实现较直接，但数据拷贝与同步可能较昂贵。
- **GPU 路径：** 用 Compute Shader 在 GPU 上处理 Texture 并累计 Histogram，仅回读少量 Bin 或统计结果；可减小回读数据量，但增加 GPU Dispatch、同步和数据竞争处理。

选择应基于纹理尺寸、更新频率、是否需要精确 Source 值、是否正在编辑器交互、GPU/CPU 性能预算。

### 8. 为什么 GPU Histogram 与 Source Histogram 可能不同？

不是所有不同都代表 Bug。需要确认究竟统计的是：

- 导入时的 Source Pixel。
- 压缩/重建后的指定 Mip。
- 硬件采样后经 sRGB 解码的线性值。
- Shader 预览 Render Target 中的最终值。
- Alpha 裁剪/颜色分级/Tone Mapping 之后的值。

对于有损压缩和颜色空间转换，不同数据源的统计结果本来就不一定相同。

## 十四、OpenGL / GLSL 工程示例

### 1. 创建 2D sRGB Albedo Texture 的示例

以下是 OpenGL 4.5 DSA 风格简化代码。假设调用前已经有**经过正确解码并按 RGBA8 排列**的像素数据，`width/height > 0`；此函数不负责读取 PNG/JPEG 文件。

~~~cpp
#include <algorithm>
#include <cmath>
#include <cstdint>
#include <GL/gl.h> // 实际项目需包含支持 GL 4.5 的加载器/头文件

GLuint CreateAlbedoTexture(
    int width, int height, const std::uint8_t* rgbaPixels)
{
    const int mipCount =
        1 + static_cast<int>(std::floor(
            std::log2(static_cast<double>(std::max(width, height)))));

    GLuint texture = 0;
    glCreateTextures(GL_TEXTURE_2D, 1, &texture);

    glTextureStorage2D(
        texture, mipCount, GL_SRGB8_ALPHA8, width, height);

    glPixelStorei(GL_UNPACK_ALIGNMENT, 1);
    glTextureSubImage2D(
        texture, 0, 0, 0, width, height,
        GL_RGBA, GL_UNSIGNED_BYTE, rgbaPixels);

    // 仅演示 API；对颜色敏感内容宜核对 Mip 生成的颜色空间
    glGenerateTextureMipmap(texture);

    glTextureParameteri(texture, GL_TEXTURE_MIN_FILTER,
                        GL_LINEAR_MIPMAP_LINEAR);
    glTextureParameteri(texture, GL_TEXTURE_MAG_FILTER,
                        GL_LINEAR);
    glTextureParameteri(texture, GL_TEXTURE_WRAP_S,
                        GL_REPEAT);
    glTextureParameteri(texture, GL_TEXTURE_WRAP_T,
                        GL_REPEAT);
    return texture;
}
~~~

**额外注意：** 在很多实际引擎中，Mip 会在离线导入或 Cook 阶段按颜色、法线、Alpha Coverage 等语义生成，而不是无差别调用一次 Mip Generator。

### 2. GLSL 里 implicit LOD、explicit LOD 和 explicit gradient 有什么区别？

~~~glsl
#version 450 core

in vec2 vUV;
uniform sampler2D uAlbedo;

layout(location = 0) out vec4 outColor;

void main()
{
    vec4 autoLOD = texture(uAlbedo, vUV);

    // 显式指定 Mip LOD，用于调试或特定滤波需求
    vec4 mip2 = textureLod(uAlbedo, vUV, 2.0);

    // 在导数有效的控制流中显式计算梯度
    vec2 duvdx = dFdx(vUV);
    vec2 duvdy = dFdy(vUV);
    vec4 explicitGrad = textureGrad(uAlbedo, vUV, duvdx, duvdy);

    // 用于调试：避免 unused variable
    outColor = (autoLOD + mip2 + explicitGrad) / 3.0;
}
~~~

- `texture`：依赖隐式导数自动选择 LOD，行为与 Shader Stage/平台有关。
- `textureLod`：显式指定 LOD，适用于允许该函数的 Shader Stage 与采样器类型。
- `textureGrad`：传入显式导数，适用于不能直接可靠使用隐式导数的某些场景或特殊 Filtering。

**不要**把这里把三次采样平均的调试写法当作实际材质算法。

### 3. 如何在 Shader 里可视化当前 LOD？

可以使用 `textureQueryLod`（适用版本/Shader Stage/采样器类型时）查询相关 LOD 信息；也可以基于 UV 导数手动估算：

~~~glsl
vec2 texSize = vec2(textureSize(uAlbedo, 0));
vec2 dx = dFdx(vUV) * texSize;
vec2 dy = dFdy(vUV) * texSize;

float rho = max(length(dx), length(dy));
float estimatedLod = log2(max(rho, 1e-8));
~~~

手工推导的 `estimatedLod` 是常用启发式，**不保证与硬件实际选择的 Mip 在所有采样器状态和各向异性模式下完全一致**。

### 4. 为什么 sampler2DShadow 与 sampler2D 不一样？

Shadow Sampler 通常结合 Depth Texture 的 Comparison Mode 和参考深度，得到一个或多个比较结果，过滤时可能执行 PCF 语义。

它不是“读取深度像素后自动返回普通颜色”，采样参数的维度/参考值和资源 Compare 配置必须匹配。

### 5. 为什么 texelFetch 不等于 texture？

`texelFetch` 常采用离散整数 Texel 坐标、显式 LOD（适用纹理类型时），绕过普通归一化 UV 寻址/过滤语义，适合精确读取某个 Texel；而 `texture` 通过 Sampler State 进行过滤与 LOD 选择。

`texelFetch` 也不是“任意 GPU 内存读指令”，它仍然受 Texture 对象、格式和 Shader 规则约束。

## 十五、Texture Streaming、Virtual Texturing 与资源管理拓展

### 1. Texture Streaming 只需要决定 Mip 级别吗？

传统 Mip-based Streaming 经常以某张纹理的 Mip Range 为单位加载/驻留；Virtual Texture / Sparse Texture 可进一步把纹理切成 Page/Tile，根据实际使用区域加载，避免整个大纹理高分辨率层都驻留。

这两者涉及不同的页表、反馈和资源管理成本。

### 2. Virtual Texturing 的基本数据流是什么？

~~~text
Material UV / Virtual Address
             |
             v
Page Table Lookup
             |
             v
Physical Tile Atlas / Cache
             |
             v
Texture Sample

Feedback: Missing/needed pages
             |
             v
IO -> Decode -> Upload -> Update Residency / Page Table
~~~

Virtual Texture 的核心是将**虚拟纹理地址**映射到有限的物理纹理页缓存。页缺失时通常回退到可用的粗 Mip 或替代数据，避免立即依赖 CPU 完成 IO。

### 3. 为什么 Virtual Texturing 不是免费提升性能？

它增加了 Page Table Lookup、反馈、物理 Page 管理、上传调度、Border/Gutter、同步和缓存命中率等复杂度。若页面抖动（Thrashing）或访问模式很随机，性能和画质都可能变差。

### 4. Render Texture 和普通纹理资源有什么区别？

纹理是否能作为 Color/Depth Attachment、Storage Image、Transfer Source/Destination 或 Sampled Image，是由资源格式、Usage 和 API 状态共同决定的。

不能仅靠“它是 Texture2D”就认为它可以任意同时读写。现代显式 API 通常还要求 Resource State/Layout 和 Barrier 正确转换。

## 十六、OpenGL 异步 GPU Readback 实战

### 1. 一个异步回读最小流程应该怎样设计？

以下代码以 OpenGL 4.5 DSA 接口为例，从**已经存在的、能够按 RGBA8 形式读取的 2D GPU Texture** 的指定 Mip 回读。它演示提交传输、Fence 与 CPU 延后 Map 的时序，而不是完整的 Production Readback Manager。

前提：

- 使用可访问 OpenGL 4.5 函数的加载器。
- 纹理数据已由之前的渲染/拷贝操作正确产生，且同一 Context 的命令顺序正确。
- 指定 Mip 的尺寸与输出缓冲大小匹配。
- Pixel Pack Alignment 设置为 1；输出格式为 `GL_RGBA / GL_UNSIGNED_BYTE`，每像素 4 Byte。
- 不考虑多层 Texture、MSAA Resolve、压缩块原样读取或跨 Context 同步等复杂场景。

### 2. 用 Pixel Pack Buffer + Fence 提交 Readback

~~~cpp
#include <cstddef>
#include <cstdint>
#include <vector>
// OpenGL 4.5 functions must be exposed by your actual GL loader.

struct PendingReadback
{
    GLuint pbo = 0;
    GLsync fence = nullptr;
    std::size_t byteCount = 0;
    int width = 0;
    int height = 0;
};

PendingReadback BeginTextureReadback(
    GLuint texture, int mipLevel, int width, int height)
{
    PendingReadback request;

    // 此教学示例假设 size 可用 GLsizei 表示，格式支持 RGBA8 输出。
    request.width = width;
    request.height = height;
    request.byteCount = static_cast<std::size_t>(width) *
                        static_cast<std::size_t>(height) * 4u;

    glCreateBuffers(1, &request.pbo);
    glNamedBufferData(request.pbo,
                      static_cast<GLsizeiptr>(request.byteCount),
                      nullptr, GL_STREAM_READ);

    // 使用 PBO 后，glGetTextureImage 的最后一个参数是 PBO 内偏移。
    glBindBuffer(GL_PIXEL_PACK_BUFFER, request.pbo);
    glPixelStorei(GL_PACK_ALIGNMENT, 1);

    glGetTextureImage(
        texture, mipLevel,
        GL_RGBA, GL_UNSIGNED_BYTE,
        static_cast<GLsizei>(request.byteCount),
        nullptr); // offset = 0

    glBindBuffer(GL_PIXEL_PACK_BUFFER, 0);
    request.fence = glFenceSync(GL_SYNC_GPU_COMMANDS_COMPLETE, 0);

    // 确保排队的 GPU 命令被提交；并不在这里等待 GPU 完成。
    glFlush();
    return request;
}
~~~

**重要：** 提交函数返回不代表数据已经可以被 CPU 读取。PBO 资源和 Fence 必须活到实际完成后，不能提前释放或重复用于冲突的读写操作。

### 3. 延后非阻塞轮询和 CPU Map

~~~cpp
bool TryFinishReadback(
    PendingReadback& request,
    std::vector<std::uint8_t>& outRGBA)
{
    if (!request.fence || request.pbo == 0)
        return false;

    const GLenum status = glClientWaitSync(
        request.fence, 0, 0); // timeout = 0: poll only

    if (status == GL_TIMEOUT_EXPIRED)
        return false;

    if (status == GL_WAIT_FAILED)
    {
        // 实际项目应记录 GL 错误并回收资源
        return false;
    }

    if (status != GL_ALREADY_SIGNALED &&
        status != GL_CONDITION_SATISFIED)
        return false;

    void* ptr = glMapNamedBufferRange(
        request.pbo, 0,
        static_cast<GLsizeiptr>(request.byteCount),
        GL_MAP_READ_BIT);

    if (!ptr)
        return false;

    const auto* begin = static_cast<const std::uint8_t*>(ptr);
    outRGBA.assign(begin, begin + request.byteCount);

    glUnmapNamedBuffer(request.pbo);
    glDeleteSync(request.fence);
    glDeleteBuffers(1, &request.pbo);

    request.fence = nullptr;
    request.pbo = 0;
    return true;
}
~~~

**使用方式：** 在一帧提交 `BeginTextureReadback`，过若干帧轮询 `TryFinishReadback`，直到 Fence Signal；在资源销毁前必须处理未完成任务。

上述代码强调关键流程，实际使用应加上失败清理、Context 所有权、最大任务数量、Buffer Pool、资源生命周期及跨线程调度。**不能在没有正确 Context/同步的任意 CPU 工作线程上直接调用这些 OpenGL 函数。**

### 4. 为什么 Readback Buffer Ring 有用？

如果每帧都要读取小型结果，直接反复等待同一个 PBO 会抵消异步收益。可以准备多个 PBO 与 Fence：

~~~text
Frame N:     GPU fills PBO[0]
Frame N+1:   GPU fills PBO[1], CPU polls PBO[0]
Frame N+2:   GPU fills PBO[2], CPU processes completed requests
Frame N+3:   Reuse a completed PBO safely
~~~

Ring 的数量、等待策略和是否跳帧依赖数据量、GPU Latency 与编辑器的实时性要求。不能为了避免 Stall 无限增加 Buffer，否则会造成内存增长。

### 5. 为什么“从 Texture Readback”不等于“Shader Sample 这个 Texture”？

普通 Texture Image Readback 从 Texture 的某级存储数据转换到请求的 CPU Pixel Format，而 Shader `texture()` 可能：

- 根据 UV 进行 Wrap、Bilinear、Mipmap、Anisotropic。
- 对 sRGB RGB 进行解码。
- 经过 Normal Map 解码、材质/光照和显示变换。
- 在当前 Streaming 状态下选择某个可用 Mip。

如果想获取用户眼睛看到的预览结果，可以先绘制到明确格式的 Render Target，再 Readback 该 Render Target；如果想比较源图和 GPU Decoded 资源，应该先定义数据的**格式、Mip、色彩空间和是否经过 Shader**。

## 十七、渲染问题排查与性能优化

### 1. 纹理近看正确，远处闪烁，怎么排查？

建议顺序：

1. 先看是否有完整 Mip Chain。
2. 检查 Min Filter 和当前 Sampler，是否真的使用 Mipmap。
3. 可视化实际/估算 LOD，检查 UV 导数是否异常。
4. 观察是否因为 Negative LOD Bias 而强行选择过细的 Mip。
5. 区分是 Albedo Aliasing、Normal/Specular Aliasing 还是 Masked Coverage。
6. 斜视表面检查 Anisotropic Filtering。
7. 若处于 TAA 管线，再检查 Jitter、Motion Vector 与 History 造成的时间闪烁。

### 2. 为什么某块模型一直显示最低清晰度？

可能的原因：

- Texture Streaming 预算不足或高 Mip 尚未加载。
- Sampler LOD Bias / Max LOD 限制。
- UV Scale、导数或 Mip 级别计算异常。
- Base Level / Max Level、Texture View 限制错误。
- 压缩后的资源本身就已经在 Cook 阶段降分辨率。
- 显示的是 Editor Thumbnail，而非最终 GPU 纹理。

### 3. 为什么法线贴图呈现“颜色正确但光照怪异”？

检查：

- 是否把 Normal Map 误当成 sRGB Color。
- XYZ 解码是否正确，有无通道翻转（特别是 Y/Green）。
- Normal Texture 是否采用正确压缩格式。
- TBN 是否正交、Handedness 和 UV Seam 是否正确。
- 采样后是否 Normalize。
- 光源与法线方向是否处于同一个坐标空间。

### 4. 为什么透明 PNG 在 Mipmap 后出现黑边？

检查 Straight/Premultiplied 表示、完全透明像素 RGB、sRGB 线性过滤、Mip 生成与 Atlas Gutter。仅改 Wrap 到 Clamp 未必能解决中间 Mip 已经被邻居污染的问题。

### 5. RenderDoc 调试采样具体看哪些项目？

建议围绕单个 Draw Call：

1. Texture Viewer：确认绑定的 Texture、Mip、尺寸、通道与数据值。
2. Pipeline State：资源绑定、Sampler Filter/Wrap、LOD 设置。
3. Shader 代码：`texture`、`textureLod`、`textureGrad`、`texelFetch` 的使用与分支。
4. 输入 Varying：UV 是否正确，是否经过透视校正。
5. Capture 中的 Resource Format：sRGB、UNORM、FLOAT、Compressed 的区别。
6. Pixel History/Shader Debugger：必要时定位输出结果与深度测试等影响。

### 6. 如何判断纹理采样是不是性能瓶颈？

可做对照实验：

- 替换昂贵的 Texture Sampling 为常量，测量 GPU 时间变化。
- 降低或增加纹理尺寸、Mip 使用范围，观察带宽与 Cache 命中变化。
- 比较不同 Anisotropy 设置。
- 观察屏幕分辨率、Overdraw 与 Shader 指令的变化。
- 使用厂商 GPU Profiler 查询 Texture Cache、Bandwidth、Sampler Utilization 等指标（若设备支持）。

**不要只看采样函数的次数。** Cache Locality、压缩格式、过滤、纹理维度和依赖链都可能主导最终开销。

### 7. GPU Readback 导致 Editor 卡顿，如何做工程优化？

- 不要在 UI/Main Thread 直接阻塞等待 GPU 完成。
- 缩小回读范围：指定 Mip、ROI、通道，或只回读 Histogram Bin。
- 让 GPU Copy 与 CPU UI 工作重叠，使用 Fence/异步任务。
- 缓存先前结果，避免每次 Hover/Slider Update 都重新大尺寸回读。
- 对允许一定延迟的预览做节流、合并和取消过期任务。
- 将 Pixel Conversion、Histogram 统计和 UI 更新分成不同阶段。
- 记录 CPU/GPU Timeline，区分 GPU Stall、CPU 处理与 UI 刷新成本。

## 十八、秋招高频面试题与追问

### Q1：Texel、Pixel、Fragment、Sample 有什么区别？
Texel 是纹理离散元素；Pixel 是 Render Target 的位置；Fragment 是光栅化产生的片元；Sample 参与覆盖/深度等判定。一个 Fragment 采样纹理通常不只访问一个 Texel。

### Q2：Texture 与 Sampler 为什么分开？
Texture 负责数据、格式和 Mip，Sampler 负责寻址、过滤、LOD 和比较等访问规则，可按 API 方式组合复用。

### Q3：Normalized UV 与 Texel Center 的关系？
第 `(i,j)` 个 Texel 中心为 `((i+0.5)/W,(j+0.5)/H)`，边界采样还受 Wrap Mode 影响。

### Q4：Bilinear 为什么使用 4 个 Texel？
2D 邻域四个点提供水平和垂直插值，权重是两个一维 Lerp 的乘积。

### Q5：为什么线性过滤也会让远处纹理闪烁？
单层 Bilinear 无法覆盖一个像素对应的宽广基础纹理 Footprint，没有充分低通。

### Q6：Mipmap 的本质是什么？
多分辨率预过滤表示，用适合屏幕采样分辨率的数据降低 Minification Aliasing。

### Q7：完整 2D Mip Chain 为什么约增加 1/3 内存？
对理想二次缩小的 2D 纹理，面积级数为 `1+1/4+1/16+...≈4/3`。

### Q8：GPU 怎么估算 LOD？
通过 `dFdx/dFdy` 估计 UV 在屏幕移动一像素的变化，转换为基础纹理 Texel 尺度后用对数关系选择 Mip。

### Q9：为什么 LOD 与距离不是严格一一对应？
还取决于 UV Density、Surface Orientation、投影、分辨率和 Sampler State。

### Q10：为什么 Trilinear 通常要两个 Mip？
在两个临近 LOD 的 Mip 各采样一次，再按 LOD 小数部分插值减少 Mip 边界突变。

### Q11：为什么 Anisotropic 能改善斜视地板？
映射 Footprint 的长轴远大于短轴，多个适当样本可在降低长轴走样时保留短轴细节。

### Q12：16× Anisotropy 就是读取 16 个 Texel 吗？
不是，它是可用最大过滤各向异性程度的配置，具体访存和过滤核实现依硬件。

### Q13：sRGB 与 Linear 的区别是什么？
sRGB 编码数值不与光线性能量线性成比例，渲染光照运算通常需要将颜色解码成 Linear。

### Q14：为什么 Roughness/Normal 一般不使用 sRGB？
它们表示数据或编码方向；误用 sRGB 解码将改变物理/材质参数数值。

### Q15：为什么 sRGB Mipmap 不能简单平均编码值？
直接平均编码数据不等于平均线性亮度，可能使 Mip 偏暗。

### Q16：Normal Map 采样后为什么 Normalize？
多个单位向量插值后一般不再保持长度为 1。

### Q17：为什么 Normal Map 的 Mipmap 可能导致 Specular Aliasing？
平均法线丢失局部法线方差信息，导致微表面高光估计过于锐利。

### Q18：Alpha-Test 贴图 Mipmap 后为什么可能变细？
Alpha 分布被平均后跨过 Cutout 阈值，损失原始覆盖率。

### Q19：BC1、BC3、BC5、BC7 常见用途？
BC1 偏向 RGB、BC3 支持连续 Alpha、BC5 常用于法线 XY、BC7 常用于高质量 LDR 颜色。

### Q20：BC5 Normal Map 的 Z 为什么可以重建？
在单位长度且处于约定半球条件下，`z=sqrt(1-x²-y²)`。

### Q21：ASTC 4×4 与 8×8 为什么 bpp 不同？
常见 ASTC Block 固定 128 bit，不同 Block 覆盖 Texel 数量不同。

### Q22：PNG/JPEG 压缩与 GPU BC/ASTC 压缩区别？
前者主要为磁盘/传输文件编码，后者支持 GPU Block 粒度随机采样与硬件解码。

### Q23：为什么 Source Art 不等于 GPU Decoded？
中间存在 Cook、Mipmap、压缩、格式/颜色转换、Streaming 和采样/预览路径差异。

### Q24：为什么 GPU 纹理不能无条件由 CPU 按 RGBA 数组读取？
GPU 资源可能具有压缩、Tiling、布局、专用存储和异步使用约束，需要指定 API 的读回路径。

### Q25：为什么 glReadPixels / GPU Readback 容易卡顿？
如果 CPU 等待 GPU 之前的渲染或 Copy 结果，就可能产生 Pipeline Stall。

### Q26：PBO 一定保证回读完全异步吗？
不保证，它提供异步传输与延后 Map 的机会，具体驱动和资源依赖仍可能导致同步。

### Q27：如何正确设计 Texture Editor GPU Readback？
分清数据源和数据格式，使用 Staging/PBO、Fence、任务生命周期、合理 Pixel Conversion、节流与 UI 更新机制。

### Q28：GPU Histogram 与 Source Histogram 为什么不同？
数据可能来自不同 Mip、压缩版本、Linear/sRGB 表示或 Shader Render Target，统计对象本身不同。

### Q29：纹理清晰度不足与性能不足该如何权衡？
结合目标平台、显存、带宽、采样 Footprint、压缩质量、Streaming 策略与真实 GPU 指标，而不是只将分辨率调高。

### Q30：Virtual Texturing 与普通 Mip Streaming 的差异？
Mip Streaming 通常按纹理 Mip 范围决定驻留；Virtual Texturing 进一步按 Tile/Page 决定局部区域驻留，成本是反馈和页表管理。

### Q31：为什么 `texture` 和 `texelFetch` 得到的值不同？
前者通常采用 Sampler 的寻址/过滤/LOD，后者常精确读取指定 Texel/Level，不走相同过滤路径。

### Q32：sRGB Texture 读取时 Alpha 通道会一起 Gamma Decode 吗？
典型 sRGB RGBA Texture 的 RGB 执行 sRGB 解码，Alpha 通道不经过同样的颜色传递函数。

## 十九、动手验证题

### 练习 1：实现 Nearest / Bilinear

自己构造一张 2×2 RGBA 纹理：

~~~text
C00 = Red       C10 = Green
C01 = Blue      C11 = White
~~~

在中心点采样，对比 Nearest 与 Bilinear，并用权重公式手算 Bilinear 结果。

### 练习 2：生成 Mip Chain 并对比颜色空间

制作黑白棋盘格，分别：

1. 直接对 sRGB 编码值平均。
2. 先解码到 Linear，平均后重新编码到 sRGB。

对比缩小后的亮度，解释为什么第二条路径更接近正确的光能平均。

### 练习 3：手算 LOD

给定 `W=1024、H=1024`：

~~~text
dUVdx = (0.004, 0)
dUVdy = (0, 0.002)
~~~

计算 `ρx`、`ρy` 和 `λ`，并观察为何接近 Mip 2。

### 练习 4：斜视棋盘格观察 Anisotropic

渲染一个向远处延伸的棋盘地板，分别使用：

- Bilinear without Mipmap
- Trilinear
- Trilinear + Anisotropy 8× / 16×

观察纹理稳定性、远处模糊程度与 GPU Time。

### 练习 5：Normal Map 格式与采样

选一张高频法线贴图，比较 RGBA8、BC5（若硬件支持）和错误 sRGB 解码下的结果。检查 Normal Length、Specular Aliasing 和 Compression Artifact。

### 练习 6：模拟 Atlas Bleeding

把两张高对比颜色贴图放进一个 Atlas，在 Mip 和 Linear Sampling 下观察边界。加入 Padding/Gutter 后比较。

### 练习 7：实现 GPU Readback 对照

对同一张纹理分别导出：

1. Source 文件解码数据。
2. 指定 Mip 的 GPU Image Readback。
3. Shader Sample 后写入 RGBA Render Target 的 Readback。

逐通道比较像素与 Histogram。记录 Compression、sRGB 和 Mip 差异，不应预期所有路径完全一致。

### 练习 8：PBO + Fence 性能实验

在相同纹理尺寸下比较：

- 同步读回并立刻 CPU 访问。
- 使用 PBO + Fence，延后数帧轮询。
- 仅在 GPU 计算 Histogram，回读少量统计结果。

记录 CPU 等待时间、GPU Copy Time、端到端延迟和资源占用，避免只比较单个 API 调用耗时。

## 二十、公式与关键结论速记

| 知识点 | 公式 / 结论 |
|---|---|
| Texel Center | `u=(i+0.5)/W, v=(j+0.5)/H` |
| Bilinear | `C=(1-t)(1-s)C00+t(1-s)C10+(1-t)sC01+tsC11` |
| 完整 2D Mip 级数 | `L=1+floor(log2(max(W,H)))` |
| 理想 2D Mip 总面积 | 约 `4/3` 倍 Level 0 |
| LOD Texel Gradient | `gx=(W dudx, H dvdx), gy=(W dudy, H dvdy)` |
| 常见 Isotropic LOD | `λ=log2(max(length(gx), length(gy)))` |
| Trilinear | `C=(1-t)Ck+t C(k+1)` |
| Footprint Anisotropy | `A≈σmax/σmin` |
| sRGB 0.5 解码 | Linear 约 `0.214` |
| Linear 0.5 编码 | sRGB 约 `0.735` |
| Tangent Normal 解码 | `n=normalize(2*rgb-1)` |
| BC1/BC4 | 4 bpp |
| BC3/BC5/BC6H/BC7 | 8 bpp |
| ASTC 4×4 | 8 bpp |
| ASTC 8×8 | 2 bpp |
| GPU Readback | GPU Copy + Staging/PBO + Fence + CPU Map |
| Source vs GPU Decoded | 不同生命周期与数据语义，不一定逐像素相等 |
