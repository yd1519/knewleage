## 一、阴影在渲染方程中是什么？

### 1. 阴影解决了光照模型的哪个问题？

BRDF 只回答**到达当前表面的入射光如何被反射**；阴影回答**光源到该表面的光路是否被其他几何阻挡**。它属于几何可见性（Visibility）问题。

对面积光源上的点 `y`，某表面点 `x` 的直接光贡献包含：

$$
L_{\mathrm{direct}}(x,\omega_o)=
\int_{A_L}
f_r(x,\omega_i,\omega_o)\,
L_e(y,-\omega_i)\,
V(x,y)\,
G(x,y)\,\mathrm dA_y.
$$

`V(x,y)` 在不透明、二值遮挡下为 0 或 1；`G(x,y)` 包含两个表面投影余弦和距离平方项。

### 2. 为什么 PBR 的 G 项不能代替阴影？

Cook–Torrance 中的 `G_micro` 处理**微表面内部**的 Masking/Shadowing，而 Shadow Map/RT 则处理**宏观场景几何**对光路的遮挡。两种可见性作用于不同几何尺度，真实直接光常需要两者。

### 3. Hard Shadow 与 Soft Shadow 的本质区别？

- **点状理想光源/方向 Delta Light：** 对给定表面点、给定光照方向，有无障碍通常只产生二值可见性，形成几何上清晰的阴影边界。
- **面积光源：** 不同发光面积元有不同光路；某点可能只能看到发光面的部分区域，形成 Penumbra（半影）。
- PCF 可以将硬阴影的离散采样边缘**过滤成较平滑的可见性**，但它本身不完整模拟物理面积光的半影扩张。

### 4. Shadow Mapping 和 Ray Traced Shadow 之间的基本差别？

Shadow Mapping 先**从光源视角存储最近遮挡深度**，再由相机可见点投影回光源视角比较；光线追踪则可沿表面点到光源的方向/采样点发出 Shadow Ray 检查遮挡。

两者都是 Visibility 的估计方式，但性能、精度、覆盖范围及适配的光源类型不同。

## 二、Shadow Mapping 的两个 Pass

### 1. Shadow Mapping 的基本步骤？

~~~text
Shadow Pass：
Shadow-Casting Geometry
      |
      v
Light View + Light Projection
      |
      v
Light Depth Render Target (Shadow Map)

Lighting Pass：
Camera-visible P_world
      |
      +---> P_lightClip = LightVP * P_world
      |
      +---> Perspective Divide / Shadow UV + Depth
      |
      +---> Sample Shadow Map + Compare
      |
      +---> Visibility -> Direct Lighting
~~~

这是一种**光源空间深度可见性缓存**，不是直接缓存“每个相机像素是否被阴影覆盖”。

### 2. 光源视角的深度图到底存储什么？

对 Shadow Map 的每个光源投影 Sample，深度测试留下沿该光源视线方向**最近能被光源看到的投影表面**的深度。

被它挡在后方的相机可见点投到相近的光源 Texel 后，通常会拥有更大的普通深度，因此可以被判断为处于阴影。

### 3. 从世界空间到 Shadow UV 的变换过程是什么？

对世界坐标 `P`：

$$
P_c=P_{\mathrm{light}}V_{\mathrm{light}}
\begin{pmatrix}P_x\\P_y\\P_z\\1\end{pmatrix}
=
\begin{pmatrix}x_c\\y_c\\z_c\\w_c\end{pmatrix}.
$$

先透视除法：

$$
p_{\mathrm{ndc}}=
\left(\frac{x_c}{w_c},
\frac{y_c}{w_c},
\frac{z_c}{w_c}\right).
$$

对于传统 OpenGL NDC 和左下角原点的光源纹理坐标：

$$
\boxed{
u_s=\frac{x_{\mathrm{ndc}}+1}{2},
\quad
v_s=\frac{y_{\mathrm{ndc}}+1}{2},
\quad
z_s=\frac{z_{\mathrm{ndc}}+1}{2}.
}
$$

等价地可使用将 `[-1,1]` 映射到 `[0,1]` 的 Bias Matrix。应注意：**该 Bias Matrix 与深度偏移的 Depth Bias 不是同一个东西。**

### 4. Spot Light 与 Directional Light 的 Light Projection 有何区别？

- Spot Light：常用**透视投影**，视锥由锥角、近平面、远平面限定。
- Directional Light：常用**正交投影**，光线近似平行，按当前可见范围选择光源空间盒。
- Point Light：向所有方向照明，不能只用一个普通单面 2D 透视阴影图覆盖整个球面，通常使用 Cubemap 或其它全向参数化。

### 5. Light View 矩阵是否与 Camera View 原理相同？

本质上都是将世界坐标转换到某个观察者/光源空间的变换矩阵。Light View 决定阴影深度渲染方向，Light Projection 决定阴影贴图的可覆盖区域及深度映射。

**注意：** 对方向光必须选择稳定的 Up Vector 和观察范围，避免视线方向接近 Up 时 LookAt 奇异，或摄像机移动时投影发生不必要的跳动。

### 6. 为什么不能直接使用 Camera MVP 得到 Shadow Map UV？

Camera Projection/View 将世界点映射到屏幕，Shadow Map 则必须使用**光源的 Projection/View**。混用矩阵会使相机移动时阴影跟着屏幕错误滑动。

Model Matrix 已把物体顶点变到 World Space；若 Lighting Pass 的 Varying 已是 World Position，就不应重复乘 Model。

### 7. 深度比较的数学条件是什么？

对普通 Shadow Depth（数值越大表示越远），光源记录的最近遮挡深度为 `z_map`，当前 Receiver 投影深度为 `z_receiver`，Bias 为 `b≥0`：

$$
\boxed{
V_{\mathrm{hard}}=
\begin{cases}
1,& z_{\mathrm{receiver}}-b\le z_{\mathrm{map}},\\
0,& z_{\mathrm{receiver}}-b>z_{\mathrm{map}}.
\end{cases}
}
$$

这是一种常见**Receiver Bias** 形式。实际也可在生成 Shadow Map 时偏移写入深度；两种方式对应的符号、状态和数值意义不同。

### 8. 为什么 Shadow Map 只保存最近深度仍然能判断不透明阴影？

对于**单个理想光照方向/单条光源视线**，只要知道第一个遮挡物的深度，就能判断同一条光路上后方 Receiver 是否被遮挡。若需要透明材质透射、体积光等，则单个最近深度不够表达全部贡献。

## 三、Light Space、裁剪范围与深度约定

### 1. Light Clip Space 与 Camera Clip Space 是同一个空间吗？

不是。二者可能都采用 NDC `[-1,1]`（传统 OpenGL），但矩阵不同、可见体不同，最终 Depth Resource 也不同。

**场景点在主相机可见并不意味着它在当前光源 Shadow Projection 内。** Receiver 在 Shadow Map 外时应使用显式的退化策略，而不是盲目 Clamp 并比较阴影边缘 Texel。

### 2. Shadow UV 在 [0,1] 之外怎么办？

需要按照光源有效范围和渲染目标要求处理：

- 检查 Light Clip 的齐次 `w`、投影后的 `z` 和 UV 是否在合理范围。
- 对 Light Projection 外的 Receiver，根据光源管理策略选择**视为未阴影、换级联/阴影页或使用回退**。
- Border Sampler 可以辅助安全取样，但**不能替代完整的视锥/深度范围检查**。

### 3. 为什么还要检查 z 超过 Far Plane？

假设 Shadow Map Far 对应 1.0。Receiver 在光源远平面之外，它根本没有在本张 Shadow Map 的可用投影深度范围内。若仍用接近 1 的固定深度与最远遮挡值比较，可能出现大片错误阴影。

常见策略是将无可用阴影数据的区域按“Lit”处理；如果其它 Shadow Cascade/Page 覆盖该 Receiver，则应选用正确区域的数据。

### 4. 投影后 w 接近 0 或小于 0 怎么处理？

对 Spot Light 等透视 Light Projection，`w≤0` 或特别小的情况下，点可能位于光源相机后方或接近透视奇点。

应优先使用**齐次 Clip Space 条件**及光源投影的正面范围检查，而不是对非法 `w` 直接除法产生异常 UV。

### 5. OpenGL 和 D3D/Vulkan 的深度约定为什么不能照抄？

- 传统 OpenGL Clip Z 常为 `[-w,w]`，Viewport Window Depth 默认为 `[0,1]`。
- D3D/Vulkan 常用 Clip Z 为 `[0,w]`，同时还存在不同的 Y/Viewports/纹理坐标方向。
- OpenGL 可以通过 Clip Control 使用 `[0,1]` 深度约定。
- Reversed-Z 还会反转 Near/Far 深度关系和 Comparison Function。

所以要问：**当前 Shadow Projection 产生的 NDC Z 是哪个范围？Shader/硬件采样器拿来比较的是哪种 Window Depth？**

### 6. Reversed-Z Shadow Map 应如何比较？

如果使用 Near→1、Far→0 的 Reversed-Z Shadow Map，则 Receiver **更远**通常意味着数值**更小**，因此常见硬阴影判断需使用相反不等号，例如将有偏移的 Receiver Depth 与已存最近深度作 `GEQUAL` 方向比较。

**不能只把 `LESS` 换成 `GREATER` 而忽略 Depth Clear、投影矩阵、Bias 符号和深度重建。** 主相机采用 Reversed-Z 也不强制所有 Shadow Map 都采用相同约定。

## 四、Shadow Acne：阴影自遮挡为何产生？

### 1. Shadow Acne 是什么样的现象？

明明朝向光源且无遮挡的表面，却出现不规则的深色条纹、斑点或密集自阴影，常称 Shadow Acne。

原因通常是同一表面的 Shadow Map 深度记录和 Lighting Pass 中的 Receiver 深度不完全一致。有限分辨率、深度精度、Rasterization、坐标重建误差都可能造成比较值略大于存储值。

### 2. 为什么同一个平面会挡住自己？

Shadow Map 中一个 Texel 覆盖光源视角的一片几何区域。Shader 在一个具体 Receiver 位置读取的是离散深度表示，它未必等于那个位置精确的几何深度。

当 Receiver Depth 因角度、插值或量化稍大于 `z_map` 时：

~~~text
receiver_depth > stored_nearest_depth
          |
          v
         Shadow!
~~~

理论上两者可能对应同一个表面，但有限分辨率比较无法自动判断这一点。

### 3. 为什么斜向受光的表面更容易 Acne？

一个 Shadow Texel 覆盖的区域内，如果几何深度变化很陡，则同一 Texel 内不同 Receiver 位置的真实深度差更明显。比较采样中心记录的值与另一位置的值时，误差可能增大。

这解释了**Slope-Scale Bias** 通常有用。问题并非单纯“深度格式位数不够”。

### 4. 什么时候不能靠增加 Depth Map 分辨率根治？

即使分辨率提高，深度量化、Depth Function、三角形边缘、不同 Vertex Shader 路径和浮点精度仍可能导致误差。应明确是 **Resolution Aliasing** 还是**Depth Comparison Precision/Self-Shadowing**。

### 5. 什么是 Peter Panning？

Bias 过大使原本应有的阴影被错误地判为受光，阴影与接触物体之间出现明显空隙，好像物体悬浮。

因此 Bias 是偏差-伪影折中，不是越大越好。

## 五、Depth Bias、Slope Bias 与 Normal Bias

### 1. 三种常见 Bias 的区别？

| 方式 | 主要思想 | 代价/问题 |
|---|---|---|
| Constant Depth Bias | 在深度比较或写入中加入常量偏移 | 不足时 Acne，过大时 Peter Panning |
| Slope-Scale Bias | 根据 Shadow Depth 随光源屏幕坐标的变化调整偏移 | 陡坡需要更大偏移；参数依投影/格式 |
| Normal Bias | 将 Receiver 取样位置沿法线方向略微移动 | 改变几何采样位置，可能产生接触偏移 |

### 2. 常见的角度启发式 Bias 怎么写？

可以按入射角设计一个简化 Receiver Bias：

$$
b=c_0+c_1\big(1-\max(0,\mathbf N\cdot\mathbf L)\big).
$$

这使掠射处 Bias 更大。**注意：这不是严格的硬件 Slope-Scale Depth Bias 数学定义**，只是常见 Shader 启发式；光源空间实际深度梯度还与投影方向、几何方向和纹理尺度有关。

### 3. 硬件 Polygon Offset 大致如何描述？

OpenGL `glPolygonOffset(factor,units)` 的概念：

$$
\mathrm{offset}=m\cdot\mathrm{factor}
+r_{\mathrm{depth}}\cdot\mathrm{units}.
$$

其中 `m` 与屏幕深度坡度有关；`r_depth` 与深度格式/实现定义有关。不同 API 对 Depth Bias 单位、Clamp、Slope 的具体语义不完全相同。

### 4. Receiver Depth Bias 与 Caster Depth Bias 能混用吗？

两者可组合，但都改变最终比较，必须明确各自在什么坐标空间、在哪个 Pass 生效：

- **Caster Bias：** 绘制 Shadow Map 时修改参与深度写入的数值。
- **Receiver Bias：** Lighting Pass 取样比较前修改当前 Receiver 的参考深度。
- **Normal Bias：** 偏移世界空间采样位置，再投影到 Light Space。

若两边都叠加大的偏移，容易产生明显阴影悬浮。

### 5. Normal Bias 为什么要考虑 World Units 与 Shadow Texel Size？

世界空间单位的固定 Bias 在不同 Cascade/Shadow Projection 下覆盖的相对 Texel 数不同；尤其 CSM 各级联 World Units per Texel 不同，统一常数会产生不一致阴影边界。

较合理的策略会依 Shadow Texel Footprint、投影深度梯度与几何朝向调整 Bias，且需要防止过大的偏移改变 Receiver 的真实接触关系。

### 6. Front-Face/Back-Face Culling 能缓解 Shadow Acne 吗？

某些闭合厚实几何在 Shadow Pass 绘制背面，可减少表面直接与自身深度接近的问题。但是：

- 单面平面、树叶、细薄网格可能完全错误。
- 物体内部/薄壳可能带来漏光。
- Shadow Caster 与 Receiver 的几何绕序、双面材质仍需正确处理。

不能把 Back-Face Shadow Mapping 当成通用替代 Bias 的方法。

### 7. PCF 核变大为什么可能需要重新调整 Bias？

PCF 会在邻近的多个 Shadow Texel 上比较，样本覆盖的光源空间区域更广；其中深度变化更大，可能增加 Self-Shadowing 或影响阴影边缘。

这说明 Bias 与 Filter Radius、Shadow Resolution、光照角度和 Cascade 设计存在耦合，需要一起调优。

## 六、OpenGL / GLSL：基础 2D Shadow Map

### 1. Shadow Pass 的 Vertex Shader 应如何输出？

以下示例把顶点直接变换到 Light Clip Space；Shadow Pass 只需要深度附件，通常无需输出颜色：

~~~glsl
#version 450 core

layout(location = 0) in vec3 aPosition;
uniform mat4 uModel;
uniform mat4 uLightVP;

void main()
{
    gl_Position = uLightVP * uModel *
                  vec4(aPosition, 1.0);
}
~~~

对于 Depth-Only Render Pass，Fragment Shader 可以非常简单或使用固定功能的默认深度输出。但 **Masked/Alpha-Test 材质**通常仍需要 Fragment Shader 采样透明遮罩并按阈值 `discard`，才能投射带孔洞的阴影。

### 2. Shadow Depth Texture 与 FBO 如何配置？

OpenGL 4.5 风格的核心思路：

~~~cpp
GLuint depthTexture = 0;
GLuint shadowFBO = 0;
const GLsizei kShadowSize = 2048;

glCreateTextures(GL_TEXTURE_2D, 1, &depthTexture);
glTextureStorage2D(depthTexture, 1,
                   GL_DEPTH_COMPONENT32F,
                   kShadowSize, kShadowSize);

glTextureParameteri(depthTexture, GL_TEXTURE_MIN_FILTER, GL_NEAREST);
glTextureParameteri(depthTexture, GL_TEXTURE_MAG_FILTER, GL_NEAREST);
glTextureParameteri(depthTexture, GL_TEXTURE_WRAP_S, GL_CLAMP_TO_BORDER);
glTextureParameteri(depthTexture, GL_TEXTURE_WRAP_T, GL_CLAMP_TO_BORDER);

const GLfloat borderDepth[] = {1.0f, 1.0f, 1.0f, 1.0f};
glTextureParameterfv(depthTexture, GL_TEXTURE_BORDER_COLOR, borderDepth);

// Manual comparison via sampler2D (rather than sampler2DShadow).
glTextureParameteri(depthTexture, GL_TEXTURE_COMPARE_MODE, GL_NONE);

glCreateFramebuffers(1, &shadowFBO);
glNamedFramebufferTexture(shadowFBO, GL_DEPTH_ATTACHMENT,
                          depthTexture, 0);
glNamedFramebufferDrawBuffer(shadowFBO, GL_NONE);
glNamedFramebufferReadBuffer(shadowFBO, GL_NONE);

// Production code checks GL_FRAMEBUFFER_COMPLETE and failures.
~~~

在执行 Shadow Pass 之前还要正确绑定 FBO、设定 Viewport、启用深度测试/写入、清除深度并实际绘制 Shadow Casters。示例没有展示全部状态恢复和资源生命周期。

### 3. 一个显式深度比较的 GLSL 函数

输入 `lightClip` 是 `uLightVP*vec4(positionWS,1)` 的结果；假设传统 OpenGL、非 Reversed-Z、Shadow Texture 仅存普通深度：

~~~glsl
uniform sampler2D uShadowDepth;

float HardShadowVisibility(vec4 lightClip, float bias)
{
    if (lightClip.w <= 0.0) return 1.0;

    // Homogeneous clip test for GL traditional [-w,w] depth.
    if (any(greaterThan(abs(lightClip.xyz),
                        vec3(lightClip.w))))
        return 1.0;

    vec3 ndc = lightClip.xyz / lightClip.w;
    vec3 shadowPos = ndc * 0.5 + 0.5;

    float zStored = texture(uShadowDepth, shadowPos.xy).r;
    float zReceiver = shadowPos.z;
    return (zReceiver - bias <= zStored) ? 1.0 : 0.0;
}
~~~

如果你想要 `GL_LESS` 的严格相等行为，比较函数和处理 Tie 的细节应额外明确。这里使用 `LEQUAL` 风格的“可见”判断以减轻边界不稳定。

### 4. 这个函数为什么没有直接写 `texture(uShadowMap,uv).r < depth`？

必须明确哪一个深度是 Receiver、哪一个是存储的最近深度、Bias 加在哪边。若写成“存储深度小于 Receiver 就被遮挡”，结果可以等价，但往往把返回值（阴影程度 vs 可见度）搞反。

这里返回**Visibility**，1=可见，0=阴影，后续乘到 Direct Light 上。切勿在 Shader 另一处把它再做 `1-visibility` 当成可见度。

### 5. Shadow Map 与 Lighting Pass 是否应使用完全相同的世界位置？

应保证它们表示同一几何面。若主 Pass 做了 Vertex Animation、Skinning、Morph 或 Wind Deformation，Shadow Pass 也应该以兼容的方式生成 Cast Geometry。

否则可能出现阴影“脱体”、时间抖动，或者因为两 Pass 使用不同几何而产生 Shadow Acne / Light Leak。

## 七、Hardware Comparison Sampler 与基础 PCF

### 1. 什么是 sampler2DShadow？

Shadow Comparison Sampler 将参考深度与存储深度作硬件 Comparison，返回可见性相关结果。若配置支持硬件过滤，采样可能在多个深度比较结果之间过滤。

它和普通 `sampler2D` 的区别是**先比较还是直接读取深度数值**，不能把 `sampler2DShadow` 的返回值当作原始深度使用。

### 2. OpenGL 如何配置硬件阴影比较？

~~~cpp
glTextureParameteri(depthTexture, GL_TEXTURE_COMPARE_MODE,
                    GL_COMPARE_REF_TO_TEXTURE);
glTextureParameteri(depthTexture, GL_TEXTURE_COMPARE_FUNC,
                    GL_LEQUAL);

// Enable filtering of comparison results where supported.
glTextureParameteri(depthTexture, GL_TEXTURE_MIN_FILTER, GL_LINEAR);
glTextureParameteri(depthTexture, GL_TEXTURE_MAG_FILTER, GL_LINEAR);
~~~

GLSL 以 `sampler2DShadow` 绑定该资源：

~~~glsl
uniform sampler2DShadow uShadowCompare;

float SampleShadowCompare(vec3 shadowUVZ, float bias)
{
    // vec3 = (u, v, receiver reference depth).
    return texture(uShadowCompare,
                   vec3(shadowUVZ.xy, shadowUVZ.z - bias));
}
~~~

**比较方向：** 此处普通 Shadow Map Near→0，Far→1，因此用 `LEQUAL`。实际驱动与 API 的比较过滤精度/样本配置不应靠想象得出固定 Sample Count。

### 3. 为什么硬件 Linear Shadow Sample 不等于“先双线性过滤深度再比较”？

常见 Comparison Filtering（PCF 思路）是**对若干邻近的存储深度分别执行比较，再对比较结果过滤**。

如果先平均深度再比较，深度不连续的边界上可能得到完全不同结果。因此必须区分 Depth Linear Filter、Comparison Filter 和手写 PCF。

### 4. PCF（Percentage-Closer Filtering）的核心是什么？

定义每个核内偏移点的二值可见性：

$$
V_i =
\mathbf 1[z_{\mathrm{receiver}}-b\le z_{\mathrm{shadow}}(u_i,v_i)].
$$

用滤波核权重求平均：

$$
\boxed{
V_{\mathrm{PCF}}=
\frac{\sum_i w_i V_i}{\sum_i w_i}.
}
$$

对于等权 N 个样本，就是通过的比较数/总数。**PCF 是过滤可见性，不是直接过滤 Depth Buffer。**

### 5. 手写 3×3 PCF 示例

~~~glsl
uniform sampler2D uShadowDepth;

float PCF3x3(vec3 shadowUVZ, float bias)
{
    vec2 texel = 1.0 / vec2(textureSize(uShadowDepth, 0));
    float visibilitySum = 0.0;

    for (int y = -1; y <= 1; ++y)
    {
        for (int x = -1; x <= 1; ++x)
        {
            vec2 uv = shadowUVZ.xy + vec2(x, y) * texel;
            float zMap = texture(uShadowDepth, uv).r;
            visibilitySum +=
                (shadowUVZ.z - bias <= zMap) ? 1.0 : 0.0;
        }
    }

    return visibilitySum / 9.0;
}
~~~

此函数假设上游已经验证 `shadowUVZ` 在光源有效范围内，并且已针对纹理边界设置合适采样状态。它是**固定半径 PCF**，在不同世界空间投影范围下对应的软化尺寸可能不一样。

### 6. PCF 为什么可以让阴影边缘更平滑？

阴影比较是离散 0/1。多个邻近 Shadow Texel 的比较结果平均后，在阴影边缘能产生连续的中间可见度值。

但固定核宽 PCF 的边缘通常不会自动根据遮挡物与 Receiver 距离产生正确的 Penumbra 增长。

### 7. PCF 采样越多越好吗？

不一定。较大 Filter Kernel 能减少锯齿，但增加 Texture Sample、阴影边缘模糊以及跨深度不连续处的偏差。

优化可以使用硬件 Comparison Filter、核权重设计、Poisson Disk、旋转采样核、时域积累或根据 Screen Footprint 调整 Sample Count。

## 八、Poisson Disk、随机旋转与阴影噪点

### 1. 为什么规则 3×3 或 5×5 PCF 可能出现条纹？

固定规则核在周期性几何/Shadow Texel 网格上可能产生可见结构，尤其低分辨率 Shadow Map 和斜向边缘更明显。

Poisson Disk 核使采样位置更不规则，可以将结构性条纹转化为相对不规则的噪点。

### 2. Poisson Disk Sampling 的作用是什么？

在近似均匀覆盖采样区域的同时保持样本间适度距离，避免样本大量堆叠。常用于软阴影、AO、SSR、环境采样等屏幕空间或纹理域随机核。

Poisson Disk 不是自动无偏的万能保证；样本分布、权重及滤波区域仍需要符合目标积分的约定。

### 3. 为什么用随机旋转 Kernel 能缓解 Banding？

如果所有像素使用同一组 Offset，阴影误差会在画面中形成重复的方向图案。按像素/蓝噪声旋转 Kernel，可以减少这种固定方向相关性，使误差更适合时域累积或空间降噪。

代价是噪点与时域稳定性问题；没有 TAA/稳定过滤时，随机核可能出现明显闪烁。

### 4. 是否应该每帧都生成完全独立随机 Offset？

不能无条件这样做。每帧大幅改变采样核会使阴影在静止画面下闪烁。真实引擎通常会平衡固定样本、时域 Jitter、Blue Noise、Motion Vector 和 History Accumulation。

### 5. PCF 和 MSAA 是同一件事吗？

不是。MSAA 主要优化几何 Coverage Sampling；PCF 优化 Shadow Test 在光源空间的深度比较采样。即使启用 MSAA，Shadow Map 分辨率不足导致的锯齿仍可能存在。

## 九、PCSS：Percentage-Closer Soft Shadows

### 1. 为什么固定半径 PCF 不能正确模拟接触软阴影？

真实面积光源的半影宽度会随遮挡物（Blocker）与接收表面（Receiver）之间的距离变化。两个表面靠得很近时，阴影边缘较锐利；二者分开时，同一面积光源往往产生更宽半影。

固定 PCF Kernel 不知道 Blocker 的距离，因此**只能施加固定阴影过滤宽度**，没有真正的接触硬化（Contact Hardening）机制。

### 2. PCSS 的三个典型阶段是什么？

~~~text
Receiver in Light Space
          |
          v
1. Blocker Search
   在潜在光源投影区域搜集比 Receiver 更近的深度
          |
          v
2. Penumbra Estimate
   用 Receiver / Blocker 深度差 + 光源尺寸估算过滤半径
          |
          v
3. Variable-Radius PCF
   按估算半影大小执行可见性过滤
~~~

**PCSS 本质是以几何关系调节 PCF 半径的软阴影近似**，不是每个面积光源点都做精确的遮挡积分。

### 3. PCSS 中为什么需要 Blocker Search？

先寻找**光源视角比当前 Receiver 更近的阴影深度**，它们可能是遮挡当前 Receiver 的几何。

对普通 Shadow Depth：如果 `z_sample < z_receiver - bias`，可将该深度视为潜在 Blocker 候选。

Blocker 搜索一般需要**未比较的原始深度**，因此光靠返回 0/1 的 `sampler2DShadow` 不够；可以另用普通深度采样路径。

### 4. 经典 PCSS 的半影宽度如何推导？

以简化的**平行平面面积光源与 Shadow Receiver** 几何为例，设：

- `z_b>0`：Blocker 到光源平面/参考光源的正向距离。
- `z_r>z_b`：Receiver 的对应正向距离。
- `w_L`：光源在横向的有效宽度。

利用相似三角形，有经典估计：

$$
\boxed{
w_p \approx w_L\frac{z_r-z_b}{z_b}.
}
$$

当 `z_r≈z_b`，半影宽度趋近零；当 Receiver 远离 Blocker，半影扩大。

**非常重要：** 这里的 `z_b`、`z_r` 是**同一光源几何约定下的线性距离**，不是未经反投影的 OpenGL Perspective Shadow Map 窗口深度。

### 5. 为什么 PCSS 要先把 Depth 线性化？

透视 Shadow Projection 的设备深度通常与距离成 `A+B/d` 的非线性关系。如果直接将 `z_shadow` 当物理距离放进相似三角形公式，会得到错误的半影比例。

对聚光灯 Perspective Shadow Map，需要根据 Light Near/Far 重建线性深度。对正交方向光 Shadow Map，普通窗口深度与光源视线距离是仿射关系，但仍应先明确映射到相应的世界单位。

### 6. Blocker Search Radius 与 PCF Filter Radius 一样吗？

不是：

- Search Radius 决定**寻找可能遮挡 Receiver 的几何范围**，与光源尺寸及 Receiver 到光源的几何关系有关。
- PCF Filter Radius 用**搜索到的平均 Blocker 深度**估计最终半影宽度。

二者都可能随 Receiver 距离、光源投影尺寸、分辨率而变化，但不是同一个数学量。

### 7. PCSS 完全找不到 Blocker 时如何处理？

在指定搜索核内没有找到比 Receiver 更近的有效深度，通常可返回 `visibility=1`。不过这只代表**所搜索样本内未发现遮挡物**，不保证完整光源可见性在几何上严格为 1；搜索样本不足会漏掉细小 Blocker。

### 8. PCSS 为什么容易出现噪声和伪影？

- Blocker Search Sample Count 太少。
- 深度线性化、Bias 或单位不一致。
- Blocker 与 Receiver 深度差很小，半影估计不稳定。
- 光源尺寸过大，搜索域超出 Shadow Map/Cascade。
- 在遮挡不连续处直接平均 Blocker 深度，丢失复杂几何关系。
- Filter Kernel 太大导致 Banding/Light Leak、性能下降。

提高 Sample Count 或使用降噪可以改善部分问题，但不能使 PCSS 成为无偏的真实面积光算法。

### 9. 一段不依赖具体投影的 PCSS 伪代码

~~~text
function PCSS(receiverLightData):
    zReceiver = LinearizeLightDepth(receiverLightData.depth)
    searchRadiusUV = ComputeBlockerSearchRadius(receiverLightData)

    blockers = []
    for uvOffset in SearchPattern:
        sampledDepth = ReadRawShadowDepth(receiverUV + uvOffset*searchRadiusUV)
        sampledLinearZ = LinearizeLightDepth(sampledDepth)
        if sampledLinearZ < zReceiver - linearBias:
            blockers.push(sampledLinearZ)

    if blockers is empty:
        return 1.0

    avgBlockerZ = average(blockers)
    penumbraWorld = lightWidth*(zReceiver-avgBlockerZ)/avgBlockerZ
    filterRadiusUV = ConvertPenumbraToShadowUV(penumbraWorld)

    return PCF(receiverUV, referenceShadowDepth, filterRadiusUV)
~~~

这是算法组织示例而非可直接粘贴的 GLSL：`ComputeBlockerSearchRadius`、`LinearizeLightDepth` 和 `ConvertPenumbraToShadowUV` 必须根据 Point/Spot/Directional 的 Light Projection 正确设计。

## 十、CSM：Cascaded Shadow Maps

### 1. 为什么大场景方向光需要 CSM？

方向光阴影常用正交投影。若一张 Shadow Map 需要覆盖相机近处到几公里远处的巨大范围，固定分辨率被大量世界面积分摊，近景每个 Shadow Texel 覆盖的世界空间区域太大，阴影严重锯齿。

CSM 将相机视锥沿深度划成多个段，每段使用一张或一块方向光 Shadow Map，近处覆盖较小空间获得高分辨率，远处覆盖较大空间保证视距。

### 2. CSM 按哪个深度划分？

通常按**主相机 View Space 的线性距离**或相机视锥的深度区间划分，而不是简单按非线性设备深度值均分。

每个 Cascade 都有：

- 该相机深度区间对应的一组 Frustum Corners。
- 一套 Light View/Orthographic Projection。
- Shadow Map 数据/Atlas Region/Array Layer。
- 接收像素的 Cascade Selection 规则。

### 3. CSM 的线性分割公式是什么？

相机 Near、Far 分别为 `n`、`f`，划分 `m` 级，令 `s=i/m`，其中 `i=1..m`：

$$
\boxed{
C_i^{\mathrm{lin}}=n+(f-n)\frac{i}{m}.
}
$$

线性分割给每一级几乎等宽的相机深度区间。

### 4. CSM 的对数分割公式是什么？

$$
\boxed{
C_i^{\mathrm{log}}=
n\left(\frac fn\right)^{i/m}.
}
$$

这使近处划分更密集，远处划分更稀疏，有利于相机透视投影下不同距离的几何尺度分布。

### 5. Practical Split Scheme 是什么？

常见做法按参数 `lambda∈[0,1]` 组合：

$$
\boxed{
C_i=
(1-\lambda)C_i^{\mathrm{lin}}
+\lambda C_i^{\mathrm{log}}.
}
$$

`lambda=0` 为纯线性，`lambda=1` 为纯对数。中间值结合近景精度与远景覆盖需求。

### 6. 为什么 Cascade 数量不是越多越好？

增加 Cascade 数可更细地划分分辨率，但同时增加：

- Shadow Casters 的渲染和剔除开销。
- Light View-Projection 矩阵及数据管理。
- 阴影 Atlas/Array 资源分配成本。
- Cascade Selection/Blend 成本。
- 相机移动时的分界与稳定性问题。

工程上要按场景范围、GPU、物体大小和质量需求选择。

### 7. 如何构造每一级 Cascade 的 Light Orthographic Projection？

典型思路：

1. 根据相机 View/Projection 和当前 Cascade Near/Far，求该段 Frustum 的八个角点。
2. 将角点从 View/World Space 转换到 Light View Space。
3. 求适合覆盖这些点的 XY 边界。
4. 构造 Light Orthographic Projection，把该范围映射到 Shadow Map。
5. Light Z 范围还需考虑**实际可能投射阴影的 Casters**，不能只按 Receiver Frustum Corners 收得过紧。

**易错点：** 若 Light Z Near/Far 只包住相机视锥角点，视锥外但能把阴影投进视锥内的物体可能被错误裁掉，出现漏影。

### 8. 什么叫 Stable CSM？

普通 Tight Frustum Fit 在相机小幅平移或旋转时，Shadow Projection 的尺寸、中心和阴影 Texel 网格可能变化，使阴影边缘出现 Shimmering/Swimming。

Stable CSM 常通过：

- 使用更稳定的 Cascade 外包范围（如包围球拟合）。
- 固定每 Cascade 的投影尺寸/尺度。
- 将 Shadow Projection 在光源空间**对齐到 Shadow Texel 网格**。
- 维持稳定 Light Basis/Orientation。

减少相机微小移动造成的阴影采样不稳定。

### 9. Texel Snapping 是怎么计算的？

假设一个 Cascade 在光源空间 X 方向覆盖长度 `S_x`，Shadow Map 宽度为 `R_x`，则每个 Texel 对应：

$$
\boxed{
t_x=\frac{S_x}{R_x}.
}
$$

为了让光源空间投影中心 `c_x` 对齐固定 Texel 格点，可以将：

$$
c_x^{\mathrm{snap}}=
t_x\cdot\mathrm{round}\left(\frac{c_x}{t_x}\right).
$$

Y 同理。这里假设 Light Basis 与投影尺度保持稳定，否则只 Snap Center 不一定消除全部 Shimmering。

### 10. Cascade 分界为什么会出现明显颜色或阴影跳变？

相邻 Cascade 的分辨率、Depth Bias、PCF Kernel 世界尺度、Light Projection 以及 Shadow Texel 相位可能不同。Receiver 跨越 Split Plane 时突然换图，会出现明显不连续。

常用处理：

- 给相邻 Cascade 留重叠区。
- 在重叠区平滑混合两个 Cascade 的 Visibility。
- 尽量让 Filter Radius、Bias 和 World Units Per Texel 保持合理对应关系。
- 对 Level Selection 做更稳定的策略。

### 11. Cascade 级联的阴影是否必须各绘制一次全部场景？

不必。每级可以单独进行 Caster Culling、Shadow Receiver/Caster Bounds 计算，提交潜在影响该级的 Shadow Casters。重要优化是**避免所有对象重复写入每一级**。

也可以通过 Geometry/Mesh/Multiview/Instancing 等 API 策略合并工作，但需分析硬件和实际驱动成本。

## 十一、点光源与全向阴影（Omnidirectional Shadow）

### 1. 为什么 Point Light 往往使用 Cubemap Shadow？

点光源向球面各方向发光；Cubemap 六个面可覆盖近似整个球面方向范围。每个 Face 对应方向不同、通常 FOV 为 90° 的透视投影。

阴影渲染时，一个点光源可能需要处理六个方向视图；也存在 Dual-Paraboloid、Octahedral 和专门的 Ray Tracing 替代方案。

### 2. 点光 Cube Depth 常见两种存储方案是什么？

1. **硬件深度 Cubemap：** 存各 Cubemap Face 的投影深度 `z_window`，需要按对应 Face Projection 产生一致的比较参考深度。
2. **手动径向深度 Cubemap：** 在颜色/Float 目标中存 `distance(light,P)/farPlane` 等编码，采样方向后取得欧氏径向距离值并手动比较。

**非常重要：** 这两种深度并不相同。不能把归一化径向距离直接和透视 Depth Cubemap 的窗口深度比较。

### 3. 径向深度 Cubemap 的 Shadow Pass Fragment 示例

这里把归一化距离写入**单通道 Float 颜色附件**，不是深度附件：

~~~glsl
#version 450 core

in vec3 vWorldPosition;
uniform vec3 uLightPosition;
uniform float uFarPlane;

layout(location = 0) out float outRadialDepth;

void main()
{
    float radialDistance = length(vWorldPosition - uLightPosition);
    outRadialDepth = radialDistance / uFarPlane;
}
~~~

Shadow Pass 仍然需要深度测试以正确留下最近的表面；Color Attachment 中输出的径向值与硬件 Depth Attachment 的 Projection Depth 是两个不同量。

### 4. 径向深度的 Lighting Pass 怎么比较？

~~~glsl
uniform samplerCube uRadialShadowCube;
uniform vec3 uPointLightPosition;
uniform float uPointShadowFar;

float PointShadowVisibility(vec3 receiverPositionWS,
                            float radialBiasWorld)
{
    vec3 lightToReceiver = receiverPositionWS - uPointLightPosition;
    float distanceToLight = length(lightToReceiver);

    if (distanceToLight >= uPointShadowFar)
        return 1.0;

    float normalizedStored =
        texture(uRadialShadowCube, lightToReceiver).r;

    float storedDistance = normalizedStored * uPointShadowFar;
    return (distanceToLight - radialBiasWorld <= storedDistance)
        ? 1.0 : 0.0;
}
~~~

这段比较的两边单位都是 **World Distance**。如果要做 PCF，还需考虑 Cube Sampling 的方向扰动与邻域角度，不应直接拿屏幕空间 UV Texel 偏移套用。

### 5. 为什么上面的 Radial Depth 示例不能直接当完整 FBO 实现？

因为它只写了某些必要 Shader 行为；完整点光阴影还需要：

- 六 Face 的一致 View/Projection（或者等价多视图）。
- 正确的 Depth Attachment/Depth Test，保证最近几何写入。
- Cubemap Face/Layer 的资源选择、Viewport 和 Clear。
- 适当的 Color Float Format 与采样 Filter。
- 如果写 Color Radial Depth 且深度测试使用 Projection Z，要保证 Shadow Pass 的几何和 FBO 配置正确。
- 光源 Near/Far 与阴影采样范围匹配。

### 6. 为什么点光源 Shadow Cubemap 开销很大？

一个 Point Light 可以需要绘制六张方向深度图；大量动态点光会使 Caster Draw/Vertex Work、Shadow Atlas、显存和 Shadow Filtering 开销显著增加。

因此实际游戏往往对 Shadow-Casting Lights 数量、可见性、距离、更新频率、阴影分辨率设置预算。

## 十二、Shadow Atlas、Texture Array 与阴影缓存

### 1. 什么是 Shadow Atlas？

将多盏灯或多个 Cascade 的 Shadow Map 区域打包进一张较大 Texture，减少零散资源绑定和分配开销，便于统一内存预算与渲染调度。

Shadow Atlas 需要为每个 Tile 维护 Rect、Scale/Bias、Depth Range 和可能的 Border Padding。

### 2. 为什么 Filter Kernel 可能跨越 Atlas Tile 边界？

PCF/PCSS 在当前光源 Tile 附近采样时，若采样坐标跑到了相邻 Tile，可能读取另一盏灯的深度，产生脏边或奇怪阴影。

可采用：

- Tile 内缩范围与 Gutter/Padding。
- 在 Shader 中 Clamp 到当前 Tile 的合法采样区域。
- 适合的 Texture Array（各 Layer 独立），或其它 Texture View/Atlas 策略。
- 考虑 Filter Radius 最大覆盖范围。

### 3. Shadow Array 与 Atlas 各有什么优势？

| 组织方式 | 适用优势 | 注意事项 |
|---|---|---|
| 2D Texture Array | 多 Layer、每层独立坐标 | Layer 数、统一尺寸/格式约束 |
| 2D Shadow Atlas | 弹性排布不同分辨率的灯光区域 | Tile 边界、Padding、碎片化 |
| Cubemap/Cubemap Array | 点光全向阴影 | 6 Face、方向约定、资源与 Draw 成本 |
| Virtual Shadow Map/Page | 大范围高细节按需驻留 | Page Table、反馈与更新调度 |

### 4. 为什么 Shadow Map 适合缓存？

如果静态光源、静态几何及其影响范围不变，Shadow Depth 可以在多帧之间复用；没必要每帧重复构建同一份遮挡数据。

但是动态物体、动画、光源运动、Caster/Receiver Visibility、材质 Mask 改变时，应正确标记失效并更新必要区域。

### 5. Shadow Cache 最常见的错误是什么？

阴影缓存未正确失效：模型移动了，场景阴影仍停留在旧位置；或者只更新动态 Actor，却忘记某个静态对象更新了变形/可见性状态。

缓存能提升性能，但必然增加**正确的版本、依赖与失效管理**难度。

## 十三、VSM：Variance Shadow Maps

### 1. 为什么 VSM 与普通 PCF 不同？

普通 PCF 滤波的是**深度比较结果**。Variance Shadow Maps 在 Shadow Pass 中存储一组深度统计矩（Moments），可以对这些**统计值进行线性过滤**，然后用统计不等式估计当前 Receiver 被照亮的上界。

这让较大滤波核可以使用常规 Mipmap/Blur 和硬件纹理过滤，但引入显著的 Light Bleeding 风险。

### 2. VSM 要存哪两个 Moment？

对标量 Shadow Depth 随机变量 `Z`，常存：

$$
\boxed{
M_1=\mathbb E[Z],
\qquad
M_2=\mathbb E[Z^2].
}
$$

实际 Shadow Pass 可在浮点 Render Target 写 `z` 和 `z²`（还要考虑生成时的梯度修正、精度与过滤策略）。

### 3. 方差如何得到？

$$
\boxed{
\sigma^2=M_2-M_1^2.
}
$$

数值上还需防止浮点精度导致负方差、过小方差和对数值稳定性的损害：

~~~glsl
float variance = max(moment2 - moment1 * moment1,
                     minVariance);
~~~

### 4. 为什么能用 Chebyshev/Cantelli Bound 估计 Lit？

对 `t>μ` 的 Receiver Depth（普通 Near→0、Far→1），我们想估计在过滤范围内存储深度 `Z≥t` 的概率。Cantelli 单侧方差不等式给出：

$$
\boxed{
P(Z\ge t)\le
\frac{\sigma^2}{\sigma^2+(t-\mu)^2},
\quad t>\mu.
}
$$

因此一个常见的 VSM **上界式可见性估计**：

$$
V_{\mathrm{VSM}}(t)=
\begin{cases}
1,&t\le\mu,\\
\dfrac{\sigma^2}{\sigma^2+(t-\mu)^2},
&t>\mu.
\end{cases}
$$

**关键限定：** 这不是实际可见性概率的等式，它是统计上界，因此可能**过高估计照亮面积**，造成 Light Bleeding。

### 5. VSM 的 GLSL 示例

~~~glsl
float VSMVisibility(vec2 moments, float receiverDepth,
                    float minVariance)
{
    float mean = moments.x;
    float variance = max(moments.y - mean * mean,
                         minVariance);

    if (receiverDepth <= mean)
        return 1.0;

    float difference = receiverDepth - mean;
    return variance /
           (variance + difference * difference);
}
~~~

Shadow Texture 应存与 `receiverDepth` 完全一致的普通深度约定；`minVariance` 影响 Light Bleeding/Shadow Acne 的取舍。

### 6. VSM 为什么会出现 Light Bleeding？

滤波区可能同时包含一个很近的 Blocker 和很远的 Background/Geometry。方差因此增大，Cantelli Bound 可能对明明完全被遮挡的 Receiver 给出较高的“可能可见”上界。

特别是阴影深度不连续处，软化大核可能出现**阴影内部漏光**。

### 7. Bleeding Reduction 能彻底解决吗？

常见对 VSM 上界值进行非线性重映射：

~~~glsl
float ReduceLightBleeding(float p, float amount)
{
    return clamp((p - amount) / (1.0 - amount), 0.0, 1.0);
}
~~~

这是经验性偏差修正；可能压暗合法的部分半影，不是将 VSM 恢复为精确几何可见性。

## 十四、EVSM、MSM 与指数/矩阴影技术

### 1. EVSM（Exponential Variance Shadow Maps）解决什么？

EVSM 先通过指数函数变换深度，再存储变换后深度的 Moments，以便提高某些复杂深度分布下的阴影估计质量，降低部分 VSM Light Bleeding。

常用指数变换思路：

$$
Z_+=e^{c_+z},
\qquad
Z_-=-e^{-c_-z}.
$$

实际存储哪些正/负指数 Moments、是否减小/归一化指数范围及如何比较，需要严格遵循所选 EVSM 变体。

### 2. 为什么 EVSM 的指数不能无限调大？

`exp(c*z)` 随 `c` 增大可能溢出 Float/FP16 能表示的范围，或者使数值动态范围过大、精度变差。

EVSM 的稳定性依赖 Depth Range、指数系数、浮点格式、滤波精度和 Variance Clamp。**不能把提高指数当成无条件减少 Light Bleeding 的免费方案。**

### 3. VSM 与 EVSM 是否属于精确阴影？

一般不是。它们用统计 Moments 估计深度比较后的可见性分布，具有近似误差与潜在 Light Bleeding。

它们适合结合常规 Texture Filtering/Mipmap/Blur 实现较大滤波核，但正确性与 PCF 的逐样本深度比较语义不同。

### 4. MSM（Moment Shadow Mapping）为什么会被提出？

MSM 使用更多高阶深度矩等统计信息来估计深度分布，提高对复杂深度分布的约束能力，有机会减少部分 VSM/EVSM 的 Light Bleeding。

代价是更多通道、更复杂的数学重建、数值稳定性问题。**更多 Moments 不等于无条件精确且完全无漏光。**

### 5. PCF、VSM、EVSM、MSM 应怎么对比？

| 方法 | 核心机制 | 优点 | 主要风险 |
|---|---|---|---|
| PCF | 滤波二值深度比较 | 稳定直观，可用硬件 Compare | 大核采样成本、固定半影 |
| PCSS | 搜索 Blocker 后动态 PCF | 近似接触硬化 | Sample 成本、噪点、Bias 复杂 |
| VSM | 两个 Depth Moments + 方差上界 | 易做大范围线性滤波 | Light Bleeding |
| EVSM | 指数变换深度后存 Moments | 某些场景减少 Bleeding | 指数溢出、精度、仍有 Bleeding |
| MSM | 更多高阶 Moments | 对深度分布约束更强 | 存储、数值稳定与重建复杂 |

### 6. 为什么不能把 Shadow Map 的 Depth 用 Gaussian Blur 再做普通深度比较？

几何深度经过滤波会生成两个遮挡物之间根本不存在的“平均深度”，通常导致错误的前后遮挡判断。

PCF 是**先比较后过滤**；VSM/EVSM 是**过滤经定义的 Moments 后通过统计不等式估计可见性**，都不能等同于对深度直接模糊后再硬比较。

## 十五、Contact Shadows、屏幕空间与 Ray Traced Shadows

### 1. Contact Shadow 要解决什么问题？

低分辨率 Shadow Map、Bias、PCF/PCSS 滤波可能让物体与地面的接触处丢失细节、阴影悬浮或过分模糊。

Contact Shadow 通常采用短距离的 Screen-Space Ray March 或硬件 Ray Tracing，补充物体接触点附近的局部遮挡细节。

### 2. Screen-Space Contact Shadow 为什么有局限？

屏幕空间只能访问当前屏幕深度/可重建的可见几何，离屏物体或被其他表面遮挡的几何信息不完整，因此容易有：

- Screen Edge 缺失。
- 厚度假设造成错误遮挡。
- 运动时闪烁/噪点。
- 不完整的离屏阴影贡献。

它是补充 Shadow Map 的近场近似，而不是完整场景光线可见性的替代。

### 3. Ray Traced Shadow 的基本流程？

对某个 Receiver `P`，向光源上一个采样点 `Y` 发出 Shadow Ray：

~~~text
Origin = P + SurfaceOffset
Direction = normalize(Y - P)
TMin = small positive epsilon
TMax = distance(P,Y) - endpointEpsilon

Trace Scene Acceleration Structure
      |
      +-- Hit opaque blocker before Y -> occluded
      |
      +-- No hit before Y -> visible
~~~

对理想方向光射线方向固定、最大长度可由场景范围/系统策略决定。

### 4. 为什么 Shadow Ray 也需要 Bias/Epsilon？

如果从数值上恰好位于三角形表面起点发射，浮点误差可能让射线立刻命中其出发三角形产生 Self-Intersection Acne。

Ray Origin Offset/TMin 需要与场景尺度、浮点精度和几何属性相匹配；偏移过大也可能错过近距离 Blocker，导致漏影。

### 5. Ray Traced Area Shadow 为什么自然产生软边？

面积光源上的不同采样点对应不同的 Shadow Ray。把可见样本比例作为面积光照积分的近似，遮挡边界随着光源面积和几何关系自然产生 Penumbra。

但一条 Shadow Ray 只能给出一次二值结果，想降低噪声通常需要更多 Samples、时间积累或 Denoising。

### 6. BVH/Acceleration Structure 对阴影性能有什么影响？

硬件/软件 Ray Tracing 需要空间加速结构来快速寻找射线与场景几何的交点。动态物体变化带来 BLAS/TLAS 更新成本；复杂几何、透明材质、多层 Any-Hit 等都可能增加 Trace Cost。

### 7. Alpha-Masked 与半透明材质如何投射 RT 阴影？

- 完全不透明：遇到 Blocker 可较早终止 Shadow Ray。
- Alpha-Masked：交点需根据 Alpha Cutout/Opacity Test 判断是否真正阻挡。
- 连续半透明：需要计算透射/衰减或按光学模型处理，单个“是否命中”不足以精确得到彩色透明阴影。

真实 RT API 常有 Any-Hit、Opacity Micromap 或其它专门策略，性能和细节依硬件实现。

### 8. Shadow Map 与 RT Shadow 应当怎样选型？

考虑光源数量、光源形状、目标平台、光源/物体动态性、Shadow Distance、软阴影质量、硬件 RT 支持和实时预算。

方向光的大范围阴影可以与 CSM/Virtual Shadow Maps、近场 Contact Shadow、局部 RT Shadow 混合使用；没有一种方法在所有场景都绝对更优。

## 十六、透明、双面几何与特殊 Shadow Casters

### 1. Alpha-Test 植被为什么需要在 Shadow Pass 采样贴图？

叶片/栅栏的三角形通常几何上覆盖了空白区域，需要通过 Alpha Cutout 决定哪些位置真正遮挡光。若 Shadow Pass 忽略 Mask，整张矩形叶片 Mesh 可能投下实心阴影。

### 2. Alpha Blending 的玻璃能直接按普通深度投射正确透明阴影吗？

不能。单层普通 Shadow Depth 只记录最近遮挡深度，无法表达多层透射率、彩色吸收或折射光线路径。

可用 Dithered Shadow、Moment/Transmittance Shadow、Deep Shadow Map 或 Ray Traced Transmission 等按需求近似。**Masked 与 Translucent 是不同问题**。

### 3. 双面材质 Shadow Casting 要注意什么？

双面叶片、布料等可能从正背两侧可见。若仅按默认 Culling 绘制 Shadow Depth，部分面会消失，使阴影漏光。

需要按材质设置合适 Cull Mode、法线方向与 Bias；在双面叶片上用 Backface Shadow 技巧可能适得其反。

### 4. 为什么 Skinning / Wind Animation 可能让阴影抖动或脱体？

Shadow Pass 与 Main Pass 使用的动画时间、骨骼矩阵、顶点变形或 LOD 不一致，Shadow Depth 代表的几何就不是当前画面可见几何。

渲染架构上应保证共享/等价变形数据与必要同步，并正确触发 Cached Shadow 的失效。

### 5. 细小 Geometry 的阴影为何容易消失？

光源空间 Shadow Texel Footprint 可能比细线/栅栏宽，Rasterization 下 Coverage 不稳定；过大 Bias、Caster Culling 或过粗 Mip/滤波还会让小物体阴影变弱。

提高分辨率、改进 Coverage/软化策略、接触阴影补偿可能有帮助，必须先分清原因。

## 十七、Virtual Shadow Maps（VSM 名称碰撞提醒）

### 1. Virtual Shadow Maps 和 Variance Shadow Maps 是一回事吗？

**不是。** 两者常缩写为 `VSM`，但完全不同：

- **Variance Shadow Maps：** 用深度矩与方差不等式估计过滤后的阴影可见性。
- **Virtual Shadow Maps：** 将阴影深度资源虚拟化，按 Page/Tile 的需要驻留、生成和更新高分辨率阴影内容。

阅读 UE5 等引擎资料时要根据上下文判断 VSM 指哪一种。

### 2. Virtual Shadow Maps 的核心解决点是什么？

传统单张 Shadow Map 分辨率固定，覆盖大范围时近景精度不足。Virtual Shadow Maps 用虚拟地址空间与物理 Page Cache 按实际需要维护阴影数据，有机会在当前视图附近实现很高有效分辨率并减少无关区域写入。

### 3. Virtual Shadow Maps 大致如何组织？

~~~text
Receiver visible in camera
           |
           v
Request Shadow Virtual Pages
           |
           v
Resolve Residency / Page Table
           |
           v
Render Dirty / Missing Shadow Pages
           |
           v
Sample Shadow Virtual Address -> Physical Page
           |
           v
Depth Compare / Filtering
~~~

不同引擎的反馈、Cache、LOD、物体 Invalidations 和可见性处理细节可能不同，该图只是通用抽象。

### 4. Virtual Shadow Maps 为什么仍可能有明显性能开销？

- 大量动态 Shadow Casters 导致频繁 Page Invalidation。
- 大光源/大视野/高速相机移动造成更多 Page 请求与更新。
- Page Table、Feedback、Cache Residency 和同步开销。
- 大量灯光的 Page 资源分配、纹理带宽与 Filter Cost。

“Virtual”不是“不需要渲染阴影”，而是改变分辨率与工作分配方式。

### 5. Virtual Shadow Maps 与 CSM 是互斥的吗？

作为方向光 Shadow Representation，某些引擎会用 Virtual Shadow Maps 替换传统 CSM，但二者仍可共享针对可见范围、光源投影、Caster Culling、缓存、稳定性等设计思想。

具体平台是否同时使用、如何迁移，取决于引擎实现，而不是某个数学定理。
