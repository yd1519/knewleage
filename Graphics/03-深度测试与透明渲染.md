**本文统一约定（重要）：**

- 除非单独说明，示例采用传统 OpenGL 默认深度约定：投影后 NDC Z 范围 `[-1,1]`，Depth Range `[0,1]`，**Near → 0，Far → 1**。

## 一、为什么需要 Depth Buffer？

### 1. 什么是 Depth Test？

一个像素或采样点可能被多个三角形覆盖。**Depth Test** 用当前 Fragment 的深度与 Depth Buffer 中已有深度比较，决定这个片元（或 Sample）是否通过深度测试。

最常见的普通深度方式：

1. 清除深度为最大值 `1.0`。
2. 绘制一个新 Fragment，计算窗口深度 `z`。
3. 如果 `z < depthBuffer`，它比此前记录的表面更近，允许通过测试。
4. 在 Depth Write 开启且其余相关测试满足时写入新的深度。

这样可以避免对所有三角形进行严格的从远到近排序（对于普通不透明渲染）。

### 2. Depth Test 与 Depth Write 是一回事吗？

不是。可以**参与深度测试而不写入深度缓冲**。

| Depth Test | Depth Write | 典型行为 |
|---|---|---|
| 开 | 开 | 普通不透明几何 |
| 开 | 关 | 传统半透明几何，接受已有不透明深度的遮挡 |
| 关 | 关 | 某些全屏 UI / 后处理 |
| 关 | 开 | 一般需谨慎：具体 API 对测试关闭时深度写入的规则不同 |

在 OpenGL 中，用 `glDepthMask(GL_FALSE)` 禁止深度写入；`glDisable(GL_DEPTH_TEST)` 会禁用深度测试，而在传统 OpenGL 的行为中也不会进行通常的深度缓冲更新。不能把 `glDepthMask(GL_TRUE)` 理解为“无条件写深度”。

### 3. GL_LESS、GL_LEQUAL、GL_ALWAYS 分别表示什么？

常见 DepthFunc：

| 比较函数 | 通过条件 |
|---|---|
| `GL_NEVER` | 永远不通过 |
| `GL_LESS` | 新深度小于已有深度 |
| `GL_LEQUAL` | 小于或等于 |
| `GL_EQUAL` | 相等 |
| `GL_GREATER` | 新深度大于已有深度 |
| `GL_GEQUAL` | 大于或等于 |
| `GL_ALWAYS` | 永远通过 |

不同渲染 Pass 使用不同的深度函数。注意“相等”比较易受浮点与 Shader 路径差异影响。

### 4. 如果不透明物体从后往前绘制，Z-buffer 还正确吗？

只要深度状态和写入正确，最终的最近可见不透明表面通常仍正确。但是从后往前绘制可能产生更多无效 Fragment 着色（Overdraw），不一定高效。

**正确性与性能是两个问题。** 对不透明物体，Front-to-Back 常用于减少遮挡区域的昂贵像素着色，但不保证在所有引擎里总比材质排序划算。

### 5. Depth Buffer 与 Color Buffer 的 Sample 数必须一致吗？

它们属于 Framebuffer 附件，受到图形 API 对 Attachment 兼容性、Multisample 与 Framebuffer 完整性的约束。若开启 MSAA，深度/模板通常也按多样本存储；但不能简单假设 Depth 和 Color 在所有 API 与用法下都是相同的物理内存布局。

## 二、Depth 值的来源与数学推导

### 1. View-Space Z、Clip-Space Z、NDC Z、Window Depth 的关系？

按第一篇文档的右手相机约定，观察空间朝 `-Z` 看，物体在相机前方时 `z_view < 0`。

依次经过：

~~~text
View Space (z_view)
      |
      v
Projection -> Clip Space (z_clip, w_clip)
      |
      v
Perspective Divide -> z_ndc = z_clip / w_clip
      |
      v
Depth Range / Viewport -> z_window
      |
      v
Depth Test -> Depth Buffer
~~~

传统 OpenGL 默认 Depth Range 是 `[0,1]`：

$$
z_{\mathrm{window}}=\frac{z_{\mathrm{ndc}}+1}{2}.
$$

注意 Fragment Shader 里 `gl_FragCoord.z` 通常是窗口深度语义，**不是**原始 View Space Z。

### 2. 为什么透视投影的深度是非线性的？

令 `d = -z_view > 0` 表示沿视线的正距离，近、远裁剪距离分别为 `n`、`f`，其中 `0<n<f`。

在常规深度、窗口深度范围 `[0,1]` 的前提下：

$$
\boxed{
z(d)=\frac{f}{f-n}-\frac{fn}{(f-n)d}.
}
$$

验证边界：

$$
z(n)=0,\qquad z(f)=1.
$$

这个式子包含 `1/d`，因此深度不是按距离线性增长的。

### 3. 为什么 Near Plane 比 Far Plane 更影响深度精度？

对上式求导：

$$
\frac{\mathrm{d}z}{\mathrm{d}d}
=\frac{fn}{(f-n)d^2}.
$$

因此对于近似均匀量化的深度间隔 `Δz`：

$$
\boxed{
\Delta d\approx
\frac{(f-n)d^2}{fn}\,\Delta z.
}
$$

含义：同样一个深度量化误差，在更远处对应更大的几何距离误差。Near 过小会使高比例 `f/n` 下的远处精度更差。

这只是基于微分的**局部误差近似**；实际精度还受 Depth 格式和光栅化数值路径影响。

### 4. 如何从深度反推出 View-Space 距离？

从普通 `[0,1]` 深度公式解出 `d`：

$$
\boxed{
d=\frac{fn}{f-z(f-n)}.
}
$$

验证：`z=0` 得 `d=n`；`z=1` 得 `d=f`。

**常见错误：** 直接写 `d = z*f` 或线性地 `lerp(n,f,z)`，这对普通透视深度不成立。

### 5. 为什么 NDC 深度可以屏幕线性插值？

如第二篇所述，对已经投影的三角形，NDC Z 是屏幕平面上的仿射函数：

$$
z_{\mathrm{ndc}}(P)=
\lambda_0 z_{\mathrm{ndc},0}+
\lambda_1 z_{\mathrm{ndc},1}+
\lambda_2 z_{\mathrm{ndc},2}.
$$

**不要**像 UV 一样，再对三个顶点的 NDC Z 做一次 `1/w` 透视校正，那会得到错误的深度。

## 三、深度格式、精度与 Reversed-Z

### 1. D16、D24 和 D32F 有什么区别？

| 深度格式（概念） | 深度表示 | 常见权衡 |
|---|---|---|
| 16-bit UNORM Depth | 归一化定点量化 | 存储较省，量化精度相对较低 |
| 24-bit UNORM Depth | 归一化定点量化 | 传统常见，可能与 8-bit Stencil 组合 |
| 32-bit Float Depth | IEEE 风格单精度浮点 | 与 Reversed-Z 搭配常能改善大范围深度精度 |

硬件是否支持某格式、带宽/压缩表现及具体布局需要查相应 API 和设备能力。`D24S8` 是常见深度+模板组合，但不能理解为“24 bit 深度、8 bit 颜色”。

### 2. Z-Fighting 是什么？

两个表面的深度非常接近，在有限深度精度及光栅化数值误差下，它们可能得到相同或不稳定的 Depth 值，于是出现交替可见、闪烁或摩尔纹。

典型场景：共面 Decal/地板贴片、远处重叠几何、过小的 Near Plane。

**Z-Fighting 不总是因为深度位数不够。** 共面数据设计不合理、不同 Pass 深度计算不一致、过度 Depth Bias 等也可能导致问题。

### 3. 如何缓解 Z-Fighting？

优先按原因处理：

1. 合理增大 Near Plane，而非盲目把 Far Plane 缩到很小。
2. 对长视距渲染采用适配深度格式的 Reversed-Z。
3. 减少不必要的共面几何，或显式调整几何/Decal 方案。
4. 对特殊用途（如 Shadow Map）正确设置 Depth Bias。
5. 避免同一深度预处理与主 Pass 使用不一致的顶点变换/深度路径。

### 4. Reversed-Z 到底反转了什么？

传统普通深度：Near → `0`，Far → `1`，常用 `LESS`，清屏值 `1`。

Reversed-Z：Near → `1`，Far → `0`，常用 `GREATER`，清屏值 `0`。

在右手 View Space、`[0,1]` 裁剪深度下，有限远平面时：

$$
z_{\mathrm{rev}}(d)=
\frac{fn}{(f-n)d}-\frac{n}{f-n}.
$$

无限远平面极限：

$$
\boxed{z_{\mathrm{rev},\infty}(d)=\frac{n}{d}.}
$$

### 5. 为什么 Reversed-Z 与 Float Depth 格式特别适合？

浮点数在接近 `0` 时可表示值更密集。Reversed-Z 让远处深度趋近 `0`，其精度分布与透视深度对远距离的压缩在一定程度上互相抵消。

注意：**如果是均匀量化的定点 Depth，只反转数值大小并不会神奇提升量化精度。** Reversed-Z 的显著精度优势与浮点表示、Clip 深度约定等因素密切相关。

### 6. Reversed-Z 改造渲染器时容易漏什么？

至少检查：

- 投影矩阵与 Clip 深度范围，尤其是 OpenGL 的 `glClipControl` 配置。
- 清除深度改为 `0`，比较函数改为 `GREATER/GEQUAL`。
- 深度重建、SSR、SSAO、HZB、软粒子和自定义深度相关 Shader。
- Shadow Pass 与主视角深度是否使用相同约定——**不能默认影子图必须跟着主相机一起反转**。
- Depth Bias 和 Hi-Z 归约方向。
- Shader 中任何写死“近处深度更小”的逻辑。

## 四、Depth Bias 与 Polygon Offset

### 1. 什么是 Depth Bias？解决什么问题？

当两层几何深度非常接近，或 Shadow Map 中“同一表面在光源视角与相机视角的采样/计算结果略有差异”时，可以对参与深度比较的值加入适当偏移。

在 OpenGL 中，多边形 Offset 的典型概念形式为：

$$
\mathrm{offset}=m\cdot \mathrm{factor}+r\cdot\mathrm{units}.
$$

其中 `m` 表示屏幕空间深度坡度的最大量级，`r` 与可表示深度的分辨率/实现有关。它的实际定义与影响还应参考具体 OpenGL 规范及格式。

### 2. Constant Bias 与 Slope-Scale Bias 为什么要同时存在？

- Constant Bias：提供与坡度无关的偏移。
- Slope-Scale Bias：对深度随屏幕位置变化很陡的面给予更大的偏移。

表面越斜，光源/深度采样误差可能越明显，因此 Shadow Mapping 常组合使用这两种 Bias。

### 3. Bias 越大越好吗？

不是。Bias 不足可能出现 Shadow Acne（自阴影条纹）；Bias 过大又会造成 Peter Panning（阴影与物体分离）。

普通 Depth Bias 与 Shadow Bias 的使用目的有联系，但不是所有情境都按同一参数或方向设置。Reversed-Z 时偏移方向也要重新核对。

### 4. 为什么“所有物体给固定 Z 偏移”不是可靠方案？

它可能破坏真实遮挡、造成不同距离/角度下不一致的偏移，而且往往只是掩盖错误几何或错误深度约定。

应优先弄清楚偏移发生在几何空间、View Space、Clip Space，还是硬件 Depth Bias 机制。

## 五、Early-Z、Late-Z 与 Depth Pre-Pass

### 1. Early-Z 的目的是什么？

若 Fragment 注定被已有深度遮挡，则没必要执行昂贵的像素着色。Early-Z 允许在 Shader 前拒绝部分不可见的 Fragment。

典型好处：减少 Overdraw 场景下的 Fragment Shader 运算、纹理访问和材料计算。

### 2. Depth Test 打开后就保证 Early-Z 吗？

**不能保证。** 影响包括：

- Shader 修改 Fragment Depth。
- `discard`、Alpha-to-Coverage、Sample Mask 等改变覆盖的操作。
- 某些 Image/UAV/SSBO 写入和其他 Shader Side Effect。
- GPU 架构、API 的执行语义和驱动优化。

不能简单宣称“只要出现 discard 就完全失去 Early-Z”，也不能宣称“Depth Test 一定总在 Shader 前完成”。具体行为要以 API/实现为准。

### 3. OpenGL 中 early_fragment_tests 的作用是什么？

在支持的 GLSL 版本/扩展下，可声明：

~~~glsl
layout(early_fragment_tests) in;
~~~

用于请求某些深度/模板等 Early Fragment Tests 的规定执行语义，但**会影响写深度和副作用相关的行为**，不是万能性能开关。特别是提前深度测试与着色器写入 `gl_FragDepth` 的组合需要按规范判断，不应随意启用。

### 4. 什么是 Depth Pre-Pass / Z-Prepass？

先运行一个主要输出深度的 Pass，填好 Depth Buffer；后续正式 Shading Pass 通过相应深度测试来减少被遮挡表面的像素着色。

~~~text
Depth Pre-Pass (Depth Write ON, Color Write OFF)
                  |
                  v
        Populate Depth Buffer
                  |
                  v
Main Opaque Shading Pass
(Depth Test ON, depth write normally OFF or as designed)
                  |
                  v
           Lighting / Color
~~~

使用预通过的深度时，主 Pass 经常会用 `EQUAL` 或其他匹配的深度比较设置，具体取决于一致性和引擎设计。

### 5. Depth Pre-Pass 一定更快吗？

不一定，可能付出：

- 额外的顶点变换和图元提交成本。
- 对 Alpha-Test 几何可能需要额外采样以确定有效 Coverage。
- 额外的 Depth Bandwidth 与 Pass/状态切换。
- 原本已较好利用 Early-Z/Hi-Z 时，收益有限。

当材质 Shader 很昂贵、Overdraw 很高时可能更有价值。实际应分别测量 Opaque/Masked、复杂几何与不同 GPU。

### 6. Early-Z、Depth Pre-Pass、Hi-Z 三者区别？

- Early-Z：**时间上更早**进行深度拒绝，减少昂贵片元着色。
- Depth Pre-Pass：**额外绘制一遍**几何建立深度信息。
- Hi-Z：使用**层次化的深度表示**做粗粒度深度拒绝或遮挡查询。

它们不是互斥关系。Depth Pre-Pass 可以为后续深度剔除建立更完整的信息，硬件可能利用 Hi-Z 优化 Early-Z。

## 六、Hi-Z / Hierarchical Z 与遮挡剔除

### 1. Hi-Z 的基本思想是什么？

把 Depth Buffer 组织成多分辨率层次。较高层级的一个 Texel 代表更大屏幕区域的保守深度信息，从而在**粗粒度**判断图元或物体是否被遮挡。

典型有两类应用：

1. GPU 内部层次深度测试：作为硬件光栅化/Depth 单元的加速手段。
2. 引擎自己建立 HZB（Hierarchical Z Buffer）纹理：用于 Occlusion Culling、屏幕空间效果等。

两者共享思想，但不能认为它们必定是同一个 Buffer 或公开了相同 API。

### 2. 普通 LESS 深度下应做 Min 还是 Max 归约？

**没有脱离比较目标的通用答案。**

对于一种常见的**保守遮挡拒绝**策略：当前块已完全由遮挡物覆盖，要证明候选几何在该块的所有像素之后，需要知道已有深度的**最远值**（普通 LESS 深度下数值较大），所以可使用 **Max 深度金字塔**。

例如已覆盖的 2×2 深度分别是：

~~~text
0.20   0.35
0.40   0.60
~~~

若候选几何在该区域的**最近可能深度**仍大于 `0.60`，它就比该块所有已有表面更远，可以整体拒绝。

**额外前提：** 上述块必须具备保守的有效 Coverage，不能用空洞处清屏深度随意做“已遮挡”的结论。几何深度界限和不同分辨率查询也要保守处理。

### 3. Reversed-Z 需要改变归约方向吗？

若使用类似的保守逻辑，Reversed-Z 中**数值越大通常越近**，因此判断候选是否处处在已有表面之后时，可能需要该块已有深度的**最小值**。

所以面试时不要死背“Hi-Z 一定 Max”。要说明当前 Depth Compare、查询目标以及被遮挡块的 Coverage 前提。

### 4. HZB 可以替代 Frustum Culling 或 PVS 吗？

不能完全替代：

- Frustum Culling：排除视锥之外的对象。
- PVS：预计算某些观察位置的潜在可见集合。
- HZB Occlusion：利用某帧的深度/空间信息判断**屏幕空间遮挡**。

实践中常组合这些方法；HZB 可能存在查询时延、可见性保守性与动态遮挡问题，尤其不能把“没查到可见”直接当成绝对可靠的删除理由。

## 七、Stencil Buffer 的原理

### 1. Stencil Test 与 Depth Test 各做什么？

Depth Test 比较深度，Stencil Test 使用每 Sample 的整数模板值与 Reference/Mask 做比较，可用于**标记屏幕区域、限定后续绘制或实现特殊几何算法**。

常见 Stencil 格式是 8-bit，但具体位数取决于附件格式。

### 2. Stencil Test 需要配置哪些状态？

- StencilFunc：Comparison、Reference、Read Mask。
- StencilOp：Stencil 失败、Depth 失败、两个测试都通过时，各自执行什么操作。
- Stencil Write Mask：哪些位允许写入。

与 Depth Test 不同，Stencil 不直接表达“哪个三角形更近”，它表达的是一个**可被程序定义的标签/计数/掩码**。

### 3. sfail、dpfail、dppass 分别是什么？

以 OpenGL `glStencilOp(sfail,dpfail,dppass)` 为例：

| 参数 | 条件 | 操作触发时机（逻辑语义） |
|---|---|---|
| `sfail` | 模板测试未通过 | 可以保持、替换、递增等 |
| `dpfail` | 模板通过，但深度未通过 | 根据对应操作更新模板值 |
| `dppass` | 模板和深度均通过（或深度测试禁用后的相应情形） | 根据对应操作更新模板值 |

Stencil 更新还受 Stencil Write Mask 影响。未产生 Fragment、被其他规则丢弃或不符合相关写入条件时，并非一定会执行以上更新。

### 4. Stencil 如何实现一个简单的模型描边？

常见两遍方案：

1. 正常绘制模型，同时把通过测试的像素模板值设置为 `1`。
2. 把模型略微放大（或沿法线外扩），只在模板值**不等于 1** 的区域绘制纯色。

实现时需要注意深度测试、缩放方向、是否造成背面穿插以及模板写入是否被正确关闭。

### 5. Stencil Shadow Volume 为什么会被问到？

经典 Shadow Volume 根据遮挡体对光源构造一个体积，通过它的前/后面与深度/模板操作统计相机可见位置是否处于阴影体内部。

- Z-pass：依据通过深度测试的面更新模板计数；相机位于阴影体内时需额外处理。
- Z-fail / Carmack's Reverse：依据深度失败的面更新模板，适合解决某些相机位于阴影体内的情况。

现代常见实时阴影更偏向 Shadow Map/RT，但此题能够检验 Stencil 的实际理解。

## 八、Opaque、Masked 与 Transparent 是三类不同问题

### 1. 什么是不透明（Opaque）材质？

通常一个表面在其覆盖的 Sample 上完全遮住后面的表面，Depth Test 与 Depth Write 可正常参与确定最近表面。

这种渲染与 Z-buffer 非常匹配。

### 2. Alpha Test / Masked 材质是什么？

根据 Alpha 与阈值做**二值覆盖**判断。例如围栏、树叶、镂空贴图。

~~~glsl
#version 450 core
in vec2 vUV;
uniform sampler2D uMask;
layout(location = 0) out vec4 outColor;

void main()
{
    float alpha = texture(uMask, vUV).a;
    if (alpha < 0.5)
        discard;

    outColor = vec4(0.1, 0.8, 0.2, 1.0);
}
~~~

通过的片元通常像不透明表面一样参与深度写入；被丢弃部分不应遮挡后面的物体。

阈值式覆盖会产生明显的 Alpha Edge Aliasing，特别是细树叶、栅栏等。

### 3. Transparent / Translucent 与 Masked 的本质区别是什么？

**Masked：** 二值决定是否覆盖，能按常见 Z-buffer 逻辑确定“最近不透明表面”。

**Transparent：** 一个像素可以同时看到多层表面，颜色必须由**多层的贡献与顺序**计算。单个最近深度值本身不足以表示这些层。

### 4. 为什么透明物体通常关闭 Depth Write，但保留 Depth Test？

如果第一层透明材质写入了最近深度，后面的透明层可能被深度测试直接拒绝，从而失去其应有的颜色贡献。

常见设置：

- Opaque 先绘制：Depth Test ON，Depth Write ON。
- Transparent 后绘制：Depth Test ON，Depth Write OFF，Blending ON，通常 Back-to-Front 排序。

Depth Test 保证透明表面能被前景不透明物体遮挡；关闭 Depth Write 保证其他透明层仍有机会参与合成。

**局限：** 关闭 Depth Write 不自动解决透明层之间的排序问题。

## 九、Alpha Blending 的物理含义与公式

### 1. Alpha 可以代表哪些不同含义？

在具体实现里，Alpha 可能表示：

- 透明/不透明程度或表面覆盖率。
- 贴图二值遮罩。
- 渲染目标中与合成相关的 Alpha 通道。
- 某种业务自定义数据。

不同语义不应混用。常见 `source-over` 合成使用 Alpha 作为层的有效不透明程度/覆盖贡献，**它不是物理折射率**。

### 2. Straight Alpha 与 Premultiplied Alpha 是什么？

设表面直通道颜色为 `C_s`，Alpha 为 `α_s`。

- Straight / Unassociated：存储 `(C_s, α_s)`，RGB 尚未乘 Alpha。
- Premultiplied / Associated：存储 `(α_s C_s, α_s)`，RGB 已经乘过 Alpha。

两种表示都能进行透明合成，但 **Shader 输出格式、BlendFunc、贴图过滤与中间 Render Target 的表示必须匹配**。

### 3. Straight Alpha 的“前景盖到不透明背景”公式？

若目标背景已不透明 `α_d=1`，且颜色在线性空间中：

$$
\boxed{
C_{\mathrm{out}}=
\alpha_s C_s+(1-\alpha_s)C_d.
}
$$

例如红色前景 `C_s=(1,0,0)`、蓝色背景 `C_d=(0,0,1)`、`α_s=0.25`：

$$
C_{\mathrm{out}}=
0.25(1,0,0)+0.75(0,0,1)
=(0.25,0,0.75).
$$

这里的式子已经假设背景 `C_d` 是不透明目标颜色。

### 4. 两个都可能半透明的图层，正确的 source-over 是什么？

用 Premultiplied Color `c_s=α_s C_s` 与 `c_d=α_d C_d` 表示：

$$
\boxed{
c_{\mathrm{out}}=c_s+(1-\alpha_s)c_d,
}
$$

$$
\boxed{
\alpha_{\mathrm{out}}=
\alpha_s+(1-\alpha_s)\alpha_d.
}
$$

若最终需要 Straight RGB，且 `α_out>0`，才做 `C_out = c_out / α_out`。

**易错点：** 如果用 Straight RGB 做完整多层合成，不能只写 `C_out = α_s C_s + (1-α_s)C_d` 而无视目标 Alpha；那只是目标已不透明，或目标颜色本身已按合适的关联约定表示时的特例。

### 5. Premultiplied Alpha 为什么适合中间渲染与过滤？

- 零 Alpha 像素的颜色贡献也是零，避免透明贴图边缘 RGB 污染更容易。
- 图层合成公式简单，便于连续合成和部分滤波场景。
- 和许多图形 UI / 后处理流程的中间目标表示更契合。

但从 Straight 转 Premultiplied 应在正确**线性颜色空间**内进行，不能忽略 sRGB 解码/编码。

### 6. Alpha 合成满足交换律吗？

通常**不满足**，所以透明物体顺序很关键。

以前景 A（红色）和 B（蓝色）都具有 `α=0.5`，叠加在黑色不透明背景上：

先 B 后 A：

$$
C_{A\text{ over }B}
=0.5(1,0,0)+0.5[0.5(0,0,1)]
=(0.5,0,0.25).
$$

先 A 后 B：

$$
C_{B\text{ over }A}
=0.5(0,0,1)+0.5[0.5(1,0,0)]
=(0.25,0,0.5).
$$

结果不同。正确配合 Premultiplied 的 `source-over` 在精确算术下满足**结合律**，但通常不满足交换律。真实浮点渲染还可能出现舍入差异。

## 十、Blend State 与 OpenGL 示例

### 1. Blending 一般在哪个阶段发生？

在 Fragment Shader 产生输出颜色后，按照 Blend State 将 Source 与 Framebuffer 目标值合成。它与 Depth/Stencil 等 Fragment Operations 的具体优化次序由 API 和实现控制。

**注意：** 混合发生前，目标颜色格式及颜色空间必须明确。特别是 sRGB Framebuffer 和整数格式，对 Blend 的支持和行为不同。

### 2. Straight Alpha 渲染到不透明背景怎么设置？

~~~cpp
glEnable(GL_BLEND);
glBlendEquation(GL_FUNC_ADD);

// RGB = src.rgb * src.a + dst.rgb * (1-src.a)
// Alpha = src.a + dst.a * (1-src.a)
glBlendFuncSeparate(
    GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA,
    GL_ONE,       GL_ONE_MINUS_SRC_ALPHA
);

glEnable(GL_DEPTH_TEST);
glDepthFunc(GL_LESS);
glDepthMask(GL_FALSE); // Transparent pass 通常不写 Depth

// 绘制按 Back-to-Front 排序的透明物体...

glDepthMask(GL_TRUE);
glDisable(GL_BLEND);
~~~

这套设置的前提是 Shader 输出 **Straight RGB**，Render Target 接收相应颜色/Alpha 合成，且背景已按需要建立。

### 3. Premultiplied Alpha 应如何设置？

Shader 输出的 RGB 已经乘 Alpha：

~~~glsl
vec4 raw = texture(uTexture, vUV); // 假设 raw.rgb 是 Straight RGB
vec4 outColor = vec4(raw.rgb * raw.a, raw.a);
~~~

对应 OpenGL：

~~~cpp
glEnable(GL_BLEND);
glBlendEquation(GL_FUNC_ADD);
glBlendFuncSeparate(
    GL_ONE, GL_ONE_MINUS_SRC_ALPHA,
    GL_ONE, GL_ONE_MINUS_SRC_ALPHA
);
~~~

**禁止混用：** 对已经 Premultiply 的 RGB 再设置 `GL_SRC_ALPHA`，会在 RGB 上额外乘一次 Alpha，边缘通常会错误地变暗。

### 4. 为什么不能仅使用 glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA)？

如果 RGB 采用 Straight 输入，那么这组系数对 RGB 正确；但它也会默认应用于 Alpha 通道，导致源 Alpha 再乘自身：

~~~text
alpha_out_wrong = alpha_s * alpha_s
                + alpha_d * (1 - alpha_s)
~~~

对于希望正确保存复合后 Alpha 的 Render Target，应使用 `glBlendFuncSeparate` 或与数据表示一致的其他设置。

**注意：** 如果目标始终不透明，Alpha 输出可能不参与后续运算，错误不一定立刻可见，但不能把它当成一般正确公式。

### 5. 加法混合（Additive Blending）为什么经常不需要传统的远近排序？

常见发光粒子等效果可使用近似加法：

~~~cpp
glBlendEquation(GL_FUNC_ADD);
glBlendFunc(GL_ONE, GL_ONE);
~~~

在没有饱和截断、浮点舍入和其他非线性处理的理想情况下，加法具有交换性，因此颜色贡献对层顺序不敏感。但仍需决定与不透明深度的遮挡关系，并考虑 HDR 格式和后处理。

### 6. Alpha Blending 为什么应该在线性空间进行？

sRGB 编码值不与光能线性成比例。直接对编码后的 RGB 做线性混合，会得到不正确的亮度变化。

正确的典型流程：

~~~text
Sample sRGB Texture -> Decode to Linear
                              |
                              v
                    Shader Linear RGB
                              |
                              v
                     Blend in Linear
                              |
                              v
          Tone Mapping / Display Transform / Encode
~~~

具体 sRGB Framebuffer Blend 与自动转换行为要参考 API 状态；不能假设任何 UNORM Color Attachment 都会自动替你做线性合成。
