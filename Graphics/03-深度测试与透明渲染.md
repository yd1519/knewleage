**本文统一约定（重要）：**

## 一、为什么需要 Depth Buffer？

### 1. 什么是 Depth Test？

一个像素或采样点可能被多个三角形覆盖。**Depth Test** 用当前 Fragment 的深度与 Depth Buffer 中已有深度比较，决定这个片元（或 Sample）是否通过深度测试。

最常见的普通深度方式：

1. 清除深度为最大值 `1.0`。
2. 绘制一个新 Fragment，计算窗口深度 `z`。
3. 如果 `z < depthBuffer`，它比此前记录的表面更近，允许通过测试。
4. 在 Depth Write 开启且其余相关测试满足时写入新的深度。

这样可以避免对所有三角形进行严格的从远到近排序（对于普通不透明渲染）。

### 2. Depth Test 与 Depth Write 是一回事吗？

不是。可以**参与深度测试而不写入深度缓冲**。

| Depth Test | Depth Write | 典型行为 |
|---|---|---|
| 开 | 开 | 普通不透明几何 |
| 开 | 关 | 传统半透明几何，接受已有不透明深度的遮挡 |
| 关 | 关 | 某些全屏 UI / 后处理 |
| 关 | 开 | 一般需谨慎：具体 API 对测试关闭时深度写入的规则不同 |

在 OpenGL 中，用 `glDepthMask(GL_FALSE)` 禁止深度写入；`glDisable(GL_DEPTH_TEST)` 会禁用深度测试，而在传统 OpenGL 的行为中也不会进行通常的深度缓冲更新。不能把 `glDepthMask(GL_TRUE)` 理解为“无条件写深度”。

### 3. GL_LESS、GL_LEQUAL、GL_ALWAYS 分别表示什么？

常见 DepthFunc：

| 比较函数 | 通过条件 |
|---|---|
| `GL_NEVER` | 永远不通过 |
| `GL_LESS` | 新深度小于已有深度 |
| `GL_LEQUAL` | 小于或等于 |
| `GL_EQUAL` | 相等 |
| `GL_GREATER` | 新深度大于已有深度 |
| `GL_GEQUAL` | 大于或等于 |
| `GL_ALWAYS` | 永远通过 |

不同渲染 Pass 使用不同的深度函数。注意“相等”比较易受浮点与 Shader 路径差异影响。

### 4. 如果不透明物体从后往前绘制，Z-buffer 还正确吗？

只要深度状态和写入正确，最终的最近可见不透明表面通常仍正确。但是从后往前绘制可能产生更多无效 Fragment 着色（Overdraw），不一定高效。

**正确性与性能是两个问题。** 对不透明物体，Front-to-Back 常用于减少遮挡区域的昂贵像素着色，但不保证在所有引擎里总比材质排序划算。

### 5. Depth Buffer 与 Color Buffer 的 Sample 数必须一致吗？

它们属于 Framebuffer 附件，受到图形 API 对 Attachment 兼容性、Multisample 与 Framebuffer 完整性的约束。若开启 MSAA，深度/模板通常也按多样本存储；但不能简单假设 Depth 和 Color 在所有 API 与用法下都是相同的物理内存布局。

## 二、Depth 值的来源与数学推导

### 1. View-Space Z、Clip-Space Z、NDC Z、Window Depth 的关系？

按第一篇文档的右手相机约定，观察空间朝 `-Z` 看，物体在相机前方时 `z_view < 0`。

依次经过：

~~~text
View Space (z_view)
      |
      v
Projection -> Clip Space (z_clip, w_clip)
      |
      v
Perspective Divide -> z_ndc = z_clip / w_clip
      |
      v
Depth Range / Viewport -> z_window
      |
      v
Depth Test -> Depth Buffer
~~~

传统 OpenGL 默认 Depth Range 是 `[0,1]`：

$$
z_{\mathrm{window}}=\frac{z_{\mathrm{ndc}}+1}{2}.
$$

注意 Fragment Shader 里 `gl_FragCoord.z` 通常是窗口深度语义，**不是**原始 View Space Z。

### 2. 为什么透视投影的深度是非线性的？

令 `d = -z_view > 0` 表示沿视线的正距离，近、远裁剪距离分别为 `n`、`f`，其中 `0<n<f`。

在常规深度、窗口深度范围 `[0,1]` 的前提下：

$$
\boxed{
z(d)=\frac{f}{f-n}-\frac{fn}{(f-n)d}.
}
$$

验证边界：

$$
z(n)=0,\qquad z(f)=1.
$$

这个式子包含 `1/d`，因此深度不是按距离线性增长的。

### 3. 为什么 Near Plane 比 Far Plane 更影响深度精度？

对上式求导：

$$
\frac{\mathrm{d}z}{\mathrm{d}d}
=\frac{fn}{(f-n)d^2}.
$$

因此对于近似均匀量化的深度间隔 `Δz`：

$$
\boxed{
\Delta d\approx
\frac{(f-n)d^2}{fn}\,\Delta z.
}
$$

含义：同样一个深度量化误差，在更远处对应更大的几何距离误差。Near 过小会使高比例 `f/n` 下的远处精度更差。

这只是基于微分的**局部误差近似**；实际精度还受 Depth 格式和光栅化数值路径影响。

### 4. 如何从深度反推出 View-Space 距离？

从普通 `[0,1]` 深度公式解出 `d`：

$$
\boxed{
d=\frac{fn}{f-z(f-n)}.
}
$$

验证：`z=0` 得 `d=n`；`z=1` 得 `d=f`。

**常见错误：** 直接写 `d = z*f` 或线性地 `lerp(n,f,z)`，这对普通透视深度不成立。

### 5. 为什么 NDC 深度可以屏幕线性插值？

如第二篇所述，对已经投影的三角形，NDC Z 是屏幕平面上的仿射函数：

$$
z_{\mathrm{ndc}}(P)=
\lambda_0 z_{\mathrm{ndc},0}+
\lambda_1 z_{\mathrm{ndc},1}+
\lambda_2 z_{\mathrm{ndc},2}.
$$

**不要**像 UV 一样，再对三个顶点的 NDC Z 做一次 `1/w` 透视校正，那会得到错误的深度。

## 三、深度格式、精度与 Reversed-Z

### 1. D16、D24 和 D32F 有什么区别？

| 深度格式（概念） | 深度表示 | 常见权衡 |
|---|---|---|
| 16-bit UNORM Depth | 归一化定点量化 | 存储较省，量化精度相对较低 |
| 24-bit UNORM Depth | 归一化定点量化 | 传统常见，可能与 8-bit Stencil 组合 |
| 32-bit Float Depth | IEEE 风格单精度浮点 | 与 Reversed-Z 搭配常能改善大范围深度精度 |

硬件是否支持某格式、带宽/压缩表现及具体布局需要查相应 API 和设备能力。`D24S8` 是常见深度+模板组合，但不能理解为“24 bit 深度、8 bit 颜色”。

### 2. Z-Fighting 是什么？

两个表面的深度非常接近，在有限深度精度及光栅化数值误差下，它们可能得到相同或不稳定的 Depth 值，于是出现交替可见、闪烁或摩尔纹。

典型场景：共面 Decal/地板贴片、远处重叠几何、过小的 Near Plane。

**Z-Fighting 不总是因为深度位数不够。** 共面数据设计不合理、不同 Pass 深度计算不一致、过度 Depth Bias 等也可能导致问题。

### 3. 如何缓解 Z-Fighting？

优先按原因处理：

1. 合理增大 Near Plane，而非盲目把 Far Plane 缩到很小。
2. 对长视距渲染采用适配深度格式的 Reversed-Z。
3. 减少不必要的共面几何，或显式调整几何/Decal 方案。
4. 对特殊用途（如 Shadow Map）正确设置 Depth Bias。
5. 避免同一深度预处理与主 Pass 使用不一致的顶点变换/深度路径。

### 4. Reversed-Z 到底反转了什么？

传统普通深度：Near → `0`，Far → `1`，常用 `LESS`，清屏值 `1`。

Reversed-Z：Near → `1`，Far → `0`，常用 `GREATER`，清屏值 `0`。

在右手 View Space、`[0,1]` 裁剪深度下，有限远平面时：

$$
z_{\mathrm{rev}}(d)=
\frac{fn}{(f-n)d}-\frac{n}{f-n}.
$$

无限远平面极限：

$$
\boxed{z_{\mathrm{rev},\infty}(d)=\frac{n}{d}.}
$$

### 5. 为什么 Reversed-Z 与 Float Depth 格式特别适合？

浮点数在接近 `0` 时可表示值更密集。Reversed-Z 让远处深度趋近 `0`，其精度分布与透视深度对远距离的压缩在一定程度上互相抵消。

注意：**如果是均匀量化的定点 Depth，只反转数值大小并不会神奇提升量化精度。** Reversed-Z 的显著精度优势与浮点表示、Clip 深度约定等因素密切相关。

### 6. Reversed-Z 改造渲染器时容易漏什么？

至少检查：

- 投影矩阵与 Clip 深度范围，尤其是 OpenGL 的 `glClipControl` 配置。
- 清除深度改为 `0`，比较函数改为 `GREATER/GEQUAL`。
- 深度重建、SSR、SSAO、HZB、软粒子和自定义深度相关 Shader。
- Shadow Pass 与主视角深度是否使用相同约定——**不能默认影子图必须跟着主相机一起反转**。
- Depth Bias 和 Hi-Z 归约方向。
- Shader 中任何写死“近处深度更小”的逻辑。

## 四、Depth Bias 与 Polygon Offset

### 1. 什么是 Depth Bias？解决什么问题？

当两层几何深度非常接近，或 Shadow Map 中“同一表面在光源视角与相机视角的采样/计算结果略有差异”时，可以对参与深度比较的值加入适当偏移。

在 OpenGL 中，多边形 Offset 的典型概念形式为：

$$
\mathrm{offset}=m\cdot \mathrm{factor}+r\cdot\mathrm{units}.
$$

其中 `m` 表示屏幕空间深度坡度的最大量级，`r` 与可表示深度的分辨率/实现有关。它的实际定义与影响还应参考具体 OpenGL 规范及格式。

### 2. Constant Bias 与 Slope-Scale Bias 为什么要同时存在？

- Constant Bias：提供与坡度无关的偏移。
- Slope-Scale Bias：对深度随屏幕位置变化很陡的面给予更大的偏移。

表面越斜，光源/深度采样误差可能越明显，因此 Shadow Mapping 常组合使用这两种 Bias。

### 3. Bias 越大越好吗？

不是。Bias 不足可能出现 Shadow Acne（自阴影条纹）；Bias 过大又会造成 Peter Panning（阴影与物体分离）。

普通 Depth Bias 与 Shadow Bias 的使用目的有联系，但不是所有情境都按同一参数或方向设置。Reversed-Z 时偏移方向也要重新核对。

### 4. 为什么“所有物体给固定 Z 偏移”不是可靠方案？

它可能破坏真实遮挡、造成不同距离/角度下不一致的偏移，而且往往只是掩盖错误几何或错误深度约定。

应优先弄清楚偏移发生在几何空间、View Space、Clip Space，还是硬件 Depth Bias 机制。

## 五、Early-Z、Late-Z 与 Depth Pre-Pass

### 1. Early-Z 的目的是什么？

若 Fragment 注定被已有深度遮挡，则没必要执行昂贵的像素着色。Early-Z 允许在 Shader 前拒绝部分不可见的 Fragment。

典型好处：减少 Overdraw 场景下的 Fragment Shader 运算、纹理访问和材料计算。

### 2. Depth Test 打开后就保证 Early-Z 吗？

**不能保证。** 影响包括：

- Shader 修改 Fragment Depth。
- `discard`、Alpha-to-Coverage、Sample Mask 等改变覆盖的操作。
- 某些 Image/UAV/SSBO 写入和其他 Shader Side Effect。
- GPU 架构、API 的执行语义和驱动优化。

不能简单宣称“只要出现 discard 就完全失去 Early-Z”，也不能宣称“Depth Test 一定总在 Shader 前完成”。具体行为要以 API/实现为准。

### 3. OpenGL 中 early_fragment_tests 的作用是什么？

在支持的 GLSL 版本/扩展下，可声明：

~~~glsl
layout(early_fragment_tests) in;
~~~

用于请求某些深度/模板等 Early Fragment Tests 的规定执行语义，但**会影响写深度和副作用相关的行为**，不是万能性能开关。特别是提前深度测试与着色器写入 `gl_FragDepth` 的组合需要按规范判断，不应随意启用。

### 4. 什么是 Depth Pre-Pass / Z-Prepass？

先运行一个主要输出深度的 Pass，填好 Depth Buffer；后续正式 Shading Pass 通过相应深度测试来减少被遮挡表面的像素着色。

~~~text
Depth Pre-Pass (Depth Write ON, Color Write OFF)
                  |
                  v
        Populate Depth Buffer
                  |
                  v
Main Opaque Shading Pass
(Depth Test ON, depth write normally OFF or as designed)
                  |
                  v
           Lighting / Color
~~~

使用预通过的深度时，主 Pass 经常会用 `EQUAL` 或其他匹配的深度比较设置，具体取决于一致性和引擎设计。

### 5. Depth Pre-Pass 一定更快吗？

不一定，可能付出：

- 额外的顶点变换和图元提交成本。
- 对 Alpha-Test 几何可能需要额外采样以确定有效 Coverage。
- 额外的 Depth Bandwidth 与 Pass/状态切换。
- 原本已较好利用 Early-Z/Hi-Z 时，收益有限。

当材质 Shader 很昂贵、Overdraw 很高时可能更有价值。实际应分别测量 Opaque/Masked、复杂几何与不同 GPU。

### 6. Early-Z、Depth Pre-Pass、Hi-Z 三者区别？

- Early-Z：**时间上更早**进行深度拒绝，减少昂贵片元着色。
- Depth Pre-Pass：**额外绘制一遍**几何建立深度信息。
- Hi-Z：使用**层次化的深度表示**做粗粒度深度拒绝或遮挡查询。

它们不是互斥关系。Depth Pre-Pass 可以为后续深度剔除建立更完整的信息，硬件可能利用 Hi-Z 优化 Early-Z。

## 六、Hi-Z / Hierarchical Z 与遮挡剔除

### 1. Hi-Z 的基本思想是什么？

把 Depth Buffer 组织成多分辨率层次。较高层级的一个 Texel 代表更大屏幕区域的保守深度信息，从而在**粗粒度**判断图元或物体是否被遮挡。

典型有两类应用：

1. GPU 内部层次深度测试：作为硬件光栅化/Depth 单元的加速手段。
2. 引擎自己建立 HZB（Hierarchical Z Buffer）纹理：用于 Occlusion Culling、屏幕空间效果等。

两者共享思想，但不能认为它们必定是同一个 Buffer 或公开了相同 API。

### 2. 普通 LESS 深度下应做 Min 还是 Max 归约？

**没有脱离比较目标的通用答案。**

对于一种常见的**保守遮挡拒绝**策略：当前块已完全由遮挡物覆盖，要证明候选几何在该块的所有像素之后，需要知道已有深度的**最远值**（普通 LESS 深度下数值较大），所以可使用 **Max 深度金字塔**。

例如已覆盖的 2×2 深度分别是：

~~~text
0.20   0.35
0.40   0.60
~~~

若候选几何在该区域的**最近可能深度**仍大于 `0.60`，它就比该块所有已有表面更远，可以整体拒绝。

**额外前提：** 上述块必须具备保守的有效 Coverage，不能用空洞处清屏深度随意做“已遮挡”的结论。几何深度界限和不同分辨率查询也要保守处理。

### 3. Reversed-Z 需要改变归约方向吗？

若使用类似的保守逻辑，Reversed-Z 中**数值越大通常越近**，因此判断候选是否处处在已有表面之后时，可能需要该块已有深度的**最小值**。

所以面试时不要死背“Hi-Z 一定 Max”。要说明当前 Depth Compare、查询目标以及被遮挡块的 Coverage 前提。

### 4. HZB 可以替代 Frustum Culling 或 PVS 吗？

不能完全替代：

- Frustum Culling：排除视锥之外的对象。
- PVS：预计算某些观察位置的潜在可见集合。
- HZB Occlusion：利用某帧的深度/空间信息判断**屏幕空间遮挡**。

实践中常组合这些方法；HZB 可能存在查询时延、可见性保守性与动态遮挡问题，尤其不能把“没查到可见”直接当成绝对可靠的删除理由。

## 七、Stencil Buffer 的原理

### 1. Stencil Test 与 Depth Test 各做什么？

Depth Test 比较深度，Stencil Test 使用每 Sample 的整数模板值与 Reference/Mask 做比较，可用于**标记屏幕区域、限定后续绘制或实现特殊几何算法**。

常见 Stencil 格式是 8-bit，但具体位数取决于附件格式。

### 2. Stencil Test 需要配置哪些状态？

- StencilFunc：Comparison、Reference、Read Mask。
- StencilOp：Stencil 失败、Depth 失败、两个测试都通过时，各自执行什么操作。
- Stencil Write Mask：哪些位允许写入。

与 Depth Test 不同，Stencil 不直接表达“哪个三角形更近”，它表达的是一个**可被程序定义的标签/计数/掩码**。

### 3. sfail、dpfail、dppass 分别是什么？

以 OpenGL `glStencilOp(sfail,dpfail,dppass)` 为例：

| 参数 | 条件 | 操作触发时机（逻辑语义） |
|---|---|---|
| `sfail` | 模板测试未通过 | 可以保持、替换、递增等 |
| `dpfail` | 模板通过，但深度未通过 | 根据对应操作更新模板值 |
| `dppass` | 模板和深度均通过（或深度测试禁用后的相应情形） | 根据对应操作更新模板值 |

Stencil 更新还受 Stencil Write Mask 影响。未产生 Fragment、被其他规则丢弃或不符合相关写入条件时，并非一定会执行以上更新。

### 4. Stencil 如何实现一个简单的模型描边？

常见两遍方案：

1. 正常绘制模型，同时把通过测试的像素模板值设置为 `1`。
2. 把模型略微放大（或沿法线外扩），只在模板值**不等于 1** 的区域绘制纯色。

实现时需要注意深度测试、缩放方向、是否造成背面穿插以及模板写入是否被正确关闭。

### 5. Stencil Shadow Volume 为什么会被问到？

经典 Shadow Volume 根据遮挡体对光源构造一个体积，通过它的前/后面与深度/模板操作统计相机可见位置是否处于阴影体内部。

- Z-pass：依据通过深度测试的面更新模板计数；相机位于阴影体内时需额外处理。
- Z-fail / Carmack's Reverse：依据深度失败的面更新模板，适合解决某些相机位于阴影体内的情况。

现代常见实时阴影更偏向 Shadow Map/RT，但此题能够检验 Stencil 的实际理解。

## 八、Opaque、Masked 与 Transparent 是三类不同问题

### 1. 什么是不透明（Opaque）材质？

通常一个表面在其覆盖的 Sample 上完全遮住后面的表面，Depth Test 与 Depth Write 可正常参与确定最近表面。

这种渲染与 Z-buffer 非常匹配。

### 2. Alpha Test / Masked 材质是什么？

根据 Alpha 与阈值做**二值覆盖**判断。例如围栏、树叶、镂空贴图。

~~~glsl
#version 450 core
in vec2 vUV;
uniform sampler2D uMask;
layout(location = 0) out vec4 outColor;

void main()
{
    float alpha = texture(uMask, vUV).a;
    if (alpha < 0.5)
        discard;

    outColor = vec4(0.1, 0.8, 0.2, 1.0);
}
~~~

通过的片元通常像不透明表面一样参与深度写入；被丢弃部分不应遮挡后面的物体。

阈值式覆盖会产生明显的 Alpha Edge Aliasing，特别是细树叶、栅栏等。

### 3. Transparent / Translucent 与 Masked 的本质区别是什么？

**Masked：** 二值决定是否覆盖，能按常见 Z-buffer 逻辑确定“最近不透明表面”。

**Transparent：** 一个像素可以同时看到多层表面，颜色必须由**多层的贡献与顺序**计算。单个最近深度值本身不足以表示这些层。

### 4. 为什么透明物体通常关闭 Depth Write，但保留 Depth Test？

如果第一层透明材质写入了最近深度，后面的透明层可能被深度测试直接拒绝，从而失去其应有的颜色贡献。

常见设置：

- Opaque 先绘制：Depth Test ON，Depth Write ON。
- Transparent 后绘制：Depth Test ON，Depth Write OFF，Blending ON，通常 Back-to-Front 排序。

Depth Test 保证透明表面能被前景不透明物体遮挡；关闭 Depth Write 保证其他透明层仍有机会参与合成。

**局限：** 关闭 Depth Write 不自动解决透明层之间的排序问题。

## 九、Alpha Blending 的物理含义与公式

### 1. Alpha 可以代表哪些不同含义？

在具体实现里，Alpha 可能表示：

- 透明/不透明程度或表面覆盖率。
- 贴图二值遮罩。
- 渲染目标中与合成相关的 Alpha 通道。
- 某种业务自定义数据。

不同语义不应混用。常见 `source-over` 合成使用 Alpha 作为层的有效不透明程度/覆盖贡献，**它不是物理折射率**。

### 2. Straight Alpha 与 Premultiplied Alpha 是什么？

设表面直通道颜色为 `C_s`，Alpha 为 `α_s`。

- Straight / Unassociated：存储 `(C_s, α_s)`，RGB 尚未乘 Alpha。
- Premultiplied / Associated：存储 `(α_s C_s, α_s)`，RGB 已经乘过 Alpha。

两种表示都能进行透明合成，但 **Shader 输出格式、BlendFunc、贴图过滤与中间 Render Target 的表示必须匹配**。

### 3. Straight Alpha 的“前景盖到不透明背景”公式？

若目标背景已不透明 `α_d=1`，且颜色在线性空间中：

$$
\boxed{
C_{\mathrm{out}}=
\alpha_s C_s+(1-\alpha_s)C_d.
}
$$

例如红色前景 `C_s=(1,0,0)`、蓝色背景 `C_d=(0,0,1)`、`α_s=0.25`：

$$
C_{\mathrm{out}}=
0.25(1,0,0)+0.75(0,0,1)
=(0.25,0,0.75).
$$

这里的式子已经假设背景 `C_d` 是不透明目标颜色。

### 4. 两个都可能半透明的图层，正确的 source-over 是什么？

用 Premultiplied Color `c_s=α_s C_s` 与 `c_d=α_d C_d` 表示：

$$
\boxed{
c_{\mathrm{out}}=c_s+(1-\alpha_s)c_d,
}
$$

$$
\boxed{
\alpha_{\mathrm{out}}=
\alpha_s+(1-\alpha_s)\alpha_d.
}
$$

若最终需要 Straight RGB，且 `α_out>0`，才做 `C_out = c_out / α_out`。

**易错点：** 如果用 Straight RGB 做完整多层合成，不能只写 `C_out = α_s C_s + (1-α_s)C_d` 而无视目标 Alpha；那只是目标已不透明，或目标颜色本身已按合适的关联约定表示时的特例。

### 5. Premultiplied Alpha 为什么适合中间渲染与过滤？

- 零 Alpha 像素的颜色贡献也是零，避免透明贴图边缘 RGB 污染更容易。
- 图层合成公式简单，便于连续合成和部分滤波场景。
- 和许多图形 UI / 后处理流程的中间目标表示更契合。

但从 Straight 转 Premultiplied 应在正确**线性颜色空间**内进行，不能忽略 sRGB 解码/编码。

### 6. Alpha 合成满足交换律吗？

通常**不满足**，所以透明物体顺序很关键。

以前景 A（红色）和 B（蓝色）都具有 `α=0.5`，叠加在黑色不透明背景上：

先 B 后 A：

$$
C_{A\text{ over }B}
=0.5(1,0,0)+0.5[0.5(0,0,1)]
=(0.5,0,0.25).
$$

先 A 后 B：

$$
C_{B\text{ over }A}
=0.5(0,0,1)+0.5[0.5(1,0,0)]
=(0.25,0,0.5).
$$

结果不同。正确配合 Premultiplied 的 `source-over` 在精确算术下满足**结合律**，但通常不满足交换律。真实浮点渲染还可能出现舍入差异。

## 十、Blend State 与 OpenGL 示例

### 1. Blending 一般在哪个阶段发生？

在 Fragment Shader 产生输出颜色后，按照 Blend State 将 Source 与 Framebuffer 目标值合成。它与 Depth/Stencil 等 Fragment Operations 的具体优化次序由 API 和实现控制。

**注意：** 混合发生前，目标颜色格式及颜色空间必须明确。特别是 sRGB Framebuffer 和整数格式，对 Blend 的支持和行为不同。

### 2. Straight Alpha 渲染到不透明背景怎么设置？

~~~cpp
glEnable(GL_BLEND);
glBlendEquation(GL_FUNC_ADD);

// RGB = src.rgb * src.a + dst.rgb * (1-src.a)
// Alpha = src.a + dst.a * (1-src.a)
glBlendFuncSeparate(
    GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA,
    GL_ONE,       GL_ONE_MINUS_SRC_ALPHA
);

glEnable(GL_DEPTH_TEST);
glDepthFunc(GL_LESS);
glDepthMask(GL_FALSE); // Transparent pass 通常不写 Depth

// 绘制按 Back-to-Front 排序的透明物体...

glDepthMask(GL_TRUE);
glDisable(GL_BLEND);
~~~

这套设置的前提是 Shader 输出 **Straight RGB**，Render Target 接收相应颜色/Alpha 合成，且背景已按需要建立。

### 3. Premultiplied Alpha 应如何设置？

Shader 输出的 RGB 已经乘 Alpha：

~~~glsl
vec4 raw = texture(uTexture, vUV); // 假设 raw.rgb 是 Straight RGB
vec4 outColor = vec4(raw.rgb * raw.a, raw.a);
~~~

对应 OpenGL：

~~~cpp
glEnable(GL_BLEND);
glBlendEquation(GL_FUNC_ADD);
glBlendFuncSeparate(
    GL_ONE, GL_ONE_MINUS_SRC_ALPHA,
    GL_ONE, GL_ONE_MINUS_SRC_ALPHA
);
~~~

**禁止混用：** 对已经 Premultiply 的 RGB 再设置 `GL_SRC_ALPHA`，会在 RGB 上额外乘一次 Alpha，边缘通常会错误地变暗。

### 4. 为什么不能仅使用 glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA)？

如果 RGB 采用 Straight 输入，那么这组系数对 RGB 正确；但它也会默认应用于 Alpha 通道，导致源 Alpha 再乘自身：

~~~text
alpha_out_wrong = alpha_s * alpha_s
                + alpha_d * (1 - alpha_s)
~~~

对于希望正确保存复合后 Alpha 的 Render Target，应使用 `glBlendFuncSeparate` 或与数据表示一致的其他设置。

**注意：** 如果目标始终不透明，Alpha 输出可能不参与后续运算，错误不一定立刻可见，但不能把它当成一般正确公式。

### 5. 加法混合（Additive Blending）为什么经常不需要传统的远近排序？

常见发光粒子等效果可使用近似加法：

~~~cpp
glBlendEquation(GL_FUNC_ADD);
glBlendFunc(GL_ONE, GL_ONE);
~~~

在没有饱和截断、浮点舍入和其他非线性处理的理想情况下，加法具有交换性，因此颜色贡献对层顺序不敏感。但仍需决定与不透明深度的遮挡关系，并考虑 HDR 格式和后处理。

### 6. Alpha Blending 为什么应该在线性空间进行？

sRGB 编码值不与光能线性成比例。直接对编码后的 RGB 做线性混合，会得到不正确的亮度变化。

正确的典型流程：

~~~text
Sample sRGB Texture -> Decode to Linear
                              |
                              v
                    Shader Linear RGB
                              |
                              v
                     Blend in Linear
                              |
                              v
          Tone Mapping / Display Transform / Encode
~~~

具体 sRGB Framebuffer Blend 与自动转换行为要参考 API 状态；不能假设任何 UNORM Color Attachment 都会自动替你做线性合成。

## 十一、透明物体为什么必须排序？

### 1. 为什么 Opaque 不需要严格的透明式 Back-to-Front 排序？

对普通不透明表面，只有最近表面贡献颜色；Depth Buffer 可选择通过测试的最近表面。

对半透明表面，每一层都可能有贡献，而 `source-over` 不满足交换律。排序错误可能直接导致颜色错误。

### 2. 为什么传统半透明通常 Back-to-Front？

先绘制远处透明层，再绘制近处透明层，近处的 Source 才可以按 `source-over` 正确盖在已经积累的远处颜色上。

一种常见的渲染顺序：

~~~text
Clear Framebuffer + Depth
          |
          v
Opaque / Masked Pass
(Depth Test ON, Depth Write ON)
          |
          v
Transparent Pass
(Depth Test ON, Depth Write OFF,
 Blend ON, Back-to-Front)
          |
          v
Post Processing / Display
~~~

### 3. 透明排序到底以什么为单位？

可以按对象、Mesh、Submesh、Triangle，甚至每像素的 Fragment/Layer 排序。

| 排序粒度 | 成本 | 局限 |
|---|---|---|
| 按物体中心 | 通常较低 | 大物体、相交物体、环形物体容易错 |
| 按 Submesh | 相对可控 | Submesh 内三角形互相遮挡仍可能错 |
| 按三角形 | 通常昂贵，动态图元排序复杂 | 相交三角形可能不存在全局正确顺序 |
| 每像素深度层 | 内存/带宽/同步成本较高 | 需要 OIT 或多 Pass 等机制 |

因此“透明物体按距离排序”并不意味着一定能获得正确结果。

### 4. 为什么两个相互穿插的透明三角形可能无法全局正确排序？

如果 A 在屏幕某些区域位于 B 前面，另一些区域又位于 B 后面，那么全局只有 A-B 或 B-A 两种绘制顺序，**两种都可能在部分像素错误**。

这不是简单更换“物体中心距离”为“包围盒最远点距离”就能彻底解决的。

### 5. 透明深度写入能不能始终关闭？

对典型半透明 Surface，通常关闭是合理默认，但也有例外：

- 完全不透明或 Masked 部分可以进行 Depth 写入。
- 某些粒子特效会使用特殊深度策略。
- Water、Hair、Glass 可能拆分多个 Pass、使用 Depth Peeling 或其它特殊深度/深度代理。
- 根据材质、渲染路径和视觉目标设置不同策略。

工程上应该明确透明阶段究竟要模拟 **Coverage、表面传输还是某种特效近似**。

## 十二、Alpha-to-Coverage、Dither 与软粒子

### 1. Alpha-to-Coverage（A2C）是什么？

在启用 MSAA 时，可以把 Alpha 转换成像素内多 Sample 的 Coverage Mask：Alpha 越大，通常保留的 Sample 越多。

它并不是直接对颜色执行 `source-over`。经过 Sample Coverage 与 Resolve 后，可能得到一种近似连续的半透明效果。

### 2. Alpha-to-Coverage 为什么适合草叶、头发和栅栏？

这些材质往往本质上是“局部完全不透明，但结构很细”的 Coverage 问题，而非真正的薄玻璃连续透射。

A2C 可以减轻硬 Alpha Cutout 产生的边缘闪烁。不过：

- 有效 Coverage 档位受 Sample 数量与实现规则限制。
- 多层半透明的排序/透射仍未真正解决。
- Alpha-to-Coverage 可能与 MSAA Sample Pattern、其他覆盖规则相关。
- 不能简单把 A2C 当成所有 Transparency 的替代方案。

### 3. 为什么 Dithered Transparency 能在 TAA 下看起来更平滑？

按空间/时间变化的阈值把某些像素保留、某些丢弃；TAA 可在时间上积累这些覆盖变化，产生近似的平均透明度。

风险包括噪点、Ghosting、时间不稳定和在未启用相应抗锯齿时的明显颗粒感。

### 4. 什么是 Soft Particle？为什么需要 Scene Depth？

普通粒子与场景几何相交时可能出现生硬的边界。

Soft Particle 读取粒子与背景场景的 Depth，重建或比较两者的**同一线性视深度度量**，在距离很近时降低粒子 Alpha。

例如用线性深度差计算一个近似 Fade：

$$
\alpha_{\mathrm{soft}}=
\alpha_{\mathrm{base}}\,
\mathrm{clamp}\left(
\frac{d_{\mathrm{scene}}-d_{\mathrm{particle}}}{h},
0,1
\right).
$$

其中 `h>0` 是淡出距离，`d_scene` 与 `d_particle` 必须使用兼容的度量。Reversed-Z 下**不能直接用原始设备深度相减就当作线性距离**。

### 5. Alpha-to-Coverage 和 Alpha Blending 可以同时使用吗？

某些管线和材质可以组合，但 A2C 会改变覆盖，而 Alpha Blending 会改变颜色合成；叠加可能重复降低有效覆盖/不透明程度，需要明确目标效果和 API 实现。

## 十三、OIT（Order-Independent Transparency）核心方案

### 1. 什么是 OIT？它解决的核心问题是什么？

OIT 试图消除或减弱传统透明混合对**图元提交顺序**的依赖，让交错透明物体获得更正确或更稳定的结果。

OIT 并非一个固定算法，而是一类方法。需要区分：

- **Exact / 接近精确的逐像素排序合成**，通常存储更多透明层。
- **Approximate OIT**，通过统计量或加权近似，降低存储与排序开销。

即便某个算法被称为 OIT，也不代表它能精确模拟折射、吸收或多次散射。

### 2. Depth Peeling 的基本原理是什么？

每一轮根据深度约束从所有透明片元里选取一层，逐轮剥离并累计合成。

~~~text
Transparent Fragments
         |
         v
Pass 1: nearest visible layer
         |
         v
Pass 2: next layer behind the first
         |
         v
Pass 3: next layer ...
         |
         v
Composite in correct order
~~~

优点：可以按逐像素深度层进行较准确的排序合成（前提是剥离足够多层且正确处理深度相等和数值边界）。

缺点：可能需要多次几何绘制/Pass，性能随透明层数及实际停止策略变化。

### 3. Dual Depth Peeling 是什么思路？

每轮同时处理前面与后面的透明层，以减少处理同样深度层数时所需的 Pass 数量。仍然可能涉及多次几何或纹理操作，不能认为它完全消除了深度复杂度的成本。

### 4. A-Buffer / Per-Pixel Linked List（PPLL）的原理是什么？

把每个像素被多少透明 Fragment 覆盖以及各 Fragment 的深度、颜色、Alpha 保存下来，最终按该像素的深度顺序进行合成。

一种常见 PPLL 结构：

~~~text
Head Pointer Texture (per pixel)
            |
            v
Fragment Node 0: depth, color, alpha, next
            |
            v
Fragment Node 1: depth, color, alpha, next
            |
            v
Fragment Node 2: ...
~~~

一般流程：

1. 清空每像素链表头。
2. 每个透明 Fragment 通过原子操作从 Node Pool 获取节点。
3. 将 Fragment 数据放入节点，并链接到对应像素列表。
4. Fullscreen / Compute Pass 逐像素读取节点。
5. 在该像素内部排序，并按正确顺序合成。

### 5. PPLL 有哪些工程问题？

- 大量 Fragment 节点带来显存和带宽成本。
- 需要原子分配/链接，可能出现争用。
- Node Pool 固定容量容易溢出，必须定义 Overflow 策略。
- 每像素深度复杂度高度不均，排序成本可能很不稳定。
- 显存写入和 GPU 内存可见性同步需要正确处理。
- MSAA/多 View 时结构与内存需求更复杂。

**面试追问：** “PPLL 一定精确吗？”——若节点容量不足、丢失层或简化排序，结果也可能不精确。正常深度相等时还需确定 Tie-breaking 行为。

### 6. Weighted Blended OIT 为什么不需要逐像素排序？

它不保存每层精确顺序，而是把透明 Fragment 转换为可累积的加权颜色、Alpha 等统计信息，再用累积结果近似合成。

一个示意性的**加权累计量**为：

$$
C_{\mathrm{acc}}=
\sum_i \alpha_i w_i C_i,\qquad
W_{\mathrm{acc}}=
\sum_i \alpha_i w_i.
$$

在某些实现中还会累计 Revealage，例如：

$$
R=\prod_i(1-\alpha_i).
$$

可用加权颜色估计与 Revealage 来恢复近似透明结果。**上述式子用于解释概念，不是所有 Weighted Blended OIT 变体的完整实现公式**；各算法对深度权重、Revealage 和最终合成有不同规定。

累加与连乘的结果对片元提交顺序相对不敏感，因此可以近似 OIT；但它**不能保留完全真实的每层遮挡顺序**，对高 Alpha、颜色差异明显或深度层复杂的情况会产生误差。

### 7. 主要 OIT 方案如何比较？

| 方案 | 正确性与特点 | 主要成本 / 适用情境 |
|---|---|---|
| 传统 Back-to-Front | 排序正确时可精确 source-over | 对交错几何难以全局排序 |
| Depth Peeling | 足够层数下逐像素正确排序 | 多 Pass、重复渲染 |
| Dual Depth Peeling | 双向剥层，降低部分 Pass 需求 | 算法与资源管理复杂 |
| A-Buffer / PPLL | 保存每像素层后排序 | 显存、原子与排序成本 |
| Weighted Blended OIT | 较便宜的顺序无关近似 | 高不透明度、颜色/层次复杂时不精确 |
| A2C / Dither | 覆盖近似，不是普适透明合成 | 适合树叶/细几何等特定材质 |

### 8. 面试被问“你会选哪种 OIT”时怎么回答？

以画质要求、层数、显存、目标平台、MSAA、移动/桌面硬件能力为准：

- 大量普通粒子且允许近似：可评估 Weighted Blended。
- 希望逐像素严格排序且层数有限：可评估 Depth Peeling。
- 能接受显存/原子成本并希望收集许多片元：可评估 PPLL。
- 草叶、栅栏等 Coverage 几何：优先考虑 Masked/A2C/Dither 而非直接上复杂 OIT。
- 光学玻璃/折射：还要评估 Refraction / Transmission，普通 OIT 并不自动解决。

## 十四、透明渲染与 Deferred / Forward 的关系

### 1. Deferred Rendering 为什么对透明材质不友好？

典型 Deferred GBuffer 的每像素数据更接近**存储一个最主要的表面**（或特定的 Sample 表面数据）。传统半透明需要多层表面依次贡献颜色，单层 GBuffer 不够表达。

因此常见架构：

~~~text
Opaque Geometry -> GBuffer -> Deferred Lighting
                                      |
                                      v
                               Opaque Scene Color
                                      |
                                      v
Transparent Forward Pass -> Blend into Scene Color
                                      |
                                      v
                              Post Processing
~~~

但这不是说 Deferred 绝对不能处理透明。通过多层数据、特殊 Pass 或 OIT 也可以扩展。

### 2. 为什么 Forward 对透明更直接？

Forward Shader 可以直接针对每层透明表面计算材质/光照，再把颜色按需要与已存在的目标颜色混合，不依赖“每像素只能存一个 GBuffer 表面”的基本设计。

不过排序、Overdraw 和多光源成本仍在，Forward 并不会自动实现 OIT。

### 3. 透明物体是否应该参与 Shadow Map？

视材质和效果而定：

- Masked 物体可以按 Alpha Cutout 写入 Shadow Map，产生洞洞的阴影。
- 传统半透明表面通常需要特殊方案才能表达**透射彩色阴影**，直接当不透明投影可能不符合预期。
- 某些引擎通过 Dithered Shadow、特殊 Transmission/Colored Shadow 或 Ray Tracing 近似。

不要从“可见颜色有 Alpha”推断阴影一定使用相同的混合路径。

### 4. 透明渲染为什么会增加 Overdraw？

多个透明层都可能通过不透明深度测试，并执行 Fragment Shader / Blending；即使被近处透明层部分遮住，远处的层也可能需要贡献颜色。

因此粒子系统的大面积覆盖、复杂玻璃材质和发光特效容易成为 Fragment/Blend/Bandwidth 负担。

## 十五、RenderDoc 与引擎调试案例

### 1. 物体莫名其妙被挡住，应该怎么查？

依次检查：

1. Depth Attachment 是否绑定正确、何时 Clear。
2. DepthFunc 是否与当前普通/Reversed-Z 对应。
3. Depth Write 状态是否被前一个 Pass 遗漏改变。
4. Vertex Shader 输出与投影矩阵、Viewport 是否匹配。
5. 是否发生近远裁剪或 Depth Clamp。
6. Depth Pre-Pass 与正式 Pass 是否深度计算一致。
7. 某个 Draw Call 是否使用了错误深度值/偏移。

RenderDoc 的 Pipeline State、Texture Viewer、Pixel History（支持时）可辅助定位。

### 2. 透明玻璃后面的物体突然消失，优先查什么？

首先检查透明 Pass 是否**错误开启 Depth Write**。其次检查是否正确开启 Blending、Depth Test 和 Back-to-Front 排序。

如果是玻璃彼此相交，仅靠物体排序可能不够，需要更细粒度排序或 OIT。

### 3. 透明贴图边缘出现黑边或白边，可能是什么原因？

常见排查方向：

- Straight/Premultiplied 表示与 Blend State 不匹配。
- 完全透明像素里存在错误 RGB，过滤时混入。
- sRGB / Linear 转换不一致。
- Mipmap 生成过程没有正确处理 Alpha 表示。
- Clamp/Repeat 或纹理边界像素不符合预期。

### 4. 使用 Reversed-Z 后，SSAO/SSR/Soft Particle 为什么坏了？

这些效果可能隐含“Depth 越小越近”或错误地把设备深度直接视为线性距离。

检查 Depth Reconstruction、Hi-Z 归约、屏幕空间深度比较和自定义 Shader 中所有相关分支。

### 5. 为什么画面前景 Z-Fighting 不一定能通过提高 24-bit 到 32-bit 解决？

还要确认：

- 几何是否本身共面。
- 不同 Pass 是否有不同投影/顶点动画计算路径。
- 是否存在过量或错误方向 Depth Bias。
- 使用普通还是 Reversed-Z 深度。
- 目标距离和 Near Plane 的设置。

## 十六、OpenGL 工程示例：分阶段设置 Depth / Stencil / Blend

下面代码展示状态配置思路，不是完整可运行的渲染器。假设普通深度 Near → 0、Far → 1，颜色采用与 Blend 状态一致的 Linear RGB。

### 1. Frame 开始与不透明 Pass

~~~cpp
// 假定绑定了完整的 Framebuffer 与有效的 Color/Depth Attachment
glEnable(GL_DEPTH_TEST);
glDepthFunc(GL_LESS);
glDepthMask(GL_TRUE);

glDisable(GL_BLEND);
glDisable(GL_STENCIL_TEST);

glClearDepth(1.0);
glClear(GL_COLOR_BUFFER_BIT | GL_DEPTH_BUFFER_BIT);

// DrawOpaque();
// DrawMasked();   // 若使用 discard，需要按材质考虑深度/性能
~~~

### 2. Transparent Pass

~~~cpp
// Opaque depth 已经填好
glEnable(GL_DEPTH_TEST);
glDepthFunc(GL_LESS);
glDepthMask(GL_FALSE);

glEnable(GL_BLEND);
glBlendEquation(GL_FUNC_ADD);
glBlendFuncSeparate(
    GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA,
    GL_ONE,       GL_ONE_MINUS_SRC_ALPHA
);

// SortTransparentBackToFront();
// DrawTransparent();

glDepthMask(GL_TRUE);
glDisable(GL_BLEND);
~~~

这里透明 Shader 应输出 **Straight Alpha**。如果 Shader 输出 Premultiplied Alpha，请改用第十节的 BlendFunc。

### 3. Stencil 模型描边的基本设置

~~~cpp
// Pass A: 正常绘制模型并留下模板标记
glEnable(GL_STENCIL_TEST);
glStencilMask(0xFF);
glStencilFunc(GL_ALWAYS, 1, 0xFF);
glStencilOp(GL_KEEP, GL_KEEP, GL_REPLACE);

// DrawBaseObject();  // 在深度通过的位置写入 Stencil=1

// Pass B: 仅在不等于 1 的位置画放大后的模型
glStencilMask(0x00);
glStencilFunc(GL_NOTEQUAL, 1, 0xFF);
glStencilOp(GL_KEEP, GL_KEEP, GL_KEEP);

// 根据所需描边遮挡效果设置 Depth Test / Depth Write
// DrawExpandedObject();

// Restore 状态
glStencilMask(0xFF);
glDisable(GL_STENCIL_TEST);
~~~

**状态管理注意：** 引擎里不能随意遗漏状态恢复。渲染状态由 Render Pass / PSO / Command List / State Cache 统一管理，往往比在各业务模块直接零散调用更可靠。

### 4. 使用 Reversed-Z 的基本状态示例

~~~cpp
// 前提：投影矩阵和 Clip Control 已正确采用 [0,1] 深度约定
// OpenGL 需要支持相应 glClipControl 功能/扩展。
glClipControl(GL_LOWER_LEFT, GL_ZERO_TO_ONE);

glEnable(GL_DEPTH_TEST);
glDepthFunc(GL_GREATER);
glDepthMask(GL_TRUE);
glClearDepth(0.0);
glClear(GL_DEPTH_BUFFER_BIT);

// 此处使用相应 Reversed-Z Projection Matrix
// DrawOpaque();
~~~

**不能只改深度比较函数，不改投影矩阵与相关深度重建路径。**

## 十七、秋招高频面试题与追问

### Q1：为什么需要 Z-buffer？它解决了什么问题？

解决不透明图元在屏幕 Sample 上的最近可见性选择，避免严格依赖 CPU 排序；不解决所有半透明层的正确合成。

### Q2：Depth Test 与 Depth Write 有什么区别？

一个决定是否通过可见性测试，另一个控制是否将结果写回深度缓冲；可以测试但不写深度。

### Q3：为什么 Near Plane 对精度影响更明显？

透视深度与距离成 `A+B/d` 关系，局部深度分辨能力随距离下降，Near 设置过小会进一步恶化远距离精度。

### Q4：什么是 Z-Fighting？有哪些缓解方法？

相近深度因量化或数值路径无法稳定区分；改善 Near、Reversed-Z、几何分离、合理 Depth Bias、保持 Pass 一致性。

### Q5：Reversed-Z 为什么一般搭配浮点 Depth？

利用浮点值靠近零时更密集的分布，缓解远处透视深度压缩；定点 Depth 仅反转本身不能带来同样优势。

### Q6：使用 Reversed-Z 要同步修改什么？

投影和 Clip Depth、Depth Clear、比较函数、深度重建、Hi-Z、屏幕空间效果，以及某些 Bias 逻辑。

### Q7：Early-Z 有什么好处？什么情况可能受限制？

减少被遮挡 Fragment 的昂贵着色；深度写入、Discard、Shader Side Effect 等可约束 Early Test。

### Q8：Depth Pre-Pass 为什么可能让渲染更快，也可能更慢？

在高 Overdraw/昂贵 Shader 场景可节省 Fragment 成本；但会重复顶点/图元工作、产生额外带宽与 Pass 开销。

### Q9：Hi-Z 与普通 Z-buffer 的区别是什么？

Hi-Z 用层次化、较粗粒度的深度信息做提前拒绝；普通 Z-buffer 保存更细粒度的深度测试状态。

### Q10：构建 Hi-Z 一定使用 Max 吗？

不一定，取决于 Depth Compare、普通还是 Reversed-Z、遮挡测试目标及覆盖保守性。

### Q11：Stencil Buffer 有什么作用？

存屏幕区域标签/计数，可实现区域 Mask、描边、部分阴影体算法等。

### Q12：StencilOp 的三个参数各对应哪种情况？

Stencil 失败、Stencil 通过但 Depth 失败、Stencil 和 Depth 都通过时的操作。

### Q13：Opaque、Masked、Transparent 该怎么区分？

Opaque 完全覆盖；Masked 二值覆盖；Transparent 需要多层颜色合成。

### Q14：为什么透明物体要关闭 Depth Write 但保留 Depth Test？

仍需要被前景不透明物体遮挡，但不应阻止后续透明层贡献颜色。

### Q15：为什么透明材质通常 Back-to-Front？

因为 `source-over` 一般不满足交换律；先画远层再画近层才能获得预期叠加顺序。

### Q16：物体中心排序为什么不能保证正确？

大物体、互相穿插或三角形投影交叉会产生屏幕不同区域前后关系不一致。

### Q17：Straight 与 Premultiplied Alpha 的区别是什么？

RGB 是否已经乘自身 Alpha；Shader 输出与 BlendFunc 必须配套。

### Q18：正确的 Premultiplied source-over 公式是什么？

$$
c_{\mathrm{out}}=c_s+(1-\alpha_s)c_d,
\qquad
\alpha_{\mathrm{out}}=\alpha_s+(1-\alpha_s)\alpha_d.
$$

### Q19：为什么简单 glBlendFunc 会算错目标 Alpha？

RGB 的 Source 因子可能是 `srcAlpha`，但 Alpha 通道的 Source 因子需要 `ONE`，应考虑使用 `glBlendFuncSeparate`。

### Q20：Premultiplied Alpha 纹理为什么有时能减少透明边缘黑边？

因为零 Alpha 像素对应的 RGB 贡献也为零，过滤与合成更容易保持一致，但颜色空间和数据转换仍需正确。

### Q21：Alpha Blending 可以直接在 sRGB 中做吗？

一般应在 Linear RGB 中执行颜色合成，不能把 sRGB 编码值当成线性光强。

### Q22：MSAA Alpha-to-Coverage 是真实连续透明混合吗？

不是，它把 Alpha 转成多 Sample 覆盖，适合细几何 Coverage 近似，但不是普适的多层透明合成。

### Q23：什么是 OIT？有哪些主要方法？

Depth Peeling、Dual Depth Peeling、A-Buffer/PPLL、Weighted Blended 等，要区分精确/近似及资源成本。

### Q24：为什么 Weighted Blended OIT 是近似算法？

它积累的是加权统计量，通常丢失了每像素各层的完整深度排序信息。

### Q25：PPLL 的瓶颈和风险有哪些？

节点内存、原子操作、每像素排序成本、溢出策略和 GPU 内存同步。

### Q26：Deferred 为什么通常另用 Forward 绘制透明？

单层 GBuffer 不容易表达多个透射层的颜色贡献，Forward 可直接逐层着色并参与 Blend。

### Q27：如何解决软粒子和场景几何交界处的硬边？

读取场景深度，在同一度量中比较粒子深度，按交界距离调整 Alpha。特别注意 Reversed-Z 与非线性设备深度。

### Q28：RenderDoc 如何定位透明消失与 Z-Fighting？

查看 Depth Attachment、Blend/Depth/Stencil State、Pixel History、相关 Draw Call 和 VS/FS 输出，检查是否发生错误的 Depth Write 或 Alpha 表示不一致。

### Q29：如果用户反馈“透明玻璃互相穿插颜色错误”，怎么做技术选型？

先确认排序粒度、效果要求和平台性能，再比较拆分排序、Depth Peeling、PPLL 或 Weighted Blended OIT 的质量与成本。

### Q30：为什么说 Depth Buffer 只保存最近深度，不足以实现严格 OIT？

多个透明层都要对最终颜色做贡献；只有一个最近深度无法恢复它们的排序和各自颜色/Alpha 数据。

## 十八、动手验证题

### 练习 1：自己推导深度重建

从：

$$
z(d)=\frac{f}{f-n}-\frac{fn}{(f-n)d}
$$

推出：

$$
d=\frac{fn}{f-z(f-n)}.
$$

然后选取 `n=0.1`、`f=100`，检验 `z=0`、`z=1` 分别映射到 `0.1` 与 `100`。

### 练习 2：手算两个透明层的混合顺序

令不透明背景为黑色，透明红层和蓝层 Alpha 都为 `0.5`。

分别计算红盖蓝与蓝盖红：

$$
C_{R\ \mathrm{over}\ B}=(0.5,0,0.25),\qquad
C_{B\ \mathrm{over}\ R}=(0.25,0,0.5).
$$

验证 `source-over` 不满足交换律。

### 练习 3：验证 Straight 和 Premultiplied

向不透明黑色背景绘制 Alpha 为 `0.25` 的红色层：

- Straight 输出 `(1,0,0,0.25)`，使用正确 Straight BlendFunc。
- Premultiplied 输出 `(0.25,0,0,0.25)`，使用正确 Premultiplied BlendFunc。

预期颜色相同。然后故意交叉使用 BlendFunc，观察错误变暗/变亮。

### 练习 4：实现 Stencil 描边

绘制一个旋转的模型，使用 Stencil 标记原始区域并仅在外侧绘制扩张版本。旋转、缩放模型，检查描边厚度是否符合预期。

### 练习 5：Depth Pre-Pass 性能实验

在相同分辨率下设置：

- 低/高 Overdraw。
- 简单/昂贵 Fragment Shader。
- 开关 Pre-Pass。

同时记录 GPU Frame Time、Pre-Pass、Main Pass 的时间，分析什么时候预通过值得使用。

### 练习 6：实现简易 Hi-Z 遮挡判断

使用普通 LESS 深度和一个完全覆盖区域的 Depth Map，建立 Max Pyramid；对候选矩形及其深度范围做保守遮挡判断。然后切换 Reversed-Z，重新推导正确归约/比较方向。

### 练习 7：透明交错的对照渲染

绘制两个相互穿插的透明三角形或玻璃片，分别尝试：

1. 固定绘制顺序。
2. 对象中心排序。
3. 三角形细粒度排序。
4. 如果有时间，使用 Weighted Blended OIT。

观察不同区域的错误及各方案的性能。

## 十九、公式和关键结论速记

| 知识点 | 公式 / 结论 |
|---|---|
| 常规 Depth | Near=0、Far=1，常用 LESS，Clear=1 |
| Reversed-Z | Near=1、Far=0，常用 GREATER，Clear=0 |
| 普通透视深度 | `z(d)=f/(f-n)-fn/((f-n)d)` |
| 线性距离重建 | `d=fn/(f-z(f-n))` |
| Reversed-Z 无限远 | `z(d)=n/d` |
| 深度误差趋势 | `Δd ≈ ((f-n)d²/(fn))Δz`（均匀 Δz 近似） |
| Polygon Offset | `offset = m * factor + r * units`（概念式） |
| Straight over 不透明背景 | `Cout = αs Cs + (1-αs) Cd` |
| Premultiplied over | `cout = cs + (1-αs) cd` |
| Composite Alpha | `αout = αs + (1-αs) αd` |
| Transparent | 一般 Depth Test ON、Depth Write OFF、Back-to-Front |
| Masked | 二值覆盖，可正常做 Depth Test/Write |
| StencilOp | sfail、dpfail、dppass |
| Hi-Z | 保守多层深度，归约方向取决于约定 |
| OIT | Depth Peeling、A-Buffer/PPLL、Weighted Blended |
| A2C | Alpha 转多采样 Coverage，不等于标准连续透明 |
